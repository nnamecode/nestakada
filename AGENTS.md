# Инструкции проекта «Эстакада»

## Начало работы

Прочитать README.md, docs/decisions.md и docs/tasks.md. По задаче обращаться к docs/pipeline.md и соответствующему утверждённому документу. Не считать переписку единственным хранилищем требований.

## Управление работой

- Общаться с владельцем по-русски. Работать по согласованным этапам. Не переходить через требуемое согласование без ответа владельца.
- Если требование непонятно, задавать владельцу вопросы и предлагать варианты решения; не переспрашивать уже зафиксированные договорённости.
- Перед новым инструментом или существенной настройкой объяснять, что это, зачем нужно проекту, какие есть альтернативы и что изменится на компьютере владельца.
- Принятые решения записывать в docs/decisions.md с датой и основанием. Предложения не выдавать за утверждённые решения; отложенные идеи хранить в docs/future-ideas.md.
- В docs/tasks.md обновлять номер задачи, описание, статус, зависимости и результат. Выполненные задачи отмечать только по факту, не при создании плана.
- Технологическая основа согласована: Python/Django, PostgreSQL, адаптивные серверные HTML/CSS-шаблоны и немного JavaScript. Конкретная архитектура, версии и зависимости проходят отдельное согласование.
- Сейчас лайт-версия. D-077 добавляет блок заявки на запись на главной, его дизайн/содержание/обработку прорабатывать после утверждения дизайна главной; до подготовки правового и технического процесса данные не собирать. Отдельный обратный звонок, клиентский кабинет, API Android и чат остаются будущими этапами. Редактор содержимого и блоков не должен позволять исполнять произвольные Django-шаблоны, Python или JavaScript.
- Вход администратора — логин и пароль. Не добавлять второй фактор, email-подтверждение или CAPTCHA без нового решения. Обсуждение раздела «Логи» возобновлено владельцем 2026-10-27 (D-037/D-038); предложения в docs/logging-proposal.md, полный объём и правила ещё не утверждены.

- Первая версия сохраняет старую структуру, тексты и точные URL рекламируемого сайта (D-023). Редирект не заменяет требование идентичного адреса. Фото собственных работ из /gallery-of-works/ переносить побайтно без изменений (D-024), это исключение из общей оптимизации изображений. Остальные иллюстрации создавать заново по смыслу услуги (D-025). Рерайт и новые видео — будущие работы. Формы остаются за пределами MVP (D-027).

- Права сотрудников и версия страницы: D-030/D-031 уточняют D-028/D-029. По уточнениям D-042/D-043 сотрудник сохраняет разрешённый текст сразу на публичном сайте; система при каждом сохранении создаёт новую автоматическую версию и сохраняет прежние. Ручные именованные версии создаёт/удаляет только администратор; сотрудник не публикует защищённые поля или чужие черновики. Восстановление не меняет защищённые поля и URL. Новые опубликованные разделы/страницы автоматически включаются в соответствующую навигацию (D-032).

- По решению D-041 сначала согласовать область админки, затем архитектуру и её ревью/согласование, дизайн админки и его согласование; после — публичный дизайн. Основа для обсуждения: docs/admin-design-brief.md. Требования к общим данным, URL и публикации сохраняются; согласования и тесты до кода не пропускать.

- По D-044/D-045 хранить 10 последних обычных версий каждой страницы и все Stable вне лимита. Цветную Stable ставит только владелец, в том числе после просмотра версии сотрудника; сотрудник не назначает/не снимает метку. Stable и её файлы защищены от очистки/удаления, новое сохранение не меняет Stable и не наследует метку автоматически.

- D-046: на назначенной странице сотрудник видит все обычные, ручные и Stable-версии с меткой; нет отдельного ограничения просмотра версий. Восстановление остаётся только по разрешённым текстовым полям. При превышении лимита выбывает самая старая обычная версия, Stable неизменна и исключена из очистки. Исторические версии закрыты от обычных посетителей.

- Исключение D-047/D-048: подтверждённое владельцем удаление всей страницы удаляет все её версии, включая Stable. Перед действием явное актуальное подтверждение названия/URL и состава истории. Сотрудник не удаляет страницу; общие файлы других страниц сохраняются. Отдельное удаление Stable и её очистка по лимиту по-прежнему запрещены; поддерево не удалять неявно.

## Делегирование и экономия токенов

Команда и три навыка в docs/team-and-skills.md согласованы владельцем 2026-10-26 (D-021). Инструкции ролей — docs/agent-roles.md. Привлекать только нужные роли на ограниченные задачи с явным результатом; не создавать отдельные пользовательские чаты для внутренних задач.

При обнаружении цикла немедленно остановить работу агента и сообщить владельцу. Признак цикла: повтор той же ошибки второй раз при эквивалентном действии без нового свидетельства или изменившегося условия. Не делать третью однотипную попытку. Явный бессмысленный цикл останавливать сразу, не дожидаясь счётчика.

Передать агенту обязанность сообщать первую ошибку и причину планируемого повтора. Координатор при повторе прерывает агента; статус задачи — «Приостановлено владельцу». В отчёте: задача, ошибка без секретов, число попыток, что проверено, варианты решения. Возобновлять только по решению владельца. Не обещать мгновенный контроль внутри непрозрачного вызова инструмента: проверять на доступных границах сообщений и вызовов.

Максимум три субагента одновременно с координатором, предпочтительно один исполнитель и один независимый рецензент. Не редактировать одни файлы параллельно. Рецензент не подменяет проверку своего же изменения независимым ревью. Не перечитывать весь проект без необходимости.

## Проверки и публикация

- Связывать требования, задачи и приёмочные сценарии постоянными идентификаторами.
- Перед реализацией писать согласованные приёмочные e2e-сценарии; после — добиваться их прохождения. Юнит-тесты покрывают правила и граничные случаи, а не повторяют строки реализации.
- Не изменять живой сайт и не развёртывать продукт без отдельного разрешения.
- GitHub push разрешён владельцем в конце рабочей смены после настройки репозитория. Не выдумывать расписание: пока нет времени смены, выполнять завершение по сообщению владельца. Не создавать автоматизацию без определённого расписания.
- Не отправлять секреты, пользовательские данные, логи, дампы и оригиналы фотографий в Git. Не применять force push и разрушительные Git-команды без явного разрешения.
- Изменения с помощью ИИ проходят обычные проверки, тесты и ревью; не выкладывать их автоматически.
