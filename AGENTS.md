# Инструкции проекта «Эстакада»

## Начало работы

Сначала прочитать `docs/currentprocent.html` и только относящийся к задаче утверждённый документ. README, `docs/decisions.md`, `docs/tasks.md` и `docs/pipeline.md` читать точечно, когда нужны историческое основание, зависимость или стабильное правило. Не перечитывать многолетний журнал целиком и не считать переписку единственным хранилищем требований.

## Управление работой

- Общаться с владельцем по-русски. Работать по согласованным этапам. Не переходить через требуемое согласование без ответа владельца.
- Если требование непонятно, задавать владельцу вопросы и предлагать варианты решения; не переспрашивать уже зафиксированные договорённости.
- В конце существенного этапа и по запросу владельца обновлять и называть текущий/следующий шаг по `docs/currentprocent.html`, чтобы точку продолжения можно было восстановить в новом чате.
- При обсуждении требований нумеровать вопросы и ответы устойчивыми идентификаторами; неотвеченные вопросы повторять с тем же номером, пока владелец не ответит или явно не отложит их.
- По решению владельца 2026-11-14 не требовать от него вводить служебные идентификаторы для обычного продолжения или исправления. Ответы «продолжай» и «почини и продолжай» принимаются как согласие на непосредственно предложенный ближайший ограниченный этап; постоянные ID сохранять внутри документации для трассировки. Это не заменяет отдельное явное разрешение на live/deploy, push, внешнюю установку, разрушительное действие или существенное расширение области.
- По решению D-1363 от 2026-11-17 внутри уже согласованного bounded work package не останавливать владельца после каждого микроэтапа. Координатор самостоятельно проходит связанную цепочку documentation remediation, independent/repeat review, малое исправление замечаний и статические проверки, сообщая прогресс в commentary. Возвращать управление владельцу только при реальном выборе, anti-loop/blocker, завершении заметного REBUILD-этапа либо перед runtime/Docker/media read, live/deploy, push, внешней установкой, разрушительным действием или существенным расширением scope. Это правило не отменяет обязательные review/gates, а только убирает лишние ручные «продолжай» между ними.
- По решениям владельца D-399 и уточнению 2026-11-21 функционал и стабильность имеют приоритет над процессом. `docs/currentprocent.html` — единственный оперативный статус; дополнительный файл оперативного статуса запрещён. Не копировать одну текущую точку в README/tasks/pipeline/decisions и не создавать новый D-ID для каждого probe, review или малого исправления. Один ID ведёт существенный work package до результата либо реального блокера.
- Применять пропорциональное ревью. Independent review обязательно для архитектуры, security/privacy, destructive/data semantics, concurrency, migrations и release gates. Малые docs/test/harness-only исправления без изменения product contract, topology или доступа к данным можно закрывать self-review и релевантными статическими проверками.
- Одно явное разрешение на bounded local runtime package покрывает initial run и максимум одну materially changed confirmation после малого reviewed harness/test-only исправления, если initial run завершился до product execution, cleanup/post-audit чистые, product source и scope/topology/data access не изменились. Повтор той же стадии, третья попытка, product fix, новая topology/network/media read либо неясный cleanup требуют нового решения владельца. Live/deploy, push, внешняя установка и destructive action всегда имеют отдельный gate.
- Перед новым инструментом или существенной настройкой объяснять, что это, зачем нужно проекту, какие есть альтернативы и что изменится на компьютере владельца.
- В `docs/decisions.md` записывать только долговечные решения владельца, изменения scope/архитектуры/риска и важные исключения — с датой и основанием. Обычный результат теста или промежуточное review решением не является. Предложения не выдавать за утверждённые решения; отложенные идеи хранить в `docs/future-ideas.md`.
- В `docs/tasks.md` обновлять только существенные work packages, их зависимости и итог. Микроэтапы, probes и repeat reviews остаются внутри результата пакета. Выполненные задачи отмечать только по факту.

## Делегирование и экономия токенов

Команда и три навыка в docs/team-and-skills.md согласованы владельцем 2026-10-26 (D-021). Инструкции ролей — docs/agent-roles.md. Привлекать только нужные роли на ограниченные задачи с явным результатом; не создавать отдельные пользовательские чаты для внутренних задач.

При обнаружении цикла немедленно остановить работу агента и сообщить владельцу. Признак цикла: повтор той же ошибки второй раз при эквивалентном действии без нового свидетельства или изменившегося условия. Не делать третью однотипную попытку. Явный бессмысленный цикл останавливать сразу, не дожидаясь счётчика.

Передать агенту обязанность сообщать первую ошибку и причину планируемого повтора. Координатор при повторе прерывает агента; статус задачи — «Приостановлено владельцу». В отчёте: задача, ошибка без секретов, число попыток, что проверено, варианты решения. Возобновлять только по решению владельца. Не обещать мгновенный контроль внутри непрозрачного вызова инструмента: проверять на доступных границах сообщений и вызовов.

Максимум три субагента одновременно с координатором, предпочтительно один исполнитель и один независимый рецензент. Не редактировать одни файлы параллельно. Рецензент не подменяет проверку своего же изменения независимым ревью. Не перечитывать весь проект без необходимости.

## Проверки и публикация

- Связывать требования, задачи и приёмочные сценарии постоянными идентификаторами.
- Перед реализацией писать согласованные приёмочные e2e-сценарии; после — добиваться их прохождения. Юнит-тесты покрывают правила и граничные случаи, а не повторяют строки реализации.
- Не изменять живой сайт и не развёртывать продукт без отдельного разрешения.
- GitHub push разрешён владельцем в конце рабочей смены после настройки репозитория. Не выдумывать расписание: пока нет времени смены, выполнять завершение по сообщению владельца. Не создавать автоматизацию без определённого расписания.
- Не отправлять секреты, пользовательские данные, логи, дампы и оригиналы фотографий в Git. Не применять force push и разрушительные Git-команды без явного разрешения.
- Изменения с помощью ИИ проходят обычные проверки, тесты и ревью; не выкладывать их автоматически.
