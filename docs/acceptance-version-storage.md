## Что проверяется

Для restore ресурсный отказ допускается уже при prepare, если показана та же понятная причина и ничего не применено. Тест не требует выдавать подтверждение заведомо невозможного восстановления; если prepare допускает сравнение/подтверждение, действительный apply всё равно обязан отказать целиком.

- Header/Footer делят бюджет **256МиБ=268435456байт /10000снимков**, отдельно от медиа. При заполненном счётчике или недостаточном остатке под фактическую новую запись/накладные расходы ни публикация, ни восстановление не создают частичный снимок. Текущие/черновые/обычные/защищённые состояния и Asset не удаляются автоматически. В открытой вкладке остаётся введённый текст.
- При измеренной занятости не менее75% и достаточном остатке владелец видит предупреждение, но допустимая публикация проходит. Это положительный контроль того же реального handler для каждого блока. Полоса75–90% — условие тестовой fixture с запасом, не новая граница продукта.
- В Page save и в явном применении старой версии отдельно отказывают запись версии и сохранение Asset reference. Проверяется фактическое достижение семантической точки ошибки и подтверждённый rollback, неизменность всей бизнес-проекции и публичного содержимого/валидатора, сохранность ввода. После снятия технического отказа то же явное сохранение проходит:ровноодна новая версия, нужный разрешённый текст публичен, защищённые снимки целы.
- Несовместимая Page-версия отклоняется при подготовке; исходный payload/схема не переписаны, публичное состояние и собственный ввод не меняются. Полная unsafe-migration/прямая подделка подтверждения/изменение совместимости после prepare остаются отдельно.

## Реальные fixture и подготовка UI

`shared-history-resource-boundary({kind,resource,operation})`:два настоящих общих блока с независимыми историями и поодному действующему черновику, реальная Page P-ONE и реальные удерживаемые Asset; совместимый исторический restoreVersionId не равен текущему. Ветка count-full действительно содержит10000снимков обоих блоков, не fakecounter. bytes-insufficient имеет меньше10000 и реальный измеренный остаток меньше фактической prospective reservation текущей операции. Не требуется достичь ровно256МиБ на любойFS. warning-band содержит занятость75–90%, подходящий допустимый HTML-ввод размером ниже лимита и достаточно места/числа под ещёодин снимок.

`content-storage-save-restore({operation})`:S-EDIT имеет действующее назначение P-ASSIGNED/разрешённый текст и неизменяемый текущий Asset, история содержит старый совместимый снимок. Для save допустимый input уже открыт; для restore подготовка+stage выполняются настоящими existing handler/UI, и fixture.input равен именно историческому разрешённому тексту. Сохранение текста не даёт сотруднику новых прав на картинки:ссылка Asset новой истории — удержание прежнего допустимого файла. `content-storage-incompatible-history` добавляет реальный сохранённый несовместимый снимок, который не меняется тестом ради обхода совместимости.

Профили обязаны использовать reviewed `profileSetups`:настоящий actor goto/fill до проверок, без POST/автосохранения. GuardUIpreparation получает actual-db `ui-preparation-business-state` с обязательными pages **и sharedBlocks**. Pages — настоящая P-ONE/P-ASSIGNED, общие блоки не маскируются под Page. Вся serialized before/after проекция сравнивается guard, sharedBlocks содержит current/draft/revision/history/media. Это доказывается при проверке concretebindings, не флагом inputPreparedByActualUi самим по себе.

## Наблюдения

- `version-storage-fixture`:реальные выбранные input/restoreVersionId/incompatibleVersionId/kind и свидетельство подготовки UI, не готовые результаты действий.
- `version-storage-business-state` — actual-db/files устойчивые arrays pages/blocks/versions/assetReferences/assetFiles/protectedSnapshots. Pages/blocks/versions содержат текущие/черновые значения, revision/ID и полный состав истории; assetFiles — ID/размер/SHA256 **фактических байтов**, не хэш ожидаемого текста. protectedSnapshots включает существующие защищённые/Stable/используемые состояния, их payload/schema/references. Никаких wholeDBdigest с логами/таймерами/telemetry, готового expected или секретов. Состав в fixture не пуст, два блока проверяются явно.
- `version-storage-public-response` — actual-http реальная Page P-ONE/P-ASSIGNED, status/pageText/headerHtml/footerHtml/etag, извлечённые из настоящего ответа. Это семантическая проекция, не выбранная разметка сайта. Текст тестовой Page — обычный абзац, поэтому pageText совпадает с fixture.input после успешной публикации; HTML общих блоков заранее канонизирован fixture.
- `shared-history-resource-usage` — limitBytes/limitSnapshots, usedBytes/snapshotCount, nextReservationBytes и фактическая разбивка snapshotDataBytes/indexBytes/metadataBytes/temporaryBytes, их сумма равна usedBytes, mediaBytesExcluded=true/source=actual-storage-measurement. nextReservationBytes относится к **той же текущей publish/restore операции**, учитывает её собственный сериализованный снимок/ссылки/временную накладную стоимость; не задан тестом как желаемое превышение. Должен быть описан надёжный механизм reservation и его первичные измерения. Физические индексы/temp не прячутся вне квоты. Точные sizing/allocator/пики/параллельные writers требуют отдельных ресурсных испытаний.
- `shared-block-draft-counts` — actual-db число действующих черновиков каждого блока, по1 до/после отказа. Не скрывает дополнительные неиспользуемые строки под новым ID.
- `open-header-input`/`open-footer-input` — observations kind=ui-input, фиксированный locator реального owner editor текущего блока. `open-editor-input` — existing kind=ui-input для настоящего S-EDIT редактора Page. Нельзя заменить fixture-read/переданным input. `editor-memory-state` — существующий драйверный kind=ui-memory, прямое чтение своего actor URL/localStorage/sessionStorage, без копии текста в выводе.
- `content-storage-fault-evidence` — фактические faultId/pageId/phase/hitCount и DB/transaction доказательство rollbackConfirmed. Сам ярлык stage не заменяет before/after actual-db сравнение.
- `page-version-payload` — actual-db исходный versionId/schemaVersion/payload/Asset refs и выбранная реальной compatibility-проверкой совместимость. Неподдерживаемый historical payload остаётся доступен как данные; подготовка применения действительно отказывает.

## Действия и технический fault-domain

Existing `shared-block`, `prepare-shared-block-restore`, `apply-shared-block-version`, `prepare-page-version-restore`, `stage-page-version-restore`, `save-open-editor` вызывают настоящие owner/employee UI/HTTP handlers. `save-open-shared-block(kind,base)` — реальный click явной публикации открытого owner input, принятый только по действительному результату сервера, не200самомупосебе. `read-shared-history-budget(kind)` — реальный авторизованный HTTPread с warningText из показанного владельцу HTML; не уводит actor page из открытого редактора и не принимает заранее вычисленный pass от fixture.

Перед fault/reset требуется independently reviewed isolated ARC-10 admission и **content-storage-control-v1**. Только `set-content-storage-fault(pageId,phase,fault=persistent-test-storage-error)` / `clear-content-storage-fault(pageId,faultId)` управляют реальным ограниченным IO/transaction fault собственногоrun. Фазы version-persist/asset-reference-persist — семантические точки сохранения версии/удерживающей ссылки, не требование двух отдельных SQLтаблиц/коммитов. Controller не вставляет версии, не переписывает Page, не меняет grants/Stable, не выдаёт заранее запрограммированный denied. Mutation осуществляется через настоящий handler. Изменения root в transport allowlist/permit не реализуют конкретный контроллер.
