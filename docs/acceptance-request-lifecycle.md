## Fixture и подготовка

Все идентификаторы/имена действий — нормализованный тестовый интерфейс, не обязательные URL/ORM/названия кнопок продукта. Операции выполняются через настоящий UI/HTTP и проверяют реальные серверные права, токены и результат, без записи БД вместо действия.

- request-status-matrix/status: реальная R-ONE в заданном статусе, назначена активному S-EDIT, OWNER/S-OTHER/VISITOR отдельные сессии. Непустой исходник/история, настоящие непрозрачные revision/createdAt/ID. Подготовка статуса не даёт посетителю права выбрать его при отправке.
- new-request-assigned-to-S-EDIT: прежний профиль с canary в исходнике и заметках; status=new. Параллельные Promise.all должны реально отправлять две команды, не сериализоваться/вычислять исход в драйвере. Один и тот же operationId передаётся серверу буквально при повторе.
- request-with-two-active-assignees: R-ONE назначена S-EDIT, S-OTHER активен и может быть назначен владельцем, S-OFF существует и выключен. Assignment не меняет original/status/createdAt; история назначения отдельна от статуса.
- request-delete-with-live-receipt: реальная синтетическая заявка с заметкой/исходником, её действительная ранее принятая квитанция/контекст VISITOR, текущий owner passwordRef и заведомо неверный синтетический passwordRef. Начальная отправка/согласие действительно созданы штатным приёмом, не выдуманы receipt-таблицей адаптера. Защита/токены/правовой процесс тестируются только синтетически; LEGAL-01 не считается закрытым.

До **любой** подготовки профиля удаления inspectInfrastructureAdmission() читает фактический независимый ARC-10/isolation/evidence и capability=request-deletion-v1. Без этого — явный отказ теста, не skip. Никакой infrastructure fault/control в этом файле не исполняется. Сам внешний контур ещё отсутствует: клиентский preflight/метка не являются доказательством реального durable commit.

## Действия и наблюдения

prepare-request-reopen возвращает настоящее подтверждение выбранных requestId/fromStatus/current base. Получение подтверждения не меняет заявку. reopen-request-direct делает фактический серверный переход; нельзя подставить confirmation=true в адаптере. Одинаковый действительный набор аргументов используется в отрицательном запросе чужой роли и положительном запросе владельца; меняются только сессия/связанные защитные токены. Отказ невалидного payload не считается проверкой права.

assign-request-direct/change-request-status/add-request-note используют настоящую текущую revision, полученную из наблюдения. request отдаёт id/revision/createdAt/status/assignee/original/notes/history; поля обязательны, сравнение двух undefined запрещено. assignee/actor — нормализованные роли, исходный объект/текст не вычисляются по expected. request-record-count читает действительное число записей с тем же ID. История в этих утверждениях — бизнес-изменения, не аудит каждого чтения/отказа.

prepare-request-delete показывает конкретные ID/createdAt и необходимость повторного пароля; confirmation/operationId — opaque значения фактической подготовленной операции. confirm-request-delete-direct/probe-GET-request-delete обращаются к настоящему одному обработчику с допустимыми аргументами. Не создавать фиктивный product endpoint или удалять напрямую через fixture bridge ради зелёного результата.

deleted-request-evidence читает реальное отсутствие Request/его Notes и фактически подтверждённую независимую запись запрета для того же requestId/operationId, с непустым tombstoneId и проверкой, что запись не хранит исходное тело. Полнота/долговечность/связь наблюдения с реальным хранилищем и восстановлением проверяются отдельно на стенде; флаг сам по себе не закрывает anti-rollback.

accepted-request-form-context — отдельное **закрытое actual-db наблюдение** связи действительного intentRef с именно R-ONE. До/после повтора принятой отправки связь и счётчики неизменны. repeat-accepted-form-intent повторяет тот же фактический POST из исходного visitor-контекста, не генерирует новый nonce. Публичный HTTP-результат не должен раскрывать внутренний requestId и не обязан иметь JSON-поля created/requestId; тест больше их не требует. После удаления проверяются нейтральный текст/отсутствие body-canary и неизменность реальных счётчиков независимо от accepted/denied. Полная проверка всех каналов утечки внутреннего ID пока остаётся отдельной privacy-ветвью, не объявлена пройденной этим тестом. form-counters до/после **повтора после удаления** равны; этим не задаётся ещё не выбранная правовая политика хранения Consent при самом удалении.

Нейтральный ответ не является публичной квитанцией с телом/причиной удаления. До удаления доказываются непустые original/notes с REQUEST-PRIVATE-CANARY/NOTE-PRIVATE-CANARY и положительные owner HTTP-чтения того же существующего объекта/заметок. Это только синтетические маркеры, не пароли/пользовательские данные; адаптер не должен скрывать их вместо проверяемого сервера. Наличие правильного текста без проверки отсутствия повторной вставки не является достаточным успехом.
