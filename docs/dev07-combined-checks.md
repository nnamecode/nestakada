# DEV07-CM — совмещённые предельные объёмы

2026-11-01. Контракт и приёмочные сценарии **до нового тестового кода**. Основание — разрешённое владельцем продолжение DEV-07, D-331, dev07-local-processing-profile.md, FR07-006/008 и открытый MEMO-005 из dev07-parser-memo-proposal.md. Это ограниченный следующий ресурсный gate, а не завершение DEV-07 или новая настройка ресурсов. DEV-07 около95%, этап8 около20%; результаты ниже ещё не получены.

## Область и неизменные условия

Только отдельная локальная тестовая БД и собственные синтетические Page/пользователи/версии/черновики. Старый сайт, VPS и публичный предпросмотр не используются. Новых пакетов, инструментов, сетевых служб, контейнерных ресурсов или исключений CSP нет. До независимого ревью этого контракта и отдельного code gate координатора приложение и тесты не меняются.

Каждый Check проходит настоящий framework handler, сессию/CSRF/доступ к Page, получение выбранного сохранённого источника, настоящий normalizer child и PostgreSQL. Допустим только уже описанный FR07-006 seam `read_json_bytes`: он возвращает **те же переданные bytes** без глобального Django HttpRequest.body cache. Результат не является доказательством Nginx/socket admission, браузерного MAX render или production-профиля.

Ресурсы остаются прежними: app768МиБ/1CPU/pids128; child AS384МиБ/CPU10s/wall20s; один heavy slot. Проверки выполняются последовательно. При отказе допустимого максимального кандидата сохраняется FAIL и его измерения. Уменьшение fixture, автоматическое повышение лимитов, отключение проверки или повтор неизменного отказавшего прогона не являются исправлением.

## Точная форма rich-fixture

Один rich-кандидат одновременно достигает четырёх действующих границ: raw UTF-8 **1048576байт**, decoded text **200000 Unicode codepoints**, **20000 HTML элементов**, максимальная глубина **32**. Корневой fragment в число элементов и глубину не входит.

Форма дерева: один корневой `p` на глубине1; внутри31 вложенный `span`, последний на глубине32; под тем же `p` дополнительно19968 пустых sibling `span`. Итого1+31+19968=20000 элементов. В самом глубоком span находится150000 символов 🚀 и50000 ASCII символов:200000 codepoints и650000 UTF-8 байт. Единственный разрешённый `data-es-anchor` корневого p заполняется безопасными ASCII символами до точной общей длины1048576байт. Никаких скрытых comment/text padding, исполняемых атрибутов или изменения лимита.

Fixture имеет четыре различимых значения: сохранённые intro/main и кандидаты intro/main. Их root-anchor labels и ASCII текст различаются при той же длине/числе codepoints; хэши должны быть попарно различны. Это исключает случайный cross-field hit однозаписного exact-string memo. Сохранённые rich-поля в выбранном источнике также имеют размер1МиБ, но служат **retained unprotected source**: пустые layout/embedded_images, без protected markers. Нельзя приписывать им покрытие разбора максимальной protected-map.

Инварианты длины, числа элементов/глубины/decoded text и различия хэшей проверяются до вызова handler. Независимый структурный oracle использует фиксированную формулу fixture и отдельный штатный HTML5 parser вне измеряемого child, а не счётчики оптимизированного parser как единственный expected result. Подготовка/проверка fixture учитывается отдельно от времени handler; её вклад в lifetime cgroup peak явно сохраняется.

Все200000 codepoints не могут одновременно быть четырёхбайтовыми emoji при указанной span-структуре и1МиБ: один текст занимает800000байт, а20000 элементов добавляют достаточно разметки для превышения лимита. Смешанный текст выше достигает именно **codepoint**-границы без ложного заявления о максимуме всех возможных UTF-8 форм.

Для положительного допуска ожидается точное сохранение безопасного canonical rich-source. Если независимый oracle обнаружит нормализацию, repair или изменение длины этой формы, fixture не объявляется заранее canonical: причина предъявляется на ревью до исполнения, а oracle не ослабляется под полученный результат.

## Измерения и конечный oracle

Для каждого actor/scenario фиксируются handler wall, child user+sys CPU delta, exit code и reap, размеры wire/response и source/input/output hashes. Фиксируются реальные cgroup memory.max/cpu.max/pids.max, memory.peak и memory.events до/после, child AS/CPU/wall limits из фактических констант. Общий cgroup peak включает parent+child и подготовку fixture/предыдущие случаи; сумма отдельных несинхронных RSS peaks не выдаётся за общий максимум. При необходимости изолированный первый запуск case даёт более узкое lifetime свидетельство, но измерение не сбрасывается фальшивым oracle.

PASS требует завершённого child, отсутствия роста oom/oom_kill, соблюдения прежних caps, доказанной подписи и полного неизменного доменного состояния. Проверка только HTTP200 или только самостоятельно посчитанного SHA недостаточна. На отказе также обязательны отсутствие proof/частичной записи, reap/закрытые собственные streams, освобождённый EditorSlot и отдельный малый здоровый Check; частично выполненный MAX не становится PASS из-за успешного recovery.

Контентное состояние сравнивается до/после через PageContentState/PageRevision/OwnerDraft/RestoreStage/VersionBasePin/AssetUsage/OperationReceipt. Ограниченный audit/session accounting учитывается отдельно и не маскирует изменение контента. Большие assertion dumps запрещены: расхождение выводит только фиксированный oracle code и безопасные метаданные.

## Явный остаток

CM07-001–003 не закрывают restore-stage combined MAX, максимальные защищённые source maps/медиа, тяжёлые table/attribute/entity CPU-векторы, все границы+1 в комбинации, полный Save/draft commit MAX, Nginx64МиБ/socket перенос и браузерные RSS/render/другие семейства. Ранее прошедшие самостоятельные limits/FR07/entity проверки сохраняют свой ограниченный объём. Новый CM gate не отменяет оставшиеся shared Header/Footer/квоты и остальные partials DEV-07.

Следующий шаг после ревью — отдельный ограниченный test module и запуск координатором на замороженном source; до фактического отчёта все три CM07 сценария имеют статус **не исполнены**.
