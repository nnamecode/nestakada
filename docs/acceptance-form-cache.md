# Форма: условный GET и пригодность защиты

2026-10-30. TEST-04, этап7; частичные связи AT-402 / AC-PRO-002, REQ-050/057/060. Основание: принятый D-301 пакет, PR-01 analytics-protocol-contracts.md; работа разрешена D-308 и текущим поручением владельца. Это тесты и контракты локальной синтетической fixture, не код сайта. Старый сайт/VPS не используются.

## Подготовленные утверждения

`acceptance/form-cache.spec.js`:22экземпляра, по11для home/contacts. В десяти ETag-вариантах меняется ровно один фактор: контекст намерения, CSRF-секрет, согласие, интервал защиты, отсутствие/невалидность context-cookie, публичные данные, шаблон, политика формы; отдельная ветвь сохраняет прежний действующий контекст. Одиннадцатый вариант отправляет только If-Modified-Since с будущей датой, без If-None-Match.

Для неизменного действующего контекста допустимы200и304. При304 используется **раньше полученная** форма, при200 — форма этого полного ответа. Затем ровно один явный настоящий POST обязан создать одну Request/Consent и committed receipt; поля подтверждаются приватным чтением реальной записи. Прямая HTTP-отправка безJS допускает0–1локальную цель. Выдача формы и перепроверка не создают Request/Consent/receipt/сессиюБД. При изменении каждого фактора и IMS-only обязателен полный200; при смене проверяемой версии/секрета/контекста/интервала ETag отличается. Проверяются слабый ETag, private/no-cache, Vary:Cookie и отсутствие разрешения общего кэша.

304 **не считается принятием заявки**. Драйверу нужна отдельная узкая нормализация `not-modified` реального пустого304 исключительно условногоGET;200 требует прежний настоящий HTMLмаркер, последующийPOST — настоящий результат и privateDBпроверку. Нельзя заменить304 на200, подставить свежий context в ветвь304 или скрыто обновить защиту передPOST.

## Контракт начальной подготовки и привязок

`form-preissued-cache-variant({source,variant})` — только собственный изолированный процесс. До изменения фактора выполняется настоящий GET серверной формы, сохраняются его реальный `initial.context`, `etag`, `cacheControl`, `vary`, `observedStatus`. Token не подписывается адаптером и не создаётся из expected. Результат заранее не принимается. `storageBeforeInitialGet` — actual-db счётчики receiptRows/databaseSessionRows до этогоGET.

Затем fixture меняет **один** соответствующий фактор, сохраняя первоначальный ответ. Для нового интервала двигаются только часы изолированного тестового процесса; браузер/Windows/VPS не перенастраиваются. Для контекста/CSRF используется реальный механизм приложения; для missing/invalid убирается либо повреждается только context-cookie, CSRF-cookie не меняется. Для версий используются синтетические публичные данные/шаблон/политика; безопасная подготовка не означает право редактировать production. VISITOR получает фактические cookies текущего варианта, а первоначальный context продолжает обозначать исходную выдачу.

`prepared-form-cache` — закрытое actual-http/actual-db наблюдение перечисленных фактов подготовки: source, clockScope=`isolated-test-process`, issuedByActualFormGet, initial, storageBeforeInitialGet, before/after. В before/after присутствуют непустые фактические `contextFingerprint`, `csrfFingerprint`, `consentVersion`, `protectionInterval`, `contextCookieState`, `publicDataRevision`, `templateRevision`, `formPolicyRevision`. Первые два — стабильные непрозрачные отпечатки текущих действительных значений, не сырые секреты; contextCookieState=`valid`/`missing`/`invalid`. При missing/invalid отпечаток исходного контекста остаётся историческим, а меняется только state. Значения не выводятся из имени варианта или expected. Тест сравнивает все измерения, а не доверяет одному флагу changed=true. Сами декларации provenance ещё не доказывают корректность будущего bridge: его фактические HTTP/DB чтения и атомарную заморозку часов требуется независимо проверить после реализации.

Операции `revalidate-form-etag({source,etag})` и `revalidate-form-ims({source,modifiedSince})` — настоящий GET соответствующей страницы. Первая связывает только If-None-Match с реальным исходным ETag, вторая только If-Modified-Since; нельзя дописывать отсутствующий валидатор или выдавать ожидаемый статус из fixture. Cookies приходят из настоящего actor context. Результат проецирует фактические headers/status/body; для200 дополнительно реальный context из HTML. Для304 context не нужен, используется initial.context. Привязка Vary — разрешённое чтение заголовка ответа. `submit-form-direct`, `form-counters`, `form-storage-counters`, `form-intent-records`, `request-by-id` используют существующие контракты формы. Наблюдения не читаются посетителем и не требуют публичного ID заявки.

## Что этим не доказано

Сборка/синтаксис отделены от выполнения AC: приложение, конкретные bindings/bridge ещё отсутствуют. Поднабор не доказывает HTTPHEAD, все варианты cookies/браузерного кэша, точную границу1800сек, отсутствие исходных секретов во всех возможных ETag/логах, privacy/legal/сканы/нагрузку, отправку ночногоHTML и реальную Метрику. Контекст и пригодность старого cached-представления в ветви304 проверяются явнымPOST, но это не эмуляция браузерного cache storage. Общий AT-402/AC-PRO-002 и TEST-04 не объявляются пройденными.
