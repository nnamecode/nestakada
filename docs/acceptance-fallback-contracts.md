# Логические assertions аварийного режима — TEST-05/06

2026-10-30. `acceptance/fallback-contracts.spec.js` содержит **26 параметризованных тестов** согласованной логической схемы D-307 и PR-03/04. Это только код проверок/действий и описание привязок, не сайт, не реализация контроллера/gate/head, не фейковый движок и не завершение TEST-05/06/07.

Файл использует `openApplicationDriver()` → reset/act/observe/close, отдельное read-only расширение `inspectInfrastructureAdmission()` и отдельный канал `control(action,args)`. Он не объявляет отсутствие инфраструктуры успешным skip. Перед любым fault/reset вызывается inspectInfrastructureAdmission: обычный observe требует уже созданную fixture и для предварительного допуска не подходит. Отсутствие метода/фактического допуска даёт явный INFRASTRUCTURE_NOT_ADMITTED. Сейчас инфраструктурная реализация и конкретное ARC-10 ещё не готовы: автор **не запускал** этот набор на отсутствующем стенде и не менял старый сайт/VPS.

## Обязательный допуск инфраструктуры

`inspectInfrastructureAdmission()` получает actual-http наблюдение из независимого тестового TRUST-контура без runId/reset/создания данных и без обращения к Django: arc10Verified=true, isolatedInfrastructure=true, reviewedEvidenceId и capability fallback-control-v1. Чтение остаётся доступным при остановленной APP/EDGE-зоне. Это **не доказательство по одному boolean**: перед независимой приёмкой адаптера проверяются реальный источник evidence, отдельные зоны/хранилища/отказные границы, актуальное согласование примитивов и отсутствие старого VPS среди целей. Драйвер не должен создавать эти поля сам, считать capability из названия профиля или использовать фиктивные значения при ошибке.

Контроль вызывается только через `.control(action,args)`: отдельный локальный `controlOrigin` вне останавливаемой APP/EDGE-зоны, отдельный controlSession, связанные runId/correlation и настоящие UI/HTTP действия управляющего испытаниями. Через обычный app-origin или роль `.act('TEST-CONTROL',...)` fault не отправляется. Это не новая роль посетителя/сотрудника и не production endpoint. Reset допускается лишь для исходной синтетической fixture. Канал fixtureExchange для act не используется и не расширяется: fault/переключение/POST не заменяются записью expected-состояния через reset/observe.

Нет конкретных URL служебного API/портов/команд оператора в этом файле: их реальная разрешённая привязка отдельно проходит ARC-10 и review bindings. Нет покупок, подключений внешних сервисов, production credentials или реальных ТГ-сообщений. Telegram sink локальный; это доказывает лишь локальный протокол доставки/факта, не настоящее подключение к Telegram.

## Fixture-профили

- `fallback-healthy-validated-baseline`: реальный изолированный Django/основная PostgreSQL и фронт работают; local/external источники имеют отдельные поколения и начальный подтверждённый normal. Часы тестовых процессов управляемы; по reset следующий регулярный слот через300секунд. Прочие фоновые работы/диагностические retries выключены или отдельно классифицированы; запрета реальной бизнес-работе это не добавляет. Ночной допустимый P-LIVE содержит NIGHT-PUBLIC-CANARY, текущий динамический P-LIVE — CURRENT-APP-PUBLIC-CANARY.
- `fallback-current-policy-versus-old-files`: резерв реально выбран/подтверждён, текущий допуск проверен. P-DELETED/P-HIDDEN имеют подтверждённые состояния; лежащие старые файлы содержат REVOKED-OLD-BODY-CANARY. P-NEW-NO-SET — опубликованный новый объект без собственного ночного файла. P-UNKNOWN — действительно неизвестный путь. P-OLD-REDIRECT имеет старый файл, но актуальный прямой301 на последний путь после A→B→C. P-LIVE допустим. Aliases/пути/цели исходят из реальной fixture, не являются рекламными адресами нового сайта.
- `fallback-home-deleted-link-current-denial`: ночной файл P-HOME содержит прежнюю публичную ссылку OLD-PUBLIC-LINK-CANARY, цель P-DELETED подтверждённо удалена. Для файла доступен фактический SHA-256 и для HTTP тела — фактические байты; test не конструирует страницу из expected. Состояние видимого баннера читается из настоящего DOM/принятого UI-контракта, не из флага профиля.
- `fallback-valid-old-local-new-external-denial`: есть старый целый подписанный APP/EDGE снимок с прежним разрешением и содержимым REVOKED-OLD-BODY-CANARY; вне его отката TRUST уже хранит более новый отзыв. APP после rollback не раскрывается до сверки; восстановление здесь — управляемая fault-fixture, **не автоматический restore контроллера**. TRUST не откатывается. Временная недоступность head блокируется настоящим транспортным fault, а не возвращением ожидаемого статуса из adapter.
- `fallback-owner-revocation-with-slow-client`: реальная готовая схема gate/head, допустимый P-REVOKED без дочерних страниц и безопасные синтетические owner credentials. Клиент может удерживать уже допущенный ответ. Delete идёт через настоящую owner-операцию/подтверждение и долговечный протокол; никакого прямого изменения модельного массива страниц.

Суточный тест имеет отдельный120секундный лимит исполнения, контролируемое время вместо ожидания суток и **576 настоящих readiness SELECT через приложение**, не576 прибавлений счётчика. Если среда не обеспечивает наблюдаемую быструю виртуальную шкалу и реальные I/O, этот сценарий должен отказать/остаться непроверенным, а не упроститься до проверки арифметики.

## Контрольные действия

Нормализованные операции отдельного `.control(...)`: stop-isolated-component/start-isolated-component (application/database), block/unblock-readiness-channel (local/external), advance-infrastructure-time, replay-captured-readiness-result, block-independent-head, restart-gate-with-closed-start-barrier, rollback-isolated-app-edge-to-valid-old-snapshot, hold/release-front-switch-confirmation, block-telegram-transport, fail-front-switch-application, hold-response-after-gate-admission/release-admitted-response, stop-isolated-host-zone(APP-EDGE).

Они действуют на реальные контейнеры/процессы/сетевые границы/контролируемое тестовое время **только после допуска**; системные часы Windows/VPS не меняются. Replay повторяет уже захваченный настоящий result с тем же check-ID, не проводит новый readiness и не придумывает failed-result. Блокировки/задержки должны относиться к одному указанному каналу, не одновременно подменять внешнее и локальное наблюдение. `advance-infrastructure-time` запускает настоящий scheduler и его HTTP/SQL; не выставляет failedStreak/confirmedMode.

Тестовый actor OWNER использует настоящие prepare-delete-page/confirm-delete-page с актуальным confirmation и ссылкой OWNER-CURRENT-SECRET на защищённо генерируемый синтетический пароль. Ни actual пароль, ни поля заявок/DSN не попадают в артефакты. Состояния clock/fault должны быть сброшены между профилями, не между проверяемыми шагами одного теста.

## Наблюдения и доказательства

- `fallback-control-state`: реальные local/external completedChecks/checkId/failedStreak/healthyStreak/incidentId, requestedModeGeneration/frontConfirmedGeneration/confirmedMode/controlStatus/switchPending/admissionOpen. Подтверждённый режим не вычисляется из переданной команды или доступности Telegram.
- `reserve-public-response` / `normal-public-response`: фактический GET без автоматического redirect, status/body/bodyBytesBase64/requestedPath/location/cacheControl/robotsDirectives. `external-readiness-http`: настоящий защищённый путь приложения/БД через фронт, status/body/cacheControl и наблюдаемое отсутствие reserve-handler. `external-public-transport`: фактический результат внешней попытки; transportFailed означает реальную ошибку соединения/тайм-аут, не выдуманный HTTP503.
- `readiness-counters`: агрегаты фактических HTTP/SQL и lastSequences по обоим источникам. Instrumentation маркирует purpose readiness; начальные seed/наблюдательные/дополнительные probes учитываются отдельно и не исчезают из общего отчёта. `readiness-check-ledger` содержит последовательность/источник/checkId и scheduledMonotonicSeconds реального scheduler. Между регулярными слотами300секунд; виртуальный тест не меняет пользовательский период.
- `telegram-sink-events`: реальные принятые sink сообщения с source/kind, в частности local-controller mode-entered/mode-left/switch-failed и external-observer readiness-unavailable. Фильтрация не требует одного сообщения на всю систему: внешняя readiness-проблема и факт локального переключения различны. В локальном event-ledger `telegram-delivered` следует после `front-switch-confirmed`; не сравниваются несинхронизированные часы разных площадок.
- `controller-outbox-state`: действительное pendingModeMessages вне основной БД. Сбой отправки не выдаётся за успешную доставку и не меняет факт выбранного режима.
- `independent-head-state` / `restored-local-integrity`: реально отдельное поколение TRUST и проверка всех восстановленных подписанных локальных частей, не просто byte corruption. Допустимый результат после rollback при доступном head —404либо503 до завершения сверки; при недоступномhead строго503. Этот сценарий доказывает запрет старого200, а не полную успешную сверку/доступность.
- `retained-inflight-set` / `finished-admitted-response`: настоящее удержание набора до завершения ранее допущенного клиента, фактические body и последовательности admission/revoke. Новый запрос после owner-успеха получает404; медленный ранее допущенный может законно завершиться.
- `fallback-io-counters`: SQL именно на публичную выдачу, head HTTP и policy-registry writes. Другой access-log/фоновый трафик не приравнивается к этим счётчикам. Тест10посещений не утверждает полный ресурсный SLO.

Ожидания через expect.poll читают фактический прогресс, не проталкивают expected в приложение. Тайм-аут — реальный отказ теста. Не выдавать незапущенную binding/marker capability/сборку за результат этих операций.

После TEST-R011 проверяется структура каждого используемого наблюдения до сравнения. ID проверок/инцидентов/ответов/путей — непустые строки; поколения — явные неотрицательные целые либо непустые непрозрачные строки. Перед сравнением front/requested-generation и head до/после rollback оба значения обязательны: два undefined не проходят. completedChecks/streak/HTTP/SQL/последовательности/очередь/I/O-counters — целые неотрицательные safe-integer. lastCheckId до первого завершённого probe явно null либо непустой ID, после него только непустой ID; отсутствующее поле не равняется «проверок ещё не было». lastSequences содержит оба источника.

Ledger должен быть массивом реальных записей с типизированным source/checkId/sequence/scheduledMonotonicSeconds; controller-ledger требует kind/sequence и messageKind для доставки. Последовательности в выбранном источнике идут вперёд, время планового слота конечно/неотрицательно; шаг300секунд остаётся прежним oracle. Telegram-события имеют непустые source/kind **до фильтрации**, чтобы записи с потерянной структурой не превращались в ложное «уведомлений нет». Подтверждённый режим присутствует явно, в недоказанном состоянии допускается явный null, но не отсутствующий ключ. Эти проверки верифицируют тестовый контракт данных, не добавляют пользователю новые сроки или бизнес-правила.

## Честный остаток

Не покрыты все fault-границы prepare/commit/finalize, возврат/переиспользование пути, полная форма безJS/POST/HEAD/304 и отсутствие токенов, ночная сборка/нехватка места/удержание всех медиа, реальные хост/TLS/провайдеры/ключи/сеть, полный restore БД/сессий и правовые данные. AT-306 в этом файле затронут только частью доставки/независимости факта; тысяча critical, потеря ACK, bounded retries и несколько кодов инцидента ещё требуют отдельных проверок. AT-408 не закрывается одним полным остановом зоны: отдельный зависший контроллер/старый heartbeat ещё не проверены.

ARC-10, допуск настоящего инфраструктурного адаптера, наблюдаемые I/O и независимое ревью обязательны до исполнения/завершения TEST-05/06/07. Старый сайт/VPS не являются тестовой площадкой. В этой работе созданы только два тестовых файла; никакие сервисы/правила сайта не реализованы и ничего не запускалось.
