# DEV-07 — предложение транспорта больших допустимых прайсов

2026-10-31. Подготовка и локальные испытания приняты по DEV07-Q002/D-331. Применение handlers требует фактических проверок и независимого ревью. D-330 отдельно разрешил библиотеки; CSP не ослабляется. Поля и бизнес-лимиты уже приняты; этот документ не увеличивает число строк/ячеек или длину текста.

## Фактическое основание

Изолированный запуск принятого Python-образа и настоящего SnapshotV1 без БД/сети/секретов построил допустимые 500 строк,32 колонки,10000 текстовых ячеек по1000 Unicode-символов, подписи в их пределах, две текстовые области по200000 Unicode-символов и допустимые H1/title/description. Схема приняла содержимое; канонический JSON UTF-8 занял **43 475 643 байта** (около41.5МиБ), peak RSS184216КиБ. Действующий общий лимит11МиБ=11534336байт его не вмещает. Протокол work/dev07-20261031/transport-boundary.txt; данные синтетические, в медиатеку/БД не записывались.

Это один измеренный допустимый пример, не доказательство максимального возможного размера любого wire encoding/структуры и не измерение будущего полного handler. В частности ensure_ascii JSON может раздуть те же символы; UI должен отправлять канонический UTF-8 без такого раздувания.

## Рекомендуемая ограниченная поправка

- Разрешить до **64 МиБ сырого JSON UTF-8** ровно трём закрытым POST-путям: `/manage/pages/<uuid>/edit/check/`, `/manage/pages/<uuid>/edit/save/`, `/manage/pages/<uuid>/edit/draft/`. UUID — существующая Page, хвосты буквальные; никаких «связанных» путей автоматически. Не менять весь /manage или публичную выдачу.
- Для этих конкретных маршрутов Nginx передаёт тело потоком без предварительной дисковой буферизации (proxy_request_buffering off, HTTP/1.1 к приложению). Цель — позволить приложению отклонить неавторизованный/неправильный CSRF запрос по заголовкам до чтения большого тела, а не складывать его на диск заранее.
- Приложение проверяет текущую сессию, Page-доступ, тип запроса и CSRF до bounded-чтения JSON. Доверяет только отдельному собственному reader с абсолютным byte-budget и отказом413 при превышении; никакого доверия одному заявленному Content-Length. Общий Django11МиБ для прежних форм не повышается. Отсутствующая/неподходящая длина или неподдержанный способ передачи должны давать явный безопасный отказ, не ожидание бесконечного потока.
- Существующие пределы входа/загрузки одного фото, публичные маршруты и остальные формы остаются своими. Контейнеры приложения/БД/worker, их память/CPU, порты, CSP и Windows не изменяются этой поправкой. Новая служба/программа не нужна.
- После чтения действуют прежние строгие field/DOM/price лимиты, текущие права и DEV-05 атомарность. Большой wire budget не разрешает произвольный Snapshot writer или большие реальные значения полей.

Цена: один допущенный большой запрос занимает до64МиБ входных байтов в памяти/сети и требует дополнительной памяти/CPU на JSON и дерево. Существующие768МиБ/1CPU приложения не увеличиваются; достаточность полного pipeline ещё должна быть проверена. Без price-grant сотрудник получает производный малый budget, вмещающий только его допустимые поля; наличие доступа к Page не даёт бюджет большого прайса автоматически. Конкретный ресурсный guard до чтения/parse описан в согласованном для испытаний dev07-local-processing-profile.md.

Разрешить подготовку и локальные проверки этой конкретной поправки; при непрохождении проверок вернуть прежнюю конфигурацию без подключения и сохранить диагностику. VPS/старый сайт/production не затрагивать.

## Проверки до допуска

1. Реальный принятый большой прайс и обе области проходят HTTP с теми же допустимыми значениями, без усечения; actual RSS/время укладываются в существующий ресурсный профиль. Отдельно подтвердить верхнюю оценку канонического request по всем разрешённым полям.
2. Budget+1 и неправильные field/node/cell bounds отклоняются без версии/current/receipt успеха; parser/JSON ошибки не дают частичного результата.
3. Настоящий visitor, чужой employee и неверный CSRF получают отказ до полного тела: socket-проверка с большим Content-Length и ещё не переданным телом, не только заранее отправленный Playwright buffer. Проверить framing/chunked/отсутствующую длину, обрыв/тайм-аут и отсутствие временных request-файлов.
4. Положительные owner/assigned price-grant и прежние маленькие формы/login/media проходят; не расширены другие location/доступ/лимиты.
5. Guard/FOUNDATION и независимое ревью связывают фактическую Nginx-конфигурацию и новый reader с точным source snapshot. Пока этих свидетельств нет, размер64МиБ не называется доказанно безопасным/готовым.

Альтернатива — оставить11МиБ и отдельно проектировать многошаговую атомарную передачу прайса, с дополнительным staging/квотами/протоколом. Молчаливое уменьшение уже принятых10000ячеек/1000символов не предлагается.
