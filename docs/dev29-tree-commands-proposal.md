# DEV-29: переименование, перемещение и порядок — предложение

2026-11-03. Предложение конкретного локального профиля, **не согласование и не реализация**. Поручение владельца «Продолжай» после DEV29-READ-01. Основания: D-239–247/D-294, REQ-003–007/017/022, PR-08, существующие content.Page/Route, accounts и DEV-05 receipt. DEV-29 около5%, этап8 около31%.

## Что получит владелец

Три отдельные команды из дерева: изменить название; выбрать другой родительский раздел; поставить страницу перед выбранной соседней либо в конец. Перед применением показаны текущие название/раздел/публичный порядок. Родитель существует, цикл/self-parent невозможны, сосед относится к выбранному разделу. Переименование не переставляет страницу. При переносе можно явно выбрать место, иначе конец списка назначения. Сотруднику команды недоступны.

Это управление структурой: URL/alias/redirect, собственная публикация, H1/title/тексты/прайсы/текущая редакция содержимого/Stable/Asset/настроенная главная не меняются. Не выдавать это за создание страницы, публикацию, смену URL или удаление. Сохранение содержимого через редактор по-прежнему создаёт автоматическую PageRevision; команда структуры не публикует черновик и не подставляет историческое содержимое.

## Предлагаемая фиксация

1. GET формы — только чтение. Сервер создаёт подписанное основание с actor/security generation, action, неизменяемым PageID и SHA фактического состояния дерева. UUID операции создаётся для формы без записи receipt на GET. Основание находится в hidden POST, не URL; CSRF остаётся штатным.
2. Основание включает упорядоченные фактические Page(id/name/kind/parent/position/publication), Route(id/target/kind/page/legacy), IDs текущих PageContentState revisions и точное число уже сохранённых receipts трёх tree-команд. Последний счётчик вычисляется из неизменяемой истории, не отдельной таблицы: переименование A→B→A не делает старую форму снова актуальной. Только digest попадает в токен; содержимое/медиа/секреты туда не входят. Для небольшой первой версии используется консервативное общее основание: изменение даже другой страницы может потребовать обновить форму, вместо попытки объединить изменения автоматически. На GET короткий общий contentlock обеспечивает согласованное основание; внешней сети нет.
3. POST — одна короткая transaction.atomic: content advisory lock7342810401 → auth lock7342810301 → актуальные owner/session/security generation → затронутые Page в устойчивом UUID-порядке. Проверяются действующая сессия, nesadmin/owner и та же роль повторно под lock. Нет долгих сетевых/файловых операций под блокировкой.
4. Подпись, закрытая форма токена и привязки actor/generation/action/PageID проверяются всегда, в том числе при повторе; CSRF не обходится ради receipt. Затем до проверки свежести снимка ищется точная уже существующая квитанция этого UUID: action/actor/generation/PageID/канонический fingerprint всех смысловых входов совпадают. Успешный повтор возвращает прежний результат без записи и повторной перестановки, даже если исходное основание уже устарело вследствие первой команды. Текущие права/сессия проверяются и при повторе. Другой ввод/другая команда/actor/объект с тем же UUID отклоняются. Старый receipt не восстанавливает более позднее состояние дерева.
5. Для нового UUID сверяется актуальный SHA основания, затем цикл/родитель/сосед/название. Любой конфликт — полный отказ без Page/receipt/аудита успеха. Ввод остаётся в безопасно экранированной открытой форме; не хранится в localStorage.
6. Используются уже проверенные Page.save и отложенная уникальность parent/position. При переносе/перестановке фактический порядок двух затронутых sibling-списков нормализуется в0..N−1, интерфейс показываетposition+1. Не пересчитываются URL/публикация/дети. После применения квитанция и безопасное событие pages_links записываются в той же транзакции; ошибка любой части откатывает всё.

## Где хранится квитанция

Рекомендую **существующие page_versions.OperationReceipt и IdentityReservation**, с отдельными action tree_rename/tree_move/tree_reorder и result_code. Никаких новых моделей/полей/миграций, общего счётчика дерева или копий HTML. ResultID/sourceRevisionID/targetRevisionID остаютсяnull для структурной команды; конкретный PageID уже есть в receipt. Fingerprint включает action/actor/generation/PageID/старыйSHA/новые параметры; пароль/CSRF/session key/полный подписанный токен не сохраняются.

Новый небольшой content-command модуль явно работает с этим существующим форматом. Он **не вызывает вслепую engine.finish/result**: эти функции предполагают PageRevision и аудит VERSION, что неверно для структуры. Используется прежний immutable model guard/глобальная UUID-резервация, собственный безопасный ответ «применено/уже применено» и категория pages_links. Изменение назначения этих существующих квитанций — конкретная деталь архитектуры для отдельного DEV29-Q001 по AGENTS.md, а не уже полученное разрешение.

Минимальные receipts/UUID сохраняются без автоматического TTL/очистки, как в DEV-05. Новую политику удаления/произвольный count-limit не вводим. Измеряем фактическую прибавку таблиц/index/TOAST/аудита и поведение при ошибке записи; не объявляем хранилище бесконечным и не повышаем лимиты автоматически. Новых программ/контейнеров/томов/сетей/памяти/CPU нет; прежний APP PostgreSQL/локальный wrapper. Существующие версии/Stable/UUID/receipts и TRUST не переписываются.

Альтернатива — отдельная таблица квитанций структуры. Она отделит модули, но потребует миграции, отдельного учёта/резерва UUID и восстановления при уже имеющемся подходящем формате. Ещё вариант — только проверять актуальность без receipt; он не даёт надёжного точного повтора после потери ответа, поэтому не рекомендую.
