# REF-7: инвентаризация мёртвого кода перед REF-Q004

Дата: 2026-11-06
Статус: read-only инвентаризация завершена; удаление не разрешено, `REF-Q004` закрыт.

## Цель и граница

Документ отделяет действительно отключённую тяжёлую архитектуру от моделей, которые выглядят legacy, но всё ещё нужны runtime или совместимости. Инвентаризация не меняет код, схему или данные и не разрешает удаление.

## R7-I001 — отдельный TRUST-контур

Кандидат на первый файловый инкремент после открытия `REF-Q004`:

- `trust/**`: 31 tracked-файл, 211182 байта;
- `environment/trust/**`: 4 tracked-файла, 10164 байта;
- именованные TRUST tools/tests и `scripts/local-trust.ps1`: 53 tracked-файла, 892256 байт;
- `tools/dev29/**`: 3 tracked-файла, 475139 байт, включая source-only checkpoint ZIP.

Итого: 91 tracked-файл, 1588741 байт. Группы не входят в основной Django runtime/foundation compose. Поиск вне самих TRUST/tools, документации и архивного checkpoint не нашёл ссылок на `trust_service`, `trust-db`, `TRUST_DB*`, `TRUST_WRITE*`, `TRUST_RUNTIME*` или `local-trust`. Основной runtime использует только обычные Django/PostgreSQL механизмы и отдельный foundation compose.

Почему удаление не ухудшает безопасность: это прежний отдельный экспериментальный контур, а не фильтрация запросов, ORM, CSRF, сессии, права, throttling, аудит, backup или restore-check текущего приложения. История останется в Git. Перед удалением всё равно нужны статический поиск, foundation/Django checks, основной regression-набор и независимое ревью.

## R7-I002 — `AuthSession`

После REF-06A основной runtime не импортирует и не создаёт `AuthSession`: активна стандартная server-side Django session с generation/issued/last-seen. Оставшиеся ссылки находятся в модели, исторической миграции и тестах, проверяющих отсутствие двойной записи.

Это кандидат на отдельный schema-инкремент, не на механическое удаление вместе с TRUST:

1. проверить точное число строк непосредственно перед миграцией;
2. сохранить проверенный локальный backup и пройти restore-check;
3. создать новую Django migration `DeleteModel`, не менять историческую миграцию;
4. заменить проверки старой таблицы проверками единственной Django session;
5. проверить forward migration, rollback-план, revoke/password/active/PageGrant и полный затронутый regression-набор.

Физическое удаление таблицы является удалением данных и требует явного разрешения владельца в `REF-Q004`.

## R7-I003 — не удалять сейчас

Следующие элементы пока не являются мёртвыми:

- `AuthResourceState` нужен действующему `LoginThrottle.capacity_state`; удалить можно лишь неиспользуемое значение `sessions`, но не модель;
- `OperationReceipt` и `IdentityReservation` читаются действующими page/content/editor путями для legacy replay и collision guards;
- `RestoreStage` и `VersionBasePin` участвуют в draft/restore, защите ревизий и confirmed page delete;
- `shared_content` продолжает использовать revisions/drafts/restore stages/base pins/identity reservations и требует отдельной функциональной замены до удаления.

Удаление этих компонентов сейчас нарушило бы стабильность или совместимость. Их можно рассматривать только после отдельного переключения runtime, приёмочных сценариев и подтверждения данных.

## Предлагаемая нарезка после решения владельца

- `REF-07A`: удалить только R7-I001, без миграций и удаления БД;
- `REF-07B`: отдельно удалить модель/таблицу `AuthSession` по R7-I002;
- `REF-07C`: не планировать, пока R7-I003 имеет runtime-ссылки.

Для каждого инкремента сначала записывается приёмочный план, затем изменение, PostgreSQL checks/regressions и независимое ревью. Production, VPS, старый сайт, Git history и текущие backup generations не затрагиваются.
