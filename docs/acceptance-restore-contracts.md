# Полное восстановление: частичные AT-037/044

2026-10-30. Этап7 по D-301–D-303/D-305/D-308 и прямому поручению владельца. Основания: admin-architecture-draft.md §12, REQ-037/044, AC-037/044, D-107/D-275, внешний tombstone/допуск. Подготовлены только тесты, не restore-команда/Django/SQL-миграции/инфраструктура. Старый сайт/VPS/реальные копии не используются.

`acceptance/restore-contracts.spec.js`:10экземпляров. Три восстановления через действующую админку с причинами non-security/security-suspected/unknown; внешний путь при недоступном текущем хранилище с отдельным усиленным подтверждением потерь; три отказа обязательных стадий; две чужие роли и неверный повторный пароль с положительным контролем владельца. Это10написанных сценариев, не10исполненных restore и не закрытие полного AC.

## Проверяемый результат

Выбор/предупреждение сами ничего не заменяют. Запуск выполняет только настоящий подтверждённый запрос владельца с актуальной сессией/повторным паролем. Отказ другой роли/неверного пароля не меняет рабочие данные и число начатых исполнений. Для последующего положительного контроля владелец получает свежее подтверждение: тест не требует сохранять nonce после неуспешного входа/подтверждения.

Исполнитель закрывает новые записи до замены. При читаемом текущем хранилище до применения target БД проверены зашифрованная safety-копия и отдельный экспорт новых заявок/согласий после cutoff. Они реконструируются независимо и сравниваются с oracle, снятым **до запуска**: защищённые Page/Version/Request/consent/user/rights проекции и фактические bytes/SHA всех текущих media; отдельно точные post-cutoff Request и связанные consent записи, не только наличие одного ID. Тот же oracle проверяет доступность/содержимое safety после post-replacement отказа. Служебные audit/job/probe timestamps исключены из business projection; whole-DB equality не требуется. Fixture не допускает конкурентных входящих бизнес-записей между oracle и write fence, такие гонки остаются отдельно. При доказанной потере текущего хранилища первая команда останавливается до замены и требует отдельное усиленное подтверждение с причиной/диапазоном потерь; нельзя передать обычное bypassSafety=true.

После восстановления страницы/версии/сохраняемые заявки сравниваются с заранее независимо реконструированной выбранной точкой. Удалённая после cutoff заявка не возвращается: внешний актуальный tombstone применяется, а post-cutoff заявка не добавляется автоматически из safety-экспорта. Байты каждой небольшой синтетической media проверяются по independently inspected target SHA/size, тест сам пересчитывает фактические bytes. 256КиБ на файл — предел минимальной fixture/тестового транспорта, не лимит продукта.

Все старые сессии проверяются реальными закрытыми запросами: как существовавшие перед restore, так и содержащиеся в старой точке. Сотрудники выключены до сверки владельцем. Фактический владелец активен и имеет owner-право; новый вход проверяет реальную идентичность и приватный canary, прежний пароль из target не работает (в этой fixture его меняли после cutoff). В non-security допустим безопасный перенос актуальной идентичности владельца либо break-glass; необязательный перенос hash не превращается в обязанность. При unknown/security и недоступном актуальном состоянии требуется интерактивный break-glass, до административного доступа ротируются собственные внешние test-секреты. Новое owner ID после break-glass не запрещается: сверяется фактическая конечная запись nesadmin.

Ledger связывает реальные завершённые действия с operationId: write fence, проверка point/совместимости и safety/export либо отдельное enhanced-loss-confirmation **до применения и рабочей БД, и рабочих media**. Проверенные БД/media/tombstones/сессии/сотрудники/smoke предшествуют и normal open, и normal admin open; reset/rotation — admin open по применимому пути. Это обычный доступ к данным/изменениям, не запрет read-only внешнего статуса процедуры. Безопасный staging кандидата может начаться раньше, но не называется target-media-applied. Не задаётся порядок между независимыми стадиями DB/media или способ применения tombstones к offline dump. Длительность читается из монотонного измерителя процедуры, без срока реакции владельца.

## Изоляция, внешний путь и фиксированные controls

До reset нужен реальный ARC-10/isolated preflight, перед каждой командой — свежий допуск `restore-control-v1` для собственного run/instance/admission. Backup/fallback или роль приложения этот допуск не заменяют. Команды: set/clear-isolated-restore-fault; prepare/confirm-isolated-external-restore; confirm-isolated-restore-loss; complete-isolated-identity-recovery; prepare-isolated-restore-write-probe. Их нормализованные названия — тестовый интерфейс контроллера, не выбранные endpoints продукта/произвольный shell.

Fault из safety-write-failure/external-deletions-unavailable/smoke-failure действует только на свой стенд. Потеря safety при читаемых данных блокирует замену. Недоступность актуальных tombstones и ошибка smoke не дают полного успеха/открытия нормального доступа; если замена уже начата, проверяется закрытие normal/admin и фактический отказ новой записи. Вариант отказа preflight до замены не обязан останавливать продолжающую работать старую БД.

Внешние prepare/confirm controls запускают **ту же документированную настоящую ограниченную процедуру** через отдельного локального синтетического владельца. Требуются реальные подтверждение выбранной точки, проверка полномочий/секрета и одноразовая подписанная команда вне заменяемой БД. operatorRef/confirmationRef — ссылки на собственную секретную fixture/выданное процедурой подтверждение, не строки паролей и не достаточная авторизация сами по себе. complete-isolated-identity-recovery выполняет реальный интерактивный management-путь, подаёт скрытый тестовый пароль через stdin и обрабатывает требуемую ротацию собственных test-secret refs; не передаёт пароль argv/env/логу. Его наличие не разрешает обход owner-confirmation/native проверки. Никакие CLI/ключи/controller здесь ещё не написаны; конкретные binding/procedure/механизмы до запуска отдельно выбираются и независимо проверяются.

## Исходные данные и фактические чтения

`restore-old-point-new-state` создаёт минимальную собственную точку с согласованными DB/media, затем отличающееся текущее состояние. Target содержит R-removed/R-kept и старые owner/employee sessions; current содержит новую post-cutoff заявку/согласие, изменённую страницу и другой текущий пароль владельца. Внешний tombstone R-removed находится вне rollback-domain. Вариант currentReadable=false моделирует физическую недоступность только собственной рабочей зоны; target/external procedure остаются доступны. Все payload синтетические, без данных людей.

- restore-fixture-identifiers: фактические стабильные IDs, target point и текущее внешнее поколение удаления. Четыре session actors и два новых login actors имеют отдельные настоящие контексты. До создания target fixture должна доказать рабочие старые sessions реальными запросами/сохранённым протоколом, а до restore — рабочие current sessions. Нельзя просто выдать изначально неверные cookie и засчитать их последующий отказ.
- restore-target-inspection: независимая полная реконструкция фактических архивных bytes, point/dump SHA/pages/versions/requests/media. Target-данные берутся **до запуска restore** отдельным read-only инструментом, а не из будущего результата ресторера. source marker сам не доказывает чтение, его реализация отдельно ревьюится. Ключи/алгоритмы/версии ещё не выбраны; реальный Яндекс Диск не нужен, external zone только локальная изолированная.
- restore-live-read-only-state/restored-working-state: реальные SQL бизнес-проекции, не whole-DB equality с меняющимся аудитом. Live oracle включает непустые pages/versions/requests/consents/users/rights; Request имеет реальную createdAt, consent — requestId; raw password/hash/session secrets не выводятся. restore-current-media-inspection читает фактические текущие media bytes и связывается с тем же неизменившимся live oracle. После restore сверяются рабочие Page/Version/Request, employees/owner и фактическая media inventory с bytesBase64/size/SHA. Сортировка массивов по стабильным ID нормализуется одинаково, содержание не достраивается из expected. Полнота произвольных таблиц/связей/metadata за пределами этой fixture отдельно.
- restore-external-deletions: реальный актуальный журнал/поколение вне заменяемой БД, не старый локальный файл. Недоступность/старое подписанное поколение не должны давать старый разрешающий результат.
- restore-external-operation/restore-execution-ledger: actual-status-outside-replaced-db, действительное состояние исполнения/стадий/инициатор/point/elapsedMonotonicMs. phase — нормализация фактического внешнего статуса, не новые бизнес-статусы сайта. Ledger event означает совершённую операцию, не заранее составленный план. reportedComplete не строится из test-expected.
- restore-safety-inspection: независимая фактическая реконструкция нового safety point (не target point): businessState, mediaFiles с bytes, отдельные exportRequests/exportConsents. Они сравниваются с pre-restore oracle и точным набором createdAt>target.cutoffAt/связанных согласий. restored source не используется как oracle safety. Свидетельство включает manifest/bytes/доступность, не один файл имени safety или encrypted/verified flags. При ошибке после замены читается тот же safety и сверяется с тем же исходным oracle.
- restore-access-evidence: реальные состояние gate и число normal write commits собственного maintenance-интервала. До начала процедуры другой актёр OWNER-PRE-RESTORE-PROBE выполняет настоящий положительный штатный save с допустимым текстом/основанием; фактический текст меняется. После начала замены старые sessions уже недействительны и не подходят для проверки maintenance. Отдельный никогда ранее не открывавшийся OWNER-RESTORE-PROBE получает **новую** framework session/CSRF через provisionRestoreWriteProbe(operationId); он не переиспользует прежний cookie. restore-probe-object даёт актуальное основание/текст реального объекта, который отличается от допустимого probe payload. После POST проверяются и отсутствие изменения бизнес-проекции, и отсутствие прироста реального write counter, и закрытый gate. Отказ по старой сессии/CSRF не считается доказательством write fence.
- read-restore-private-direct/login-after-restore/read-restored-public-direct: реальные UI/HTTP той же изолированной системы. Публичная canary не подменяет full SQL/media inspection, старые actor contexts не заменяются новыми между проверками invalidation. Парольные refs берутся из секретной fixture; сырой hash/ключ/cookie не публикуется в Git/отчётах.

provisionRestoreWriteProbe — только тестовая передача новой session в actor context, не API продукта. Под свежим restore permit контроллер создаёт session/CSRF **framework-путём** для уже существующего активного owner; менять users/rights/business data нельзя. Перед/после передачи бизнес-проекция сравнивается. Cookie/credentials читаются по собственным operation/grant/run из защищённого fixture channel, не возвращаются тесту. validateRestoreProbeSession проверяет phase/sequence после invalidation, новый cookie не из старых fixture secrets, локальный origin, отсутствие localStorage и привязку к отдельному actor. Actor context до этого не создавался; на первом последующем act он реально инициализируется полученным storageState/credentials. Re-init использованного actor запрещён, ошибка handoff отравляет fixture. restore-write-probe-eligibility — фактическая независимая проверка framework auth/CSRF/object: передаваемые в actual actor.context cookies действительно пригодны для **этого** POST с его path/expiry, новое основание и CSRF берутся из настоящего контекста. Одной валидной session row в БД/flags недостаточно. Такого framework/CSRF/bridge подключения ещё нет, его клиентская передача/доступность и provenance обязаны пройти отдельное независимое ревью до запуска; текущие декларации не закрывают readiness. Нельзя просто вставить expected actorId или сделать старый session валидным. Бизнес-правила restore не реализуются в подготовщике.

close/reset останавливают и очищают только собственные тестовые исполнения/зоны с проверкой run scope; pending worker не может продолжить менять следующую fixture. Это обязательное свойство будущего подключения, ещё не доказанная реализация.
