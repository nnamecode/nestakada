## Предлагаемое поведение

1. Только `nesadmin` выбирает **одну конкретную старую версию** шапки или подвала. Нет кнопки «удалить всё», удаления по возрасту или автоматической очистки. Выбор нескольких версий можно добавить отдельно позднее.
2. Предпросмотр показывает блок, номер/дату/автора версии, используемые файлы, причины запрета и размер её HTML. Размер HTML не выдаётся за гарантированное освобождение диска PostgreSQL.
3. Для удаления нужны отдельное актуальное подтверждение выбранной версии и действующий пароль владельца. Перед действием сервер повторно проверяет сессию, права, состав и все зависимости. Изменившийся состав требует нового просмотра/подтверждения. Просмотр и GET ничего не удаляют.
4. Текущая версия, основа черновика, source/base любого существующего восстановления и любая версия с pin защищены. Это включает завершённые, отменённые и утратившие актуальность стадии: их metadata здесь не удаляются. Preview показывает конкретную причину запрета. Не удаляются состояния с неизвестной защитой/происхождением; первоначальная операция ограничена собственными проверенными file-mode версиями. Legacy inline и неподдерживаемая схема остаются доступными для просмотра, но исключаются из очистки. Новых Stable-команд нет.
5. При успешном удалении выбранная версия исчезает из истории, её конкретный HTML-файл удаляется только после проверки отсутствия других ссылок. Общие фотографии не удаляются: снимается лишь зависимость удалённой версии; действующая отдельная очистка медиатеки сохраняет свои правила.
6. Сохранённые UUID/квитанции остаются: повтор старого сохранения не создаёт удалённую версию заново. Историческая ссылка на удалённый результат показывает его отсутствие, а не чужую новую версию.
7. Если сведения версии удалены, но файл удалить не удалось, интерфейс прямо сообщает: «Версия удалена из истории. Очистка файла не завершена». Доступно ручное продолжение **той же** операции. Отказ до изменения истории сообщает об отказе; неопределённый ответ не выдаётся за полный успех.

## Неопределённые сохранения

Закрытая диагностика владельца показывает известный результат операции, наличие незавершённой брони и состояние квоты. Для подтверждённого commit/abort можно вручную вызвать существующую проверяемую reconciliation; новое содержимое при этом не публикуется.

Если квитанции нет, журнал повреждён, данные противоречат друг другу или accounting fault сохраняется, бронь остаётся. Кнопок «считать отменённым», «обнулить долг» и «снять блокировку всё равно» не предлагается. Недоступный результат/размер показывается как неизвестный, а не как отсутствие операции или нулевой расход. Диагностика должна объяснять необходимость технической проверки; сама по себе она не является полным восстановлением после любого сбоя. Изменение этого правила потребует отдельного проверенного протокола.

## Техническая схема к согласованию

Новые программы, контейнеры, тома и повышение ресурсов не требуются. Добавляется собственная таблица `SharedCleanupJob` в PostgreSQL: постоянный ID операции, block/target UUID, actor/generation, fingerprint подтверждённого намерения, неизменяемый проверенный descriptor выбранного HTML-файла, фаза и удержанный запас. Полный HTML, пароль, cookie и CSRF там не сохраняются. Одна незавершённая очистка на общий домен; таблица/индексы/TOAST и временный рост входят в прежние256МиБ.

Job служит долговечным намерением и результатом очистки. Он фиксируется **до** удаления metadata/AssetUsage. Короткая следующая SQL-транзакция повторяет защиты, удаляет только выбранную строку/её media-зависимости, атомарно фиксирует фазу и audit; permanent identities и прежние receipts сохраняются. Descriptor не исчезает вместе с удаляемой строкой. Физический unlink выполняется вне SQL по закрытому server-assigned ключу с проверками inode/owner/nlink/SHA/всех оставшихся ссылок и fsync. После сбоя тот же job позволяет продолжить, не удаляя следующую версию. Удалённый blob key навсегда зарезервирован job: последующие writer-команды проверяют его и не присваивают новому файлу, даже при совпадении случайного UUID. Задания не удаляются автоматически; их накопленный размер виден в квоте.

Используется существующая session lease перед content lock. Новые сохранения не обходят незавершённый job. Не переиспользуется старый11-полевой журнал записи под видом разрешённого `apply`; его прежние книги остаются совместимыми. Неизвестное состояние job/БД/файла закрывает дальнейшее изменение.

После unlink, но до фиксации итоговой фазы job процесс может завершиться. Повтор допускает уже отсутствующий **именно ожидаемый** файл только при доказанной фазе удаления metadata, свежей проверке отсутствия ссылок, проверенных nofollow родителях и подтверждённом fsync каталога; несовпадение descriptor/фазы не превращается в успех. После нового входа или смены пароля продолжение требует свежей сессии nesadmin, нового актуального подтверждения и пароля. Сохранённая generation job не даёт доступа сама по себе; target и descriptor не подменяются.

Для обслуживания при заполнении истории нужен заранее проверенный запас **внутри** прежних256МиБ. Размер и достаточность не объявляются до измерений: подготовить candidate profile, ограничить приём новых версий так, чтобы запас оставался, проверить отказ обычного Save вместе с успешной допустимой очисткой. Остатки после rollback, persistent jobs, PG bloat и задержанный unlink продолжают учитываться. Если этот gate не пройден, очистка остаётся выключенной; бюджет и ресурсы автоматически не повышаются. DELETE не обещает уменьшения файлов PG, VACUUM FULL/пересборка индексов/сброс retained debt не входят в предложение.

Новая additive миграция и пересмотр точного schema signature допускаются только после ответа владельца;0001–0004 не переписываются. После реализации обязательны новая калибровка, регрессии shared, HTTP/браузерные проверки и независимое ревью до локального включения. Production остаётся отдельно.

## Вопрос владельцу

**DEV07-LC-Q001:** разрешить реализовать и локально проверить описанную ручную очистку по одной выбранной старой версии шапки/подвала с закрытым журналом задания в PostgreSQL и запасом обслуживания внутри256МиБ? Рекомендация — подготовить и проверить; включить только после успешных испытаний и независимого ревью. Альтернатива — оставить историю без удаления и продолжить публичные общие блоки. Ответ не является командой удалить существующие данные или менять VPS.
