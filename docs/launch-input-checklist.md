Статус D-1009, 2026-11-14. Этот список преобразует восемь внешних входов D-1008 в короткие owner-facing gates. Он не разрешает deployment, не включает формы/аналитику и не требует выбирать необязательные сервисы заранее.

Базовый профиль первого публичного запуска: заявки и сбор ПД выключены, SMTP/Telegram/аналитика/внешние виджеты не подключены, DEV-26/27 остаются отложенными. Поэтому условные пункты не блокируют этот профиль сами по себе.

### LAUNCH-IN-002 — уже известное и минимальная сверка

Канонический подробный источник — `docs/server-environment-evidence.md`. По сведениям владельца и скриншотам от 2026-10-30 известны: существующий VPS/KVM, FirstVDS, тариф «Отрыв», Москва/IXcellerate, предварительная конфигурация 4 vCPU / 8 ГБ RAM / SSD 80 ГБ и показанный в панели шаблон CentOS 7. На VPS находился старый сайт; владелец планировал самостоятельно освободить каталог перед будущим переносом.

Это не доказывает текущую ОС, оплаченные/свободные ресурсы или готовность production. CentOS 7 не является поддерживаемой основой для нового развёртывания; контейнеры не исправляют неподдерживаемое ядро хоста. Запись не разрешает переустановку, удаление старого сайта или изменение VPS.

Для закрытия read-only части IN-002 достаточно позже сверить в панели, без SSH и без передачи секретов:

1. дату наблюдения, фактические название/версию поддерживаемой ОС и архитектуру;
2. текущие vCPU/RAM/общий и свободный диск;
3. остался ли старый сайт/БД и освобождён ли будущий каталог самим владельцем;
4. доступны ли штатные snapshot/recovery и firewall controls — только наличие, без ключей и правил;
5. возможна ли согласованная установка поддерживаемой ОС без потери нужных данных.

Безопасный локальный путь заметки/скриншотов: `work/launch-inputs/firstvds/`. Он исключён из Git. Не помещать туда в отслеживаемом виде IP, логины, пароли, SSH/private keys, cookies, токены, полные firewall rules или клиентские данные. Точные сетевые значения при необходимости передаются отдельно только на этапе разрешённого deployment.

### LAUNCH-IN-005 — минимальный выбор внешнего backup

Канонические границы — `docs/backup-proposal.md`, `docs/ref6-local-backup-results.md` и `docs/acceptance-backup-contracts.md`. Локально уже проверены два поколения PostgreSQL+media и изолированное восстановление. Они не защищают от потери VPS/диска. Названный ранее Яндекс Диск остаётся кандидатом, а не утверждённым провайдером.

Рекомендуемый no-bloat вариант — готовое независимое object/file storage с клиентским шифрованием, а не собственный второй backup-сервер. До подключения достаточно выбрать провайдера по семи фактам:

1. юридическое лицо провайдера и страна фактического хранения;
2. отдельная принадлежащая владельцу учётная запись/каталог для проекта;
3. достаточная квота и понятная стоимость для семи ежедневных внешних точек;
4. возможность загрузить ciphertext и затем проверить размер/checksum без расшифровки у провайдера;
5. способ хранить ключ отдельно от VPS, Git, application DB и backup storage;
6. возможность удалить/выгрузить данные и восстановить полный набор без зависимости от работающего Django;
7. успешное полное учебное восстановление до production launch.

Не требуется выбирать собственную backup-платформу, UI в админке, инкрементальный движок или второй сервер до проверки объёма. Точная программа шифрования/передачи выбирается отдельным техническим шагом после провайдера и объяснения изменений владельцу.

Безопасный локальный путь для сравнительной заметки: `work/launch-inputs/backup-provider/`; он исключён из Git. Не сохранять в отслеживаемых файлах ключи, recovery codes, cookies, API-токены, billing-реквизиты или содержимое копий.

### LAUNCH-IN-006 — минимальный внешний мониторинг

Канонический контракт — `docs/analytics-runtime-detail.md`; локальная закрытая DB-readiness команда подтверждена в `docs/ref6-readiness-results.md`. Сейчас нет публичного/защищённого HTTP readiness endpoint и нет выбранного внешнего наблюдателя. Обычный GET главной проверяет доступность страницы, но не заменяет отдельную проверку приложения/БД.

Рекомендуемый no-bloat вариант — один готовый внешний uptime-сервис, а не собственный monitoring stack. До подключения провайдера достаточно подтвердить семь фактов:

1. проверки выполняются вне VPS и способны заметить полный отказ хоста;
2. поддерживается HTTPS с custom header либо другой согласованный закрытый канал — секрет не передаётся в query;
3. интервал пять минут и правила последовательных отказов/recovery настраиваются и проверяемы;
4. есть один минимальный канал технических уведомлений владельца без требования Telegram на старте;
5. сервис не требует отправлять ему SQL, логи, ПД, cookies посетителей или внутренние ошибки;
6. сохраняется достаточная история результата/времени для launch smoke и разбора инцидента;
7. понятны стоимость, лимиты, страна/роль провайдера и способ удалить учётную запись/данные.

Отдельным будущим техническим gate остаётся минимальный защищённый способ вызвать существующую readiness-проверку. До его согласования нельзя обещать настоящую внешнюю app/DB проверку. Не добавлять Prometheus/Grafana, собственный агент, очередь, state machine или DEV-26/27 fallback только ради выбора сервиса.

Безопасный локальный путь для сравнительной заметки: `work/launch-inputs/monitor-provider/`; он исключён из Git. Не сохранять в Git endpoint secrets, recovery codes, cookies, API-токены, billing-реквизиты или полные incident payloads.

## Что не нужно выбирать сейчас

- MAX и Telegram URL: отсутствующие ссылки не публикуются.
- SMTP: не нужен, пока intake выключен.
- Аналитика, consent manager, YouTube и виджеты: остаются выключенными.
- DEV-26/27 runtime fallback: остаётся отложенным по D-923.
- Новая CRM, личный кабинет, API, чат, очередь или monitoring platform: не входят в этот чек-лист.

## Порядок закрытия без раздувания

1. Сначала `LAUNCH-IN-007`, потому что точные рекламируемые URL ограничивают migration/publication, но не требуют доступа к серверу.
2. Затем read-only `LAUNCH-IN-002` по пяти пунктам выше, чтобы зафиксировать фактическую production-среду до конфигурационного плана.
3. Вместе выбрать минимальные `LAUNCH-IN-005` и `LAUNCH-IN-006` по семи фактам каждого раздела; не строить собственные backup/monitoring платформы.
4. `LAUNCH-IN-003/004` закрывать только перед включением заявок и ПД.
5. `LAUNCH-IN-008` остаётся последним явным разрешением; оно не выводится автоматически из готовности остальных строк.

Текущий результат: базовый профиль не блокируется отсутствием необязательных контактов, SMTP или аналитики, но production release всё ещё закрыт обязательными `LAUNCH-IN-002`, `005`, `006`, `007`, `008`.
