## Основание

В шести парных измерениях без сети/БД пустой Python стартовал в среднем за 0,063965 с (CPU 0,029630 с), точный существующий worker с отвергнутым `{}` — за 0,265796 с (CPU 0,141118 с). Диапазон worker: 0,221549–0,299904 с. Это нижняя граница старта без TLS/SQL/ответа, не полное время HTTP-запроса и не доказанная единственная причина прежнего таймаута.

Отдельный importtime показал загрузку subprocess, pathlib и dataclasses до исполнения worker. Их cumulative времена перекрываются с зависимостями и включают планирование CPU; складывать их как гарантированную экономию нельзя. В полном снимке стартует 54 worker, поэтому этот повторяемый расход достоин исправления без повышения лимитов.

## Точное изменение

В существующем consumer.py оставить до ветки worker необходимые http.client/json/re/ssl/sys. Перенести parent-only импорты hashlib, subprocess, time, uuid, dataclass, Path и MappingProxyType после раннего выполнения worker и до объявления родительских dataclass.

Тот же блок проверки CLI/чтения stdin/вызова _http_worker/формирования ответа выполнить до parent-only импортов. После успешной записи ответа явно выйти с кодом0; прежняя ошибка остаётся ответом ok:false и exit1. При обычном импорте модуля родитель получает все прежние импорты, классы и методы.

Один дочерний процесс на запрос, фиксированный origin, CA/TLS, вход16КиБ, ответ1МиБ, whole30/request6, kill/reap, no-retry и все ограничения сохраняются. Серверные обработчики и данные не меняются. В work готовится отдельный кандидат/diff для ревью; он не считается уже установленным исправлением.

## Ограниченный runner WB15-001–003

Перед исполнением runner проходит независимое code-review. Один helper использует прежний Python image,256МиБ/0.5CPU/PIDs64, network none, readonly root и только readonly каталог с тремя публичными исходниками. БД, ключей, HTTP и новых томов нет. Whole guard35с, каждый проверочный CLI-процесс до3с; это предел диагностического runner, прежние30/6с клиента не меняются.

Для каждого варианта исполняются без изменения AST семь HTTPSWorkerTests и метод kill/reap из SnapshotTests. Это изолированные тела существующих проверок с unittest.TestCase вместо инфраструктуры Django, не полный Django suite. Дополнительно проверяются parent import/API, четыре настоящих отрицательных CLI и положительная ранняя CLI-ветка через runpy с замоканными SSL/HTTP. Все результаты сохраняются; при функциональном отказе A/B не начинается.
