## Fixture-профили и реальные действия

- `gallery-imported-originals-from-local-archive`: в изолированном приложении импортированы собственные214 originals, скопированные из локального архива, без обращения к живому сайту. `docs/analytics-media-evidence.csv` role=gallery-original — независимый oracle source_url/bytes/sha256; внешний URL используется только как идентификатор и никогда не запрашивается тестом. Существование CSV не является доказательством выполненного импорта.
- `synthetic-media-upload-files`: P-A с существующим изображением и синтетические svg/html/svg-disguised-as-png/jpeg-mime-png-bytes/png-extension-jpeg-bytes/truncated-png. `fixture.uploads[fileRef]={path,name,mimeType}` указывает на собственные сгенерированные подготовщиком файлы внутри `acceptance/generated-fixtures/<runId>/`; реальные байты, расширение и multipart MIME точно соответствуют проверяемому варианту. Все файлы синтетические, без фото/метаданных людей. PNG/JPEG/WebP могут быть кандидатами будущих fixtures, но ни один не считается утверждённым входным форматом по самому факту существования файла.
- `shared-media-replacement`: S-EDIT назначен P-A с разрешённым обычным текстом. Первый и второй placements P-A и один placement P-B используют X; ordinary/Stable/удерживаемый HTML также ссылаются на X. Y существует/разрешён владельцу, отличен от X. Alt текущего X отличен от тестовой подписи, выравнивание одно из допустимых. Для `submit-media-markup-direct` positive owner control обязан использовать тот же путь/метод/поля/допустимые значения, меняется авторизация/защитные токены; нельзя подтвердить права другим endpoint.
- `nested-media-catalog`: реальная папка P-A под `/img/`, непустые placements, хотя бы один вложенный `nested` файл с поисковым canary и история с реальными ссылками/хэшами; есть доступный корень `/img/`. Соседняя папка имеет тот же текстовый префикс без разделителя (например, `/img/foo/` и `/img/foobar/`) и файл с тем же поисковым canary. `media-fixture-identifiers.searchSiblingFolder` указывает на неё; положительный поиск внутри соседа сначала доказывает существование результата. Затем поиск в папке материала обязан исключить соседний файл: граница сравнивается с ровно одним завершающим `/`, а не голым startsWith общего префикса. Symlink/traversal защита фактически проверяется сервером, не фильтром адаптера до запроса.
- `media-cleanup-protected-consumer({consumerKind})`: X удерживается **только** выбранным типом current-page/common-block/draft/ordinary/stable/html, а отдельный orphan Y действительно кандидат. Это позволяет отдельно проверить каждый тип, не скрыть пропуск HTML наличием текущей ссылки.
- `media-cleanup-orphan-candidate`: X без ссылок, показан кандидатом. P-A содержит иной допустимый Asset; protected Y существует/нужен хотя бы одному потребителю. Непустые синтетические архив и backup находятся вне области cleanup. В race-сценарии после списка владелец реальным редакторским действием назначает X текущему месту P-A; исполнение старого confirmation либо отказывает целиком, либо исключает X, но не удаляет его.

Используется существующий openApplicationDriver/reset/act/observe/close. Все act исполняют **настоящий UI/HTTP**: upload-media-direct, submit-media-markup-direct, open-media-picker, search-media-picker, browse-media-folder-direct, rename-page, replace-image-here, prepare-media-cleanup, confirm-media-cleanup-direct. Никакого `attach-consumer` через запись БД или произвольного product API для обхода правил нет. Все protected-состояния допустимо создавать только подготовщиком собственных начальных fixture, не вместо проверяемых операций.

## Multipart и отсутствие приложения

`upload-media-direct({page,fileRef})` требует настоящего multipart-запроса с исходными байтами выбранного синтетического файла. Путь/имя multipart-поля зададут только будущие независимо проверенные bindings. JSON/base64 endpoint, клиентская очистка MIME, автоматическое исправление неверного файла либо создание Asset подготовщиком после act запрещены. Тестовый транспорт и проверка realpath не выбирают бизнес-лимит загрузки; превышенные byte/pixel пробы добавляются после отдельного согласования upload-policy. UI setInputFiles не должен скрыто заменить direct-server probe проверкой кнопки.

Отрицательные пробы без согласованного положительного upload-control **не доказывают исправность приёмного пути, точную причину MIME/extension-отказа или безопасность декодера**: неподдерживаемый формат может быть отвергнут раньше. Такой отказ не закрывает AC-026 и не выдаётся за полноценную проверку pipeline. Положительный формат/MIME берутся только из будущего независимого решения владельца, не из observed outcome/ответа приложения.

Конкретные bindings/приложение/fixture bridge ещё отсутствуют. Пока этот набор — написанные assertions, а не запущенные browser-e2e. Очистка/ссылки HTML требуют соответствующих ARC-10/READY и доказательств изоляции перед реальными разрушительными действиями; созданный синтетический HTML-потребитель не доказывает реализацию gate/head.

## Обязательная фактическая наблюдаемость

- `gallery-original-hash-inventory`:214 уникальных sourceUrl/bytes/sha256/hashFrom=storage-file-bytes. Хэш вычисляется чтением **импортированных файлов**, не копируется из manifest/Asset.sha256; независимое ревью наблюдателя проверяет этот путь. Неизменность байтов автоматически включает метаданные, но тест не заявляет правильность подписей/порядка.
- `asset({assetId})`: id/exists/path/bytes/sha256/references[{kind,objectId}], где хэш/существование относятся к физическому файлу. После удаления exists=false означает реальное отсутствие рабочего файла/Asset, не скрытую строку или вычисление по результату act. Будущие publicContentType/publicNosniff/privateSourceExists проверяются отдельно после согласованной политики, их tests сейчас не написаны.
- `page-media`: pageId/revision/folder/placements[{placementId,assetId,src,alt,alignment}] из текущего сохранённого материала; наличие всех значимых полей проверяется до сравнения. Нельзя возвращать копию before после save вместо чтения приложения.
- `media-inventory-state`: детерминированный список существующих пригодных assetIds. `last-upload-state`: фактические usableAssetCreated/activeContentExecuted. Последнее подтверждается изолированным браузерным canary/событиями, а не заявлением схемы. Конкретное наблюдение не должно запускать внешние скрипты/сеть или сохранять произвольный опасный файл публично.
- `media-fixture-identifiers`: фактические otherAssetId/otherAssetPath/protectedAssetId/orphanAssetId для профиля. Существование и принадлежность этих объектов необходимо доказать; фиктивный Asset не заменяет positive control.
- `media-picker-state`: currentFolder/rootFolder=/img//entries[{path,...}] фактического открытого выбора; entry paths ограничены корнем. Path traversal должен дойти до серверного обработчика, адаптер не подменяет его своей валидацией. Предусловия поиска гарантируют положительный вложенный результат.
- `historical-media-bindings`: реальные versionId/assetId/path/sha256 в детерминированном порядке. `retained-media-bindings`: реальные записи kind/assetId/objectId для ordinary/Stable/удерживаемого HTML. Их state сравнивается до/после замены; ссылка не исчезает из observe только потому, что стала исторической.
- `prepare-media-cleanup` возвращает фактические confirmation/candidates[{assetId,path,bytes}]/totalBytes. Непустой eligible control исключает always-empty список; точные opaque-подтверждения передаются без изготовления. `archive-and-backup-media-integrity` возвращает детерминированные archiveDigest/backupDigest, вычисленные из файлов собственных синтетических наборов вне области очистки.

Поля/ID должны присутствовать и иметь проверяемые типы/непустые значения, размеры/хэши проверяются до равенств. Наблюдения не получают expected и не моделируют правильный ответ. Реальность/полнота SQL/файлов/DOM, защита секретов и отсутствие влияния аудита чтения на сравнение проверяются отдельно на конкретном адаптере.
