# SEO-контракт: индексирование, canonical и разметка — ANA-R001

Версия 0.1, 2026-10-30. Исправление ANA-R001 в ANA-01 перед повторным независимым рассмотрением ANA-02. Основания: D-008/BR-007, D-023/D-024, D-243–D-246, D-248–D-253, D-280–D-284, D-295/D-300; REQ-001/REQ-002/REQ-007–REQ-011/REQ-025/REQ-046–REQ-050 и проектируемые **REQ-061/AC-061** свода. Этот файл сам не добавляет/не перенумеровывает строки свода. Исполняемых тестов, изменения сайта и согласования владельца нет.

## 1. Что принято и что предлагается

**Принятый объём:** Sitemap, robots, canonical, разметка автосервиса, поля SEO/alt; точные старые URL и исходные данные с явно принятыми исключениями; 301 только по разрешённой явной смене нового URL; скрытый существующий адрес — пустой белый 200, удалённый/неизвестный — 404; галерея page=2 и самостоятельные адреса альбомов сохраняются. Сотрудник не меняет SEO/медиа, владелец управляет разрешением индексации. Редирект или canonical не заменяет требуемый старый HTTP-контент.

**Предлагаемый законченный профиль к пакетному согласованию:** self-canonical для новых обычных страниц и старых без найденного canonical, сохранение четырёх наблюдаемых canonical, canonical нового корневого URL для обоих адресов автомойки, состав XML, правила robots/заголовков и доверенной JSON-LD ниже. Это технический выбор автора для ревью и владельца, а не уже полученный ответ. Его не нужно превращать в отдельный опрос по каждой строке; если при проверке выявится несовместимость с сохранённым бизнес-правилом, исправить профиль до реализации.

Не требуется заполнить все SEO-поля, получить rich result или присутствовать в Sitemap, чтобы разрешённая опубликованная страница отдала точный 200. Пустой description допустим D-249; отсутствие подтверждённых реквизитов исключает неподтверждённую разметку, а не сам материал. SEO не является авторизацией и не гарантирует включение в поиск/позиции.

## 3. Источник SEO-состояния и права

Предлагается единое проверяемое SEO-состояние страницы/разрешённой alias-группы: постоянный ID, точный текущий путь, публикация, разрешение индексации, canonical-цель по утверждённой карте, момент значимого изменения и поколение состояния. SEO-title/description/H1/alt и картинки продолжают собственные правила D-248–D-253, а не копируются из случайного текста. Назначения источников и подтверждение фактов контролирует `nesadmin`; сотрудник не передаёт индексирование/canonical/JSON-LD скрытым полем или ссылкой внутри абзаца.

Canonical не вводится как свободный URL редактора. Владелец работает с допустимой текущей страницей/утверждённым соответствием; сервер не позволяет выбрать произвольный внешний origin, закрытый ID, фрагмент, цикл или перенаправление вместо конечного материала. Изменение canonical в принятом старом соответствии требует явного проверяемого изменения конфигурации/карты с аудитом, а не переименования страницы или запроса с другим Host.

Абсолютные SEO-адреса строятся от доверенного production origin `https://estakada-service.ru`, а не из недоверенных Host/forwarded/Referer. Другая среда использует свою защищённую конфигурацию; тестовый origin не утекает в production XML/разметку. Варианты слеша, регистра, сегментов и существенные query берутся из карты, не унифицируются произвольным удалением символов.

## 4. Sitemap

Предлагается один корневой `/sitemap.xml`, UTF-8 XML с корректным namespace, экранированием URL и типом `application/xml`. В него попадают только актуальные опубликованные публичные материалы, разрешённые к индексации и являющиеся выбранным canonical-представителем со своим действительным 200. Включение в Sitemap — сигнал для поисковой системы, не гарантия обхода/индексации. Эти принципы и ограничения формата описаны в [Google Search Central](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

Профиль набора:

- включать индексируемые главную, услуги/каталоги, статьи, контакты, отзывы, акции, сохранённые legacy-материалы, корень галереи и каждый из 17 самостоятельных альбомов после готовности соответствующего представления;
- не включать скрытое/удалённое, административные пути/историю/предпросмотр, форму POST/receipt, health, логи/бэкапы/артефакты, перенаправляющий A и неканонический alias;
- не включать рекламные tracking-варианты, query page=1/page=2 с canonical на корень, `album`-варианты модальной галереи или случайные неизвестные параметры. Отсутствие этих адресов в XML не разрешает изменить их предусмотренный публичный ответ;
- старые страницы с невыясненными исходными ограничениями не объявлять индексируемыми лишь из-за отсутствия meta; перед запуском применить подтверждённый исходный профиль/решение владельца;
- `lastmod` выдавать только по подтверждённому последнему значимому изменению публичного материала/влияющих данных. Не использовать время каждого запроса, ночной сборки, миграционной операции или ручную «дату версии» вместо фактического изменения. Если подтверждённой даты нет — опустить lastmod; changefreq/priority не требуются;
- ограничения одного Sitemap: не более 50 000 URL и 50 МБ в несжатом виде. При росте нужен индекс/разбиение, а не усечение опубликованного списка. Это ограничения формата, не новый лимит числа страниц бизнеса.

Обычный ответ XML должен соответствовать согласованному поколению публикации/SEO: скрытие, удаление, noindex, смена URL и canonical не остаются в старом XML до следующей ночи. Любой используемый XML-кэш требует такой же доказанной актуальности; библиотека, Redis и расписание этим не выбираются. Условный GET может использовать валидатор набора; версия не равна текущему времени запроса. При неподтверждённой целостности/актуальности отдаётся 503 без заведомо неверного XML, а не неполный «успешный» список.

## 5. Robots и X-Robots-Tag

Robots ограничивает согласованный обход, **не доступ и не гарантированное исчезновение URL из поиска**. Публичный noindex должен быть доступен роботу для чтения директивы; скрытые данные защищаются авторизацией/правилами публикации независимо от поведения любого бота. Нельзя добавлять `Noindex:` в robots как замену поддерживаемому мета/HTTP-механизму. Основания: [robots introduction](https://developers.google.com/search/docs/crawling-indexing/robots/intro) и [Google noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

Предлагаемый доверенный production robots содержит `User-agent: *`, ссылку `Sitemap: https://estakada-service.ru/sitemap.xml`, запреты действующих административных/служебных префиксов и сохранённых недействующих CMS-префиксов из архива. Не запрещать все CSS/JS/изображения: необходимые публичные ресурсы остаются доступны. Не публиковать в robots список секретных документов/ID, токены или внутренние файловые пути. После выбора фактического административного пути сверить префиксы, а не считать `/admin/` уже установленным продуктом.

Для query предлагается сохранить общее правило `Disallow: /*?`, но добавить более специфические разрешения только для двух известных представлений:

```
Allow: /gallery-of-works/?page=1$
Allow: /gallery-of-works/?page=2$
```

Это контролируемое исключение к старому blanket-запрету, чтобы разрешённый page=2 мог отдать свой реальный HTML/canonical. Оно не разрешает произвольный crawler-поиск, новые query-маршруты или обход защиты сканеров. Синтаксис специфичности/окончания и фактические строки проверяются по [официальной спецификации robots для Google](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec); отсутствие соблюдения у другого робота не обходит серверную защиту. Неизвестный query не назначает себя canonical и не появляется в XML.

`robots.txt` — доверенный конфигурационный текст, не редактируемый сотрудником WYSIWYG. В обычном production он отвечает 200 `text/plain`; на закрытом стенде аутентификация и серверный запрет индексации дополняются отдельным robots, который не переносится в production случайно. При недоступном Django доверенный уже проверенный robots может выдаваться отдельно, без подключения к БД и без ложной гарантии доступности Sitemap.

Заголовок `X-Robots-Tag` формируется сервером/прокси из проверяемого состояния; пользовательский HTML/параметр запроса не задаёт его. Для опубликованного noindex — `noindex, follow`; для пустого скрытого 200 и закрытых ответов — `noindex, nofollow`. На индексируемой обычной странице достаточно отсутствия запрещающей директивы; предложения явно печатать `index, follow` не создают гарантии индексации. Для 301 noindex не добавляется как средство canonicalизации. У 404/503 статус сам сохраняется; никакой canonical на главную или JSON-LD не превращает их в успешный материал. Совместимость meta и HTTP-правил проверяется по [спецификации robots meta/X-Robots-Tag](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag).

## 6. Матрица ответа, canonical и индексации

Предлагается максимум один HTML `link rel=canonical` в head, в абсолютном доверенном URL. Не выдавать одновременно иной canonical через HTTP Link; сторонний плагин/JS не должен менять выбранную цель. Canonical задаёт представителя сходного материала, а не серверный редирект/авторизацию; поисковик может выбрать другого представителя. Основание: [Google canonical guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls).

| Состояние/представление | Обязательный HTTP по проекту | Предлагаемый canonical/индексирование | Sitemap/разметка |
|---|---|---|---|
| Обычная опубликованная индексируемая страница | 200 по точному URL | Новая — self-canonical. Старая с найденным canonical — сохранить подтверждённое соответствие; старая без него — добавить self-canonical после сверки карты. Не брать URL из рекламы/входящего Host | Один выбранный представитель в XML. AutoRepair только в местах/условиях §7 |
| Опубликованная с запретом индексации владельца | 200, публичный доступ не снимается | `X-Robots-Tag: noindex, follow`; предлагается не выводить canonical, чтобы не смешивать запрет с выбором индексируемой копии. Это не способ скрыть содержимое от посетителя | Нет в XML. Разметка бизнеса сама не отменяет noindex; в данном профиле AutoRepair на такой странице не выводится |
| Существующая неопубликованная | Пустой белый 200 D-052 | Только запрещающий HTTP-заголовок, без canonical/meta/текста общего шаблона внутри пустого документа | Нет XML/JSON-LD, нет доступа к черновику |
| Удалённая/неизвестная | Лёгкий 404 D-238/D-114 | Нет canonical/обхода на главную; при наличии заголовка noindex он не заменяет статус | Нет в XML/JSON-LD |
| Старая A после разрешённой смены нового URL на B | Актуальный 301 непосредственно на B, без цепочек D-243 | Не отдавать старую A как 200 с canonical на B. На целевой B собственные текущие правила; снятие B с публикации не удаляет редирект, полное удаление — D-244 | A исключена; B включается только при собственной доступной индексируемой публикации |
| Разрешённый alias с тем же содержимым | Предусмотренный точный 200; не создавать алиасы из произвольной транслитерации | Canonical на выбранного опубликованного представителя; сама цель даёт self-canonical. Не добавлять noindex только ради дедупликации. Политика alias-группы не меняет права/данные | Только представитель XML |
| Корень галереи | 200, все 17 альбомов D-245 | Сохранить найденный self-canonical корня | Корень и отдельно 17 адресов альбомов, не 17 query-копий |
| Галерея `?page=2` | 200 без редиректа, прежний второй набор D-245 | Предлагается сохранить наблюдаемый canonical на корень: новый корень содержит все альбомы, page=2 — исторический поднабор того же каталога. Это осознанный профиль данной галереи, не универсальное правило для любой будущей пагинации | page=2 исключён из XML, его реальный набор не заменён корнем |
| Галерея `?page=1` | Сохранить подтверждённую цепочку первого запроса; архив доказывает конечный корень, но не все промежуточные ответы | Финальный HTML корня сохраняет наблюдаемый root canonical; не выдумывать новый исходный 301 только по конечному 200 | Query-адрес не дублируется в XML |
| Каждый из 17 отдельных альбомов | Собственный 200 со своим содержимым D-246 | Self-canonical точного адреса альбома, не корень и не `?album=…`. Такую цель для старых альбомов предлагается добавить: найденного старого canonical у них нет | Индексируемый альбом включён отдельно после готовности; D-024 для байтов фото неизменен |
| Автомойка: старая `/services/drugie-uslugi/avtomojka` и новая `/services/avtomojka` | Оба точных адреса дают 200 с одним авторитетным содержимым, старый не перенаправляется D-023 | **Предложение к согласованию:** представитель — новый корневой `/services/avtomojka`, self-canonical у него и такой же canonical у старого адреса. Это новый профиль, не найденный факт старой страницы; общая индексация следует логическому материалу CONTENT-WASH | Только новый представитель в XML; старый URL продолжает принимать рекламу/переходы. Меню/главная/кампании автоматически не переписываются |
| Недоступная новая страница/цель без ночного файла в аварии | 503 по текущему реестру, без ложного старого 200 | Не придумывать canonical к старому A/главной как замену отсутствующему содержимому | XML может 503; главная остаётся допустимой по D-300 |

При запрете индексации/снятии публикации canonical-цели недопустимо оставлять ложную связь на закрытый/удалённый материал: общий материал/alias-группа применяет своё актуальное состояние; для иной сомнительной связи сервер отклоняет изменение либо убирает необоснованный canonical с предупреждением владельцу. Это не разрешение поменять HTTP-адрес алиаса/главной или произвольно назначить новую страницу с тем же URL старым объектом.

Tracking-параметры не становятся canonical-ключами. Их список и семантика сверяются с рекламными адресами ANA-Q041; подтверждённый параметр без изменения содержимого не копируется в canonical. Значимый `page=2` распознаётся отдельно, а не удаляется общим URL-cleaner. Отсутствие SEO-настройки неизвестного параметра само по себе не основание менять предусмотренный публичный ответ страницы.

## 7. Доверенная Schema.org AutoRepair и alt

Предлагается JSON-LD с `@context=https://schema.org`, `@type=AutoRepair` и стабильным идентификатором организации вида `https://estakada-service.ru/#auto-repair` на опубликованных индексируемых главной и contacts, где сведения действительно представлены посетителю. Это одна организация, не новая отдельная организация для каждой услуги/альбома. Тип AutoRepair — специализированный тип автосервиса Schema.org: [официальное описание](https://schema.org/AutoRepair).

| Данные разметки | Разрешённый источник/профиль |
|---|---|
| name, url, @id | Подтверждённое публичное название и доверенный origin/главная, не подпись конкурента, incoming Host или имя сотрудника |
| address / PostalAddress | Проверенный фактический адрес из собственных данных сайта; не выдумывать индекс, помещение, юридический адрес или реквизиты оператора. Для предлагаемого основного узла требуются подтверждённые name и физический address; если их пока нет, узел не выводится и владелец видит неполноту, страница всё равно отвечает 200 |
| telephone, openingHoursSpecification | Только подтверждённые общие телефон/часы, совпадающие с видимыми контактами; не график ответа на заявки или предполагаемая круглосуточная работа |
| image, logo | Явно выбранные публичные изображения бизнеса/логотип, связанные с Asset и безопасным URL; не приватные исходники или чужой бизнес |
| geo, sameAs | Только проверенные координаты и реальные публичные профили организации, если такие данные утверждены. Координаты не вычисляются по впечатлению от карты; отдельный видеоролик/URL виджета не объявляется профилем организации |

В первой версии не генерировать из комментариев/виджета `review`, `aggregateRating`, число отзывов, звёзды, ценовой диапазон, «лучший сервис», сертификаты или Offer с неподтверждёнными тарифами. Встроенный Яндекс-виджет сам по себе не подтверждает право/полноту таких данных в JSON-LD. Google отдельно ограничивает разметку отзывов бизнеса о самом себе; rich-result не гарантируется. См. [LocalBusiness](https://developers.google.com/search/docs/appearance/structured-data/local-business) и [review snippet](https://developers.google.com/search/docs/appearance/structured-data/review-snippet).

Схема строится доверенным шаблоном из разрешённых типизированных полей, не из произвольного JSON/HTML сотрудника. JSON сериализуется безопасно для HTML-контекста: пользовательская строка не закрывает script и не становится JS; формат application/ld+json не ослабляет CSP/авторизацию/проверку URL. Карта/Метрика/видеовставка не добавляются в JSON-LD как исполняемый код. Валидатор Schema и применимый проверяющий инструмент поисковой системы проверяют структуру/правила перед запуском; их «valid» не означает гарантированный показ результата.

Alt — поле конкретного использования картинки, а не изменение EXIF или байтов файла. Старые тексты/подписи переносятся из подтверждённого источника; новые описания задаёт владелец, допустимая подсказка — имеющаяся подпись/название без выдуманного визуального факта. Предлагаемый предел 300 символов совпадает с TECH-01, старое длинное значение не обрезается. Сотрудник без прав на медиа не меняет alt обходным HTML. Для информативного изображения нужен смысловой текст, для декоративного — `alt=""`; повторные миниатюры могут быть декоративными при понятной доступной подписи управляющей ссылки/кнопки. Отсутствующая подпись не заполняется SEO-спамом, номером телефона или неподтверждённой маркой машины. Принцип описательного alt и его роль в изображениях описаны в [Google Image SEO](https://developers.google.com/search/docs/appearance/google-images).

Доверенный общий шаблон содержит один viewport `width=device-width, initial-scale=1`; сотрудник/редактор контента не вставляет второй, не ограничивает масштабирование `user-scalable=no`/maximum-scale и не меняет viewport при восстановлении текстовой версии. Это предлагаемый технический контракт адаптивного шаблона, не новая редактируемая SEO-таблица. Оригиналы 214 фотографий не перекодируются ради alt/JSON-LD.

## 8. Аварийный HTML и актуальные маршруты

Этот раздел согласуется с уточнением §12 `analytics-html-reserve.md` и AC-HTML-011/012: актуальные состояния маршрутов/редиректы проверяются **до** выбора ночного HTML. Если допустимый новый URL переименован с A на B после ночной сборки, A возвращает актуальный 301 из внешнего реестра, даже когда на диске есть старый A.html; B без пригодного ночного файла отвечает 503. Не отдавать A как старый 200 и не перенаправлять B назад на A/главную. Удалённые/скрытые адреса сохраняют собственный 404/пустой 200; обычная главная не исчезает из-за старых ссылок на них D-300.

Предлагается расширить проверяемое состояние допуска SEO-признаком запрета индексации. Если владелец включил noindex днём, доверенный `X-Robots-Tag: noindex` усиливает старую ночную meta, не требуя дневной пересборки. Но обратное неверно: новый HTTP `index` **не отменяет** старую ночную meta noindex; повторное разрешение индексации может ждать свежего ночного файла. Это ожидаемая явно описанная ночная устарелость SEO-метаданных, а не обещание немедленного index в аварии.

Ночной HTML сохраняет свой один canonical и текстовые SEO-данные до следующей сборки. Прокси не должен добавлять конфликтующий HTTP Link canonical поверх старого HTML. Изменение адреса — строго актуальный маршрутный 301, а обычное изменение canonical/description/title по неизменному допустимому адресу может оставаться ночным до новой проверенной копии. Не утверждать, что устаревшая meta стала актуальной от одного успешного HTTP.

SEO-поколение/запреты должны подписываться/согласовываться с публикационным состоянием и проходить ту же проверку подлинности/свежести; неизвестное поле/несогласованную запись нельзя трактовать как разрешённый index. Конкретный формат внешнего реестра/исполнитель остаётся выбором реализации протокола, не библиотекой этого документа. Наличие сервиса SEO не вводит транзитивное выключение главной по удалённым целям.

Для XML в аварии предлагается безопасный базовый режим **503**, когда актуальный состав индексируемых доступных представителей подтвердить нельзя: старый `/sitemap.xml` не объявляется актуальным только потому, что лежит в ночном наборе. Если отдельный доверенный текущий XML-снимок и его поколение доказаны, допустим 200 по §4; список не включает B, который сейчас только 503. Отказ SEO XML не отключает допустимые HTML/главную и не запускает восстановление БД. Доверенный robots.txt остаётся самостоятельным файлом; форма/health/админка не получают ложного SEO-200.
