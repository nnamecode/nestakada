Действующие решения перечислены отдельно. Связи: REQ-002/REQ-008/REQ-012/REQ-028/REQ-029/REQ-043–REQ-050; AC-002/AC-012/AC-028/AC-029/AC-043–AC-050. **Актуализация по D-300:** ANA-Q058 закрыт прямым уточнением владельца. Удаление раздела само по себе не переделывает настроенную главную и не лишает её ночного HTML-показа. Владелец проверяет/редактирует главную отдельно; прежние публичные ссылки/цены в ночной копии допустимы. Удалённые/скрытые собственные адреса не открываются заново. ## 1. Уже принято — повторного ответа не нужно

- При отказе Django/БД автоматически использовать подготовленный HTML и уведомить владельца о подтверждённом переходе: D-280. При полном отказе того же сервера такой набор недоступен; нужен внешний наблюдатель.
- Собирать только ночью из опубликованного публичного содержимого, без админки/истории/заявок/секретов; новая проверенная копия заменяет старую только после успеха: D-281/D-295.
- Хранить две последние исправные HTML-копии; ошибки новой не вытесняют исправные: D-296. Временное место сборки учитывается отдельно.
- Вчерашние обычные тексты/цены допустимы, дневная правка не запускает сборку: D-295. Предельный возраст исправной копии не задан; новый срок здесь не вводится.
- Обычный внешний вид, без публичного сообщения о техническом сбое; форма при отправке предлагает позвонить без ложного приёма/независимого хранилища: D-283/D-284.
- Пять минут, две неудачи для подтверждения сбоя, два успеха для восстановления; возврат к приложению автоматический, без отката БД: D-276–D-278/D-282. Метод контроля уточняется в analytics-runtime-detail.md.
- Скрытая страница не должна открываться из старого снимка, удалённая не должна воскресать. Обычные ответы: скрытая — пустой 200, удалённая/неизвестная — лёгкий 404: D-052/D-238/D-295.
- Семь внешних/две локальные точки PostgreSQL/медиа — отдельный механизм, а не история HTML: D-101/D-105/D-296.

## 2. ANA-Q058 — какой конфликт решаем

Исторический стык до ответа владельца: ночной набор содержит главную с ценой/карточкой услуги, а днём источник удалён. Прежняя формулировка D-256 требовала убрать связанную позицию; запрет URL не убирал её из готового HTML. D-300 разрешил этот стык: удаление не переделывает главную автоматически, владелец проверяет её отдельно, ночной публичный вид допустим. Сам удалённый/скрытый маршрут по-прежнему закрыт.

Обычная правка суммы опубликованной услуги остаётся разрешённой устарелостью D-295. D-300 дополнительно разрешает прежние публичные элементы ночной главной после удаления источника. Из существования старой ссылки/цены нельзя выводить запрет всей главной. Это не разрешение публиковать закрытые данные/черновики или восстановить удалённую страницу.

## 4. Контракт набора и зависимостей — предложение

Один завершённый набор имеет непереиспользуемый ID, момент согласованного снимка, версии схемы/шаблонов, перечень точных маршрутов с вариантом допустимых параметров, соответствие файлам, тип ответа, размеры/контрольные суммы, перечень всех необходимых медиа и зависимостей. Например, HTML главной зависит от выбранных позиций прайса, общих блоков и ссылок навигации, а не только от Page главной.

Зависимости разделить как минимум на:

1. Собственный материал и его право оставаться публичным.
2. Содержательные заимствования: цена/название/карточка/вводный текст другого материала, связанные фотографии и блоки.
3. Публичная навигация/хлебные крошки/ссылки каталогов, включая ссылки общих блоков.
4. Версии шаблонов, кода и ресурсов, необходимых для безопасной отдачи.

Ручная веб-ссылка в тексте также учитывается как ссылка на внутренний известный материал; нельзя обходить отзыв, заменив ID текстовым URL. Неизвестные внешние ссылки не становятся безграничным графом обхода. Ночью обрабатывается только ограниченный реестр опубликованных объектов, а не произвольный URL из формы/параметра пользователя.

Ссылка на страницу и раскрытие её собственного закрытого содержимого имеют разный смысл. По D-300 прежняя публичная ссылка/карточка/цена главной не делает допустимый ночной HTML непригодным, даже если её цель удалена; на самой цели действуют её 404/пустой 200. Граф нужен для удержания файлов/правильных связей и выявления действительно закрытых данных, а не для транзитивного выключения главной из-за удалённой ссылки. Произвольный код автора не управляет условиями допуска.

Манифест не содержит имён/телефонов/заметок заявок, паролей, токенов или произвольных shell-команд. Он служебный, не общедоступный sitemap. Редакторский HTML не может задавать исполняемые условия, пути включения файлов или команды аварийного исполнителя.

## 5. Сборка и публикация — предложение

Состояния набора: `BUILDING` → `VALIDATING` → `READY`; ошибка → `FAILED`. `ACTIVE` означает выбранный исправный набор, а не его безусловную допустимость для каждого текущего маршрута. Предыдущий исправный набор остаётся `PREVIOUS`; `FAILED` не занимает одно из двух исправных мест.

- Получить согласованное опубликованное состояние страницы, общих блоков, дерева и связанных цен. Смесь данных до/после конкурентной публикации не является успешным снимком. Долгая транзакция с блокировками всего сайта не задаётся как решение: механизм согласованного снимка рассматривается в архитектурном ревью.
- Создать новый набор отдельно, без изменения активного указателя. При ограничении диска/срока работы операция заканчивается ошибкой; действующий набор не удаляется ради освобождения места под непроверенный.
- Проверить комплектность точных путей, медиа/хэшей, внутренних ссылок, разрешённую разметку, отсутствие закрытого содержимого и ложного успеха формы. Сверить граф зависимостей/допуск непосредственно перед публикацией.
- Защитить медиа нового набора от очистки до включения указателя. Успех нельзя объявить между переключением файла HTML и удержанием его изображений.
- После проверки переключить указатель на целый набор как одну наблюдаемую операцию; запрос видит старый или новый согласованный комплект, не половину файлов. Версионированные имена ресурсов не заменяются поверх старых байтов.
- Удалять вышедший из двух исправных наборов после прекращения его использования и повторной проверки ссылок. Общие медиа текущего сайта/версий/Stable/черновиков не удалять вместе с набором.
- Ошибка сборки создаёт наблюдаемый инцидент и сохраняет исправные наборы, но не снимает текущие запреты маршрутов/зависимостей. Два старых набора могут оказаться одинаково непригодны после одного отзыва.

Ночное время и ограничение длительности/ресурсов согласуются после хостинга вместе с резервированием PostgreSQL, чтобы тяжёлые задачи не накладывались без необходимости. Дневные изменения текста/цены не запускают такую сборку. Этот документ не создаёт cron/Планировщик/автоматизацию Codex.

## 6. Допуск при отказавшей БД — предложение, требующее отдельного ревью

Одной БД недостаточно: если она не отвечает, аварийный исполнитель не сможет узнать новый запрет. Предлагается отдельный ограниченный служебный реестр допуска/отзыва, доступный аварийному пути без Django/БД, с непереиспользуемыми ID объектов/операций, поколением состояния, целостностью и доступом только необходимым процессам. Это не вторая редактируемая CMS и не копия заявок.

**Важно:** транзакция PostgreSQL и замена файлов на диске не становятся одной атомарной операцией от использования `on_commit`. Документация Django описывает callback после коммита, но сбой callback не откатывает уже зафиксированные данные. Поэтому для отзыва нельзя ограничиться «сначала коммит, затем когда-нибудь обновить файл». Основание: [Django, Performing actions after commit](https://docs.djangoproject.com/en/5.2/topics/db/transactions/#performing-actions-after-commit), проверено 2026-10-30; ссылка не выбирает версию проекта.

Предлагаемый порядок безопасного отзыва:

| Шаг | Гарантия при сбое между шагами |
|---|---|
| 1. Перепроверить пользователя, права, актуальную редакцию/подтверждение и затронутые зависимости; сериализовать конфликтующие изменения | Устаревшее действие не может отозвать чужой новый объект/URL |
| 2. Долговечно опубликовать предварительный запрет аварийной отдачи самого отзываемого маршрута и действительно закрытых данных (`PENDING_DENY`), получить подтверждение; не включать главную только из-за допустимой старой ссылки/цены D-300 | До изменения БД собственная удаляемая/скрываемая страница не раскрывается при внезапном отказе; главная продолжает быть допустимой. При ошибке записи запрета изменение БД не выполнять |
| 3. Зафиксировать снятие публикации/удаление, историю и receipt операции в основной транзакции | При откате/неопределённом исходе предварительный запрет остаётся; это временная потеря доступности, а не раскрытие старого HTML |
| 4. Подтвердить окончательный тип запрета (`HIDDEN`/`DELETED`) и поколение по результату операции | Сбой финализации не снимает предварительный запрет; требует восстановления согласованности по зафиксированному ID операции |
| 5. После восстановления связи сверить pending с фактом БД/историей; разрешение снимать только при доказанной актуальности | Нельзя автоматически открыть старое содержимое по таймеру, откату системных часов или отсутствию новой ошибки |

Если основная БД уже изменена, а финализация недоступна, интерфейс не показывает «ничего не произошло» и не предлагает слепо повторять удаление. Показать безопасное состояние «Изменение записано, проверка аварийного доступа не завершена» с ID операции без секрета. Повтор с тем же receipt возвращает фактическое состояние. При неизвестном коммите сообщить неопределённость и предложить проверку результата, не вторую независимую мутацию.

Предварительный/неподтверждённый запрет даёт недоступность 503, а не выдуманное окончательное «удалено». Завершённый скрытый путь — пустой 200, завершённый удалённый — 404. Неотозванный путь с неподтверждённой допустимостью также не получает старый HTML.

При повторной публикации или создании нового объекта по прежнему пути старый допуск/снимок по совпадению URL не возвращается. Нужны ID нового объекта и подходящий снимок; до следующей ночи новое содержимое может не иметь HTML-резерва. Генерация набора не снимает чужой более новый запрет. Сравнения поколения до/после подготовки недостаточно для согласования с одновременным отзывом: требуется общая точка допуска, описанная ниже.

Чтение допуска — ограниченная операция по реестру в памяти/готовому файлу с целостным обновлением, без сканирования каталога, SQL или записи файла на каждый запрос. При потере/повреждении реестра не разрешать всё по умолчанию; использовать контактный резерв. Требуются проверки аварии процесса на каждой границе, задержек/переупорядочивания событий, ротации/восстановления диска и повторов.

### 6.1. Барьер запуска и свежесть после восстановления

Подпись/хэш доказывает целостность, но не свежесть: старые корректные HTML, БД и реестр могут откатиться вместе. Поэтому после запуска/восстановления и при неопределённой свежести реестра аварийный допуск закрыт до сверки с актуальным состоянием публикации и внешним журналом отзывов/доверенным поколением, которое не откатывается вместе с локальным диском/бэкапом. Одного чтения того же локального «последнего поколения» недостаточно. Откат пары целых подписанных файлов — обязательный отдельный сценарий.

Предложение требует выбрать место доверенного head/журнала вне общего домена отката, долговечное подтверждение записи отзыва и процедуру сверки с восстановленной БД. Не приписывать эти свойства просто наличию семи копий на Диске. Если такое место/свежесть недоступны или нельзя доказать актуальность после рестарта, отдаётся контактный резерв 503, а не разрешается старый набор. Это ограничение доступности предлагаемой безопасной схемы: при одновременном рестарте управляющего компонента и недоступной БД полная HTML-копия может оставаться закрытой до сверки. Конкретный способ защиты от отката ещё должен пройти архитектурное ревью.

### 6.2. Точка допуска ответа и одновременный отзыв

«Новый ответ» здесь означает выдачу, **допущенную к отправке после точки подтверждённого отзыва**, а не ответ на TCP-соединении, открытом раньше. Проверка маршрута/зависимостей и регистрация допуска конкретного ответа должны сериализоваться с закрытием допуска. Если отзыв выиграл эту границу, новый допуск запрещён; если ответ был допущен раньше, он может завершиться. Указанное поколение закрепляется за допущенным набором/ресурсами, которые нельзя удалить у выполняющегося ответа.

Подтверждение отзыва выдаётся только после долговечного запрета и закрытия точки допуска во всех компонентах, способных отдавать HTML. Неотвечающий/отставший компонент не получает права продолжать по локальному старому разрешению; его выдача должна быть исключена либо подтверждение операции остаётся неполным. Конкретный общий примитив синхронизации/протокол исполнения пока не выбран: две проверки файла и асинхронное оповещение воркеров сами по себе этих свойств не доказывают.

Не нужно удерживать глобальную блокировку весь сетевой ответ и заставлять владельца ждать медленного клиента. Уже допущенный до отзыва ответ/ранее переданные байты нельзя отозвать; гарантируется отсутствие новых допусков после подтверждённой границы, корректная перепроверка кэша и запрет новых ссылок. Механизм не обещает уничтожение чужих ранее сохранённых копий. Сценарии должны отдельно фиксировать порядок допуска/отзыва, а не только время завершения HTTP.

## 7. Матрица аварийных HTTP-ответов — предложение

Указанные 200/503 для полного HTML — предложение технической политики, не уже принятое решение по всему аварийному протоколу. Не применять правила как общий HTML-кэш нормальной работы.

| Ситуация | Ответ и действия |
|---|---|
| Опубликованный маршрут, допустимый набор/все необходимые медиа и зависимости | Готовый HTML 200, обычный вид; отдельный валидатор пространства `reserve + set + policy-generation`, чтобы не принять ETag обычного Django за тот же ответ |
| Главная содержит прежнюю публичную карточку/цену/ссылку удалённого раздела | По D-300 продолжать обычную ночную главную 200; не исключать её или элементы автоматически только из-за удаления. Сам целевой адрес обрабатывается отдельно |
| Актуальный служебный редирект старого пути новой страницы | HTTP 301 сразу на последний путь существующего целевого объекта, до поиска старого HTML; отсутствие цепочек и скрытие/удаление цели по §11–12. Ночной файл старого пути не заменяет 301 кодом 200 |
| Существующий путь с подтверждённым снятием публикации | Пустой белый 200 без Header/Footer/старого контента; не использовать старый HTML даже при совпадении ETag |
| Подтверждённо удалённый/неизвестный путь | Лёгкий 404/no-store без подмены главной; ранние сигнатуры сканеров отсекаются до дорогих операций |
| Новый опубликованный путь без ночного снимка | Контактный резерв 503 на том же URL, без редиректа и без чужого содержимого |
| Pending-отзыв самого запрошенного маршрута, действительно закрытые данные, невалидный набор/медиа, неизвестная целостность допуска | Контактный резерв 503, не попытка открыть предыдущий набор в обход запрета. Допустимые прежние публичные элементы главной D-300 не считаются таким отказом |
| Админка, история, предпросмотр, бэкапы/логи/заявки | Не попадают в публичный набор; статический сервер не раскрывает каталог/служебные файлы. Ошибка приложения не открывает закрытые экраны |
| POST формы, входа или административной операции | Не перенаправлять на статический GET и не выдавать HTML-успех. Подтверждённая запись требует приложения; при недоступности безопасный отказ/no-store, для формы нейтральное предложение позвонить |
| Проверка приложения/БД | Только реальная проверка; никогда не подменять ответом пригодной HTML-страницы |

Предложение по кэшу: полный аварийный HTML `no-cache` с отдельным валидатором; контактный 503/запреты/ошибки `no-store`. На первом ответе после смены режима/допуска предпочитать полный ответ, не 304 прежнего пространства. HEAD сохраняет те же статус/разрешения/заголовки без тела. Точный URL и только согласованные параметры (`page=2`, утверждённый выбор альбома) участвуют в разрешении; query с рекламной меткой не создаёт бесконечные файлы/ключи. Неизвестный параметр не должен обходить запрет или открывать другой материал.

`Retry-After`, если выбран, — рекомендация HTTP-клиенту о повторе запроса, не таймер восстановления/срок реакции владельца. Не обещать время устранения сбоя через этот заголовок; безопасно не указывать срок, который неизвестен. Основание: [RFC 9110, 503](https://www.rfc-editor.org/rfc/rfc9110.html#name-503-service-unavailable) и [Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after), проверено 2026-10-30.

## 8. Форма/скрипты и внешние ресурсы в резерве

Готовый HTML не содержит действующих одноразовых CSRF/receipt-токенов, паролей, сессионных данных или фрагментов персонального ответа. Внешний вид формы остаётся принятым, но её HTML-ветка не пытается принять заявку в недоступную БД. После отправки — нейтральное «Для записи позвоните нам: …»; реальный номер из проверенного снимка контактов, не выдуманный пример.

Повтор обычного POST после потерянного ответа обрабатывается идемпотентностью приложения при его доступности; резерв не утверждает, что заявка принята или не принята, если исход неизвестен. Возврат движка не должен автоматически повторять POST из браузера. Данные введённой формы не попадают в Telegram, почту, Метрику/Вебвизор или постоянное браузерное хранилище.

Внешние Яндекс/YouTube/Метрика не обходят согласованный режим cookies/LEGAL только потому, что ответ статический. Отказ внешнего виджета не превращает страницу в ложный аварийный режим БД; в обоих режимах приватные данные не передаются через параметры событий. Конкретная загрузка ресурсов зависит от READY-01/READY-05.

## 10. Служебные SEO-ответы

Sitemap/robots/canonical/разметка определены в analytics-seo-detail.md (исправление ANA-R001). Они не исключаются из требований только потому, что сайт находится в HTML-режиме. Скрытые/удалённые/неиндексируемые пути не выдаются как актуальный Sitemap; при невозможности доказать его состав допустим короткий 503/no-store без выдачи непроверенного XML. Robots — отдельный доверенный файл, не способ авторизации и не catch-all обычной главной. Это не причина лишать главную допустимого ночного вида D-300.

Актуальный запрет индексации может быть усилен проверенным X-Robots-Tag; старый meta noindex нельзя отменить одним новым HTTP index. Обычная ночная устарелость метаданных отдельно оговаривается SEO-профилем; не выдавать несовместимые canonical одновременно в теле и HTTP. Редиректы/собственный маршрут всегда разрешаются по актуальному реестру до старого тела HTML.

## 11. Смена URL и аварийная политика маршрутов — исправление ANA-R004

Связи: D-243/D-244/D-295, REQ-002/REQ-007/REQ-046/REQ-050, AC-007. Старые перенесённые адреса D-023 остаются защищёнными; описываемая смена допускается только для тех новых страниц/операций, которым она уже разрешена. Ночная частота и D-300 не меняются.

Служебная политика хранит не только допуск/запрет, но и **тип текущего маршрута**: `LIVE`, `LIVE_NO_SET`, `HIDDEN`, `DELETED`, `REDIRECT`, `URL_CHANGE_PENDING`. Для REDIRECT — устойчивый ID целевого объекта, его актуальный путь и поколение связи, не произвольный URL из запроса. Реестр/версия пути не заменяются поиском файла в каталоге. Редирект и текущий маршрут одного объекта имеют разные ключи.

Пример: ночью есть новая Page P по `/a`; днём владелец явно меняет её адрес на `/b`. В текущем реестре `/a` становится REDIRECT(P, `/b`), а `/b` — LIVE_NO_SET, пока нет набора для **этого точного пути и той же инкарнации объекта**. Старый `/a.html` не открывается как 200 и не переименовывается/перегенерируется днём. Совпадение ID P не делает тело с прежними canonical/путями корректным для `/b`; без подходящего файла `/b` получает контактный 503.

При следующей смене `/b` → `/c` все актуальные входящие редиректы P указывают сразу `/c`, включая `/a`; цепочка `/a` → `/b` → `/c` не создаётся. Публикация нового набора учитывает актуальную версию пути/политику и не отменяет более новую дневную смену. Политика редиректов обновляется независимо от пересборки тела, а не ждёт следующей ночи.

### Граница фиксации

Смена URL использует тот же протокол долговечного внешнего head/предварительного запрета/receipt и единого допуска, что отзыв публикации. В область операции входят старый/новый ключи, сам объект, проверка свободного адреса и **все входящие редиректы**, а не только один файл. Подготовка/подтверждение показывают старый/новый пути владельцу; фактические права/основание/занятость повторно проверяются в короткой фиксации.

До фиксации нельзя объявить новый 301 доказанным; при неопределённом исходе URL_CHANGE_PENDING не разрешает старый HTML-200 и не выдумывает новое местоположение. Если операция откатилась, возврат старого разрешения возможен только после доказанной сверки актуального состояния, а не по времени ожидания. После успешной фиксации реестр даёт согласованную пару старый 301/новый путь и плоские входящие редиректы. Известный DB-commit с неоконченной финализацией честно остаётся незавершённым с безопасной недоступностью до сверки. Ранее допущенные ответы/отставшие воркеры следуют общей границе §6.2.

При удалении P подтверждение включает его текущий путь и весь актуальный список удаляемых редиректов D-244. В реестре они прекращаются вместе с P; при повторном использовании пути другим объектом старые редиректы/HTML/канонические связи не присваиваются ему по строковому совпадению.

## 12. Аварийные 301/новые пути и приёмочные дополнения

| Состояние при отказе БД | Актуальный аварийный результат |
|---|---|
| `/a` — REDIRECT на существующий опубликованный P по `/b` | 301 с Location `/b`, без цепочки; не отдавать старый `/a`-200, даже если его файл есть |
| `/b` — текущий путь P, но ночного файла этого пути/инкарнации нет | Контактный 503 на `/b`, без редиректа на чужую/старую страницу; после следующего пригодного набора возможен обычный 200 |
| P переехал дальше на `/c` | `/a` и `/b` сразу 301 на `/c`; для `/c` — собственная пригодность набора/503, не автоматический перенос старого тела |
| P существует, но снят с публикации | Старые редиректы сохраняются по D-244 и дают 301 на текущий путь; сам текущий путь отдаёт пустой белый 200, без содержимого |
| P удалён | Его текущий путь и все подтверждённо удалённые входящие редиректы — 404, без оживления прежних файлов |
| Один из освобождённых путей занял новый объект Q | Применяется состояние Q и его собственный набор, до него LIVE_NO_SET/503; старые связи P не возвращаются |
| Смена пути/целевого списка не завершена или поколение неизвестно | Для затронутых ключей безопасный 503/no-store, не старый 200 и не недоказанный Location; главная не выключается из-за старой допустимой ссылки D-300 |

301 формируется из проверенной внутренней политики/ожидаемого HTTPS-host, не Host/redirect-параметра пользователя. Значимые query соответствуют отдельной карте старых маршрутов, не произвольной строке перенаправления. Предложение cache-политики: no-cache и отдельный валидатор политики редиректа, не старого тела. Сервер не обещает отозвать ранее запомненный клиентом 301 — это ограничение уже отмечено D-244.

| ID | Связи | Сценарий/критерий |
|---|---|---|
| AC-HTML-011 | REQ-007/REQ-046/REQ-050; AC-007 | Ночной `/a`, дневной `/a`→`/b`, затем отказ БД: `/a` даёт актуальный 301, `/b` без своего набора — 503. При `/b`→`/c` оба старых пути сразу ведут `/c`. Скрытие/удаление P и повторное использование Q следуют таблице, старый файл не даёт ложный 200. |
| AC-HTML-012 | REQ-002/REQ-007/REQ-046; AC-HTML-003 | Прервать смену URL/обновление входящих редиректов на каждой границе записи запрета, коммита, финализации и допуска; повтор того же receipt не создаёт цепочку/дубликат. Pending не открывает старый 200/неверный Location, отставший воркер не выдаёт недопущенный ответ, главная сохраняет D-300. |

## 13. Граница готовности

Не выбраны исполнитель/прокси/формат реестра, фактическая долговечность файловой публикации на хостинге и схема согласования с БД. Не считать запись протокола доказательством реализации/корректности. Перед этапом 6 нужны итоговое независимое ревью и явное согласование; реальные конфигурации/исполнители/библиотеки сейчас не создаются.
