# Контракт локального тестового адаптера — TEST-03/04

Дата2026-10-30. Подготовка тестов разрешена D-302/D-303; запрет кода сайта и любых действий на старом VPS сохраняется D-305. Этот документ описывает **внутренний интерфейс тестов**, а не API/модели/служебные endpoints продукта и не инфраструктурную схему ARC-10.

## Текущий результат

application-contracts.spec.js содержит конкретные вызовы/проверки прав, конфликтов, версии/Stable, ручного снимка и заявок. Это **написанные утверждения, ожидающие конкретного подключения настоящего изолированного приложения**, а не готовые browser-e2e. Исторический первоначальный прогон дал APPLICATION_DRIVER_NOT_IMPLEMENTED. Никакой fake in-memory реализации сайта нет.

После D-307/D-308 подготовлен isolated-application-driver.js: UI/HTTP-транспорт, фактическое чтение, ограничения и протокол локального подготовщика. Конкретные local-bindings.json и local-fixture-bridge.mjs ещё отсутствуют; приложение и его модели/URL не создаются ради обхода запрета кода. Подробности — [локальный адаптер](local-test-adapter.md), дополнительные профили — [жизненный цикл](acceptance-content-lifecycle.md). До независимой проверки конкретного подключения и остальных ветвей TEST-03/04 не завершены. ARC-10 по-прежнему обязателен для инфраструктурных сценариев.

## Интерфейс и доверие к доказательствам

- Экспорт driverKind = real-isolated-application-v1 и createDriver({baseURL}); только фиксированный модуль рядом с тестами, не путь/URL произвольного внешнего плагина. Маркер — декларация, **не доказательство** настоящего приложения. Приёмка адаптера независимо проверяет реальные UI/HTTP/наблюдения и изоляцию.
- reset(profile, options) создаёт независимый синтетический набор перед каждым тестом и подтверждает его инварианты; не создаёт ожидаемый результат проверяемой операции. Удалять/менять можно лишь собственные тестовые объекты на изолированном стенде.
- act(actor, action, arguments) выполняет действие через настоящий UI/HTTP. submit-page-direct/read-history-direct/view-request-direct проверяют прямой HTTP-путь и серверные права; нельзя заменить их отсутствием кнопки. Прямое изменение БД допустимо только для начальной fixture/наблюдения, не вместо проверяемого save/transition/delete.
- observe(view, arguments) читает фактическое состояние/HTTP/открытый ввод и нормализует **названия**, но не вычисляет правильный ответ за приложение. Не получает expected из теста. Доказательство включает исходную операцию/роль/фактический результат и идентификаторы синтетической fixture; секреты/ПД в артефакты не входят.
- close() закрывает только собственные browser contexts/ресурсы теста. Действующий VPS, его файлы/БД/ОС и старый сайт не являются допустимой целью.

outcome=accepted/denied/conflict/pending — нормализованные классы результата тестового драйвера, не обязательные тексты/коды HTTP продукта. pending требует явного наблюдаемого признака ожидания и не означает создание заявки. new/in_progress/done/cancelled — четыре принятых статуса Request; pending к ним не добавляется. OWNER соответствует nesadmin, S-EDIT/S-OTHER/VISITOR — синтетические роли. Профили/идентификаторы ниже не задают реальные URL, ORM-поля или интерфейсные селекторы.

Время/пароли генерируются изолированно, не берутся из production и не хранятся в Git. Оригинальные поля заявки — синтетические, без контактов людей. Никакого вызова/отправки реальному номеру, Telegram/Метрике/почте нет.

У assigned-page-with-owner-draft также есть P-MAIN — настоящая главная тестовой fixture с определёнными защищёнными полями/историей, доступная только владельцу. fixture-identifiers.otherAssetId указывает на другой существующий разрешённый владельцу Asset. Негативные пробы защищённых полей используют допустимые значения по типу: boolean публикации, существующий Asset и валидный текст. Тот же payload затем принимается владельцем и поле действительно меняется; отказ сотруднику не может считаться достаточным при невалидном вводе. Для прямого чтения истории/заявки/заметок положительный запрос владельца подтверждает существование объекта/доступного пути и наличие canary перед отрицательным запросом другой роли.

Для этих положительных контролей нельзя заменять проверяемый direct-запрос набором других действий: HTTP-метод/конечный путь/обработчик и значения должны быть теми же, меняется только контекст авторизации/связанные защитные токены. Если согласованная реализация разделит операции на разные обработчики, соответствующие тестовые действия должны быть явно разложены и перепроверены до применения; адаптер не должен скрыто считать невалидное поле допустимым на другом маршруте. Нормативная аналитика не требует общего endpoint для этих операций.

## Наблюдаемые представления

page: revision означает основание **текущего опубликованного содержимого**, не общий token обновления списка истории; publicText/draftText раздельны; protectedPage-поля и versions с id/kind/isStable/isCurrent/text/savedAt. currentVersionId указывает на существующую версию. manual обозначает ручной снимок. Идентификатор result.versionId связывает конкретно созданный снимок, а не случайный последний элемент.

request: id/revision/status/createdAt/original/notes/history читаются из реального обращения. history в этих тестах означает историю бизнес-изменений статуса/назначения/заметок, а не технический аудит чтения. last entry при статусном переходе содержит нормализованные actor/from/to; notes — фактические записи с автором/датой. Тесты не требуют отсутствия отдельного безопасного аудита отказа/просмотра.

public-page-body возвращает настоящее публичное HTML/содержимое выбранного материала. open-editor-input — ввод в конкретной открытой вкладке actor; не localStorage или копия из серверного snapshot. Для отказов body содержит фактический ответ, чтобы отрицательные canary-проверки не работали на придуманной пустой строке.

## Дополнение: форма и границы

form-contracts.spec.js содержит74 отдельных теста для home/contacts:20вариантов обязательности/длин/NUL,14вариантов телефонов и3идемпотентных ветви на каждую форму. Пределы1–100/300/4000/64 и нормализация телефона берутся из принятого TECH-01. Синтетический номер +7 и10нулей не проверяет существование/владение и никогда не вызывается.

submit-form-direct отправляет настоящий HTTP POST в обход клиентской валидации, с действительным контекстом из open-form; названия name/phone/car/comment/consent являются **тестовым представлением** принятой таблицы, не выбранными HTTP-полями продукта. Адаптер не должен обрезать/очищать/валидировать payload вместо сервера. undefined означает отсутствие поля, а не пустую строку. fieldErrors содержит нормализованные поля фактической серверной ошибки.

request-by-id читает фактическую созданную заявку, original.phone — сохранённое нормализованное значение. Валидационный отказ не создаёт заявку/доказательство согласия/цель. Успех даёт одну заявку и согласие, но **не требует цель Метрики при direct HTTP без JS**: проверяется верхняя граница0–1на одно намерение/0–2на два. Полное прохождение AT-057 и доставка реальной цели требуют отдельных браузерных/LEGAL-проверок. Повторные POST должны не порождать дубликат цели; доступность Метрики не условие создания заявки.

Связь intent→Request теперь берётся только отдельным закрытым form-intent-records(source,context), не из публичного result.requestId. Сохраняющиеся74form-пробы исправлены в этой области; параллельные POST допускают фактический accepted/pending с последующим явным повтором того же намерения после подтверждённого commit.20новых оконных проб и ограничения — acceptance-form-windows.md. Ранний список непокрытого ниже относится к исходному проходу; новые ветви частичны и не завершают весь AC.

explicit-new-form-intent воспроизводит явное действие посетителя, не автоматический сброс ключа после неопределённого результата. Для параллельной проверки драйвер реально отправляет два POST до завершения первого, не сериализует их и не реализует собственную receipt-таблицу. Тесты дают частичные утверждения для AT-030/031/032/108/109/110; отсутствие JS, потеря ответа, смена CSRF/согласия, окна срока/ёмкости, неизвестные/повторённые поля и прочие ветви ещё остаются в исходном каталоге.
