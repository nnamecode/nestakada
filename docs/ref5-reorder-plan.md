# REF-05I — простой reorder страниц

Дата: 2026-11-05. Статус: завершено по D-621; независимое review `APPROVED`.
Область: только изменение порядка siblings внутри текущего родителя. `move`, создание/удаление страниц, схема БД, legacy-код и production вне инкремента.

## Зачем упрощаем

Старый `reorder` связывает локальное изменение порядка с хешем всего дерева, всех маршрутов, current revisions и счётчика tree receipts, затем создаёт ещё один `OperationReceipt`. Для перестановки siblings это избыточно: несвязанное изменение другой ветки или содержимого страницы ложно делает форму устаревшей, а журнал идемпотентности растёт бессрочно.

## Приёмочные сценарии

- **RORDER-001 — права и сессия.** GET и POST доступны только владельцу с актуальными `generation` и editor-session; серверная проверка выполняется до разбора подписанного token. Сотрудник и прямой запрос не меняют данные.
- **RORDER-002 — точная область.** Подписываются actor, generation, page, operation, исходный parent и снимок всех siblings этого parent. POST не может сменить parent; `before` должен быть sibling того же parent либо пустым значением «в конец».
- **RORDER-003 — локальная транзакция.** Успех атомарно меняет только `Page.position` затронутых siblings и создаёт ровно один `TREE_REORDER` audit. Parent, name, kind, publication, routes, revisions, Stable/drafts/media и страницы других родителей неизменны.
- **RORDER-004 — нормализация.** После успеха позиции siblings текущего parent равны `0..N-1`, уникальны и соответствуют выбранному `before`. Уже существующие разрывы/аномальный порядок нормализуются в той же транзакции.
- **RORDER-005 — stale/ABA/concurrency.** Locked PostgreSQL `xmin` и точный снимок sibling-набора/порядка отклоняют удалённую, добавленную, перемещённую или изменённую после GET страницу, возврат видимого порядка через промежуточные записи (ABA) и второй concurrent submit. Ровно одна конкурентная команда может изменить порядок и записать audit.
- **RORDER-006 — неизменившаяся команда.** Перестановка, которая после нормализации не меняет фактический порядок и позиции, отклоняется без audit и без записи данных.
- **RORDER-007 — отсутствие нового ledger.** Новый путь не создаёт `OperationReceipt` и `IdentityReservation`. Повтор после успеха или потерянного ответа конфликтует; актуальный GET показывает фактический порядок.
- **RORDER-008 — rollback.** Ошибка записи audit откатывает все позиции. Ошибка БД/ОС возвращает управляемый 503 с прежними полями формы; частичного порядка нет.
- **RORDER-009 — совместимость.** Если `operation_id` уже имеет legacy receipt, HTTP направляет запрос в старый exact replay. Receipt другой команды конфликтует. `rename` simple/legacy и `move` остаются без изменений.

## Проверка

Сначала узкие command/HTTP/fault/concurrency тесты, затем весь `content`, затем связанный набор `media_library + page_versions`. После — независимое review, read-only проверка основной test-БД, login smoke и остановка `foundation-test`. Production, VPS и старый сайт не затрагивать.
