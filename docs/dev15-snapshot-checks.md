# DEV-15 — полный снимок и безопасный старт: проверки до кода

2026-11-02, D-377, принятой основой остаются dev15-proposal.md §5/7 и SC15-008/012/016. До реализации/прогона это контракт, не PASS. Новых пакетов/контейнеров/сетей/томов/ресурсов/production нет. MAIN с четырьмя synthetic operations и архив60/15360 сохраняются, writes disabled.

Техническая детализация существующего клиентского snapshot-протокола: отдельное reader-only GET `/v1/snapshot-manifest` возвращает protocolVersion1, один полный head, counts routes/tombstones/items и SHA256 канонического массива ВСЕХ snapshot items. Он вычисляется потоком в существующей Head-транзакции, в том же порядке/формате, что страницы: route key ASC, затем tombstone request UUID ASC. Это не HMAC-доказательство свежести TRUST; доверие — существующий проверенный TLS и независимая incarnation. Прежние страницы сохраняют свой формат и digest. Manifest/page/final head имеют no-store и закрытую роль reader.

Клиент последовательно получает manifest→все страницы строго cursor0/100/200… и generation→повторный head. Проверяет закрытые schemas/точные типы, ACTIVE/incarnation/protocol, непрерывность полного head, pageDigest, точное число строк/границы/nextCursor, устойчивый порядок/уникальность и корректные семантические поля каждой строки; target hash сверяется с точными UTF-8 bytes. Проверяет полный digest и последнюю независимую head-сверку. Никаких нормализаций URL/redirect/object ID. Частичный результат наружу не возвращается. Максимумы следуют существующим server caps:50000 routes/10000 tombstones/60000 items,64МиБ канонического снимка, ответ до1МиБ, не более600 страниц. Изменившееся поколение/429/ошибка не вызывает внутреннего бесконечного повтора: один bounded проход остаётся closed; оператор/контроллер может начать новую проверку явно.

Транспорт — стандартная библиотека Python, фиксированный HTTPS trust-ingress:8443, проверка CA/имени и reader credential из существующих закрытых файлов. Запрещены redirect, cookies, произвольные host/path и секреты в query/log/исключении. Запрос до6с, единый deadline до30с на весь проход; превышение остаётся закрытым, лимиты не повышаются. Precode review уточнило: interread socket timeout не является абсолютным deadline; сетевой запрос изолируется короткоживущим процессом того же Python внутри прежних256МиБ/PID64, parent ограничивает communicate/wait, по deadline kill+bounded reap. Ключ передаётся через stdin, не CLI/ENV/логи; ответы ограничены1МиБ. Regression медленно выдающего данные дочернего процесса должна доказать прерывание и отсутствие живого child, а не только проверку часов между страницами. Новых программ/служб/ресурсов нет. Это ограниченный первый клиент, не обещание чтения любых600страниц за30с.

Результат успешного чтения — immutable snapshot bytes/head/counts/digest, пригодный для следующей интеграции. Стартовая проверка требует полного совпадения восстановленного head cohort с актуальным и полного снимка; старый receipt/чужая incarnation/FROZEN/недоступный head не дают registry-ready. Каждый запуск начинается закрытым, локальный сохранённый ready-флаг не принимается как полномочие. Даже успешная сверка возвращает только snapshotReady; htmlAdmission/workflowComplete остаются false до настоящих APP/main receipt/reconciliation/gate DEV-23/26/27/29. Существующее исправное Django здесь не подключается и не выключается.
