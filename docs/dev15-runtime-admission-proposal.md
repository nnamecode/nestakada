## Что предлагается владельцу

Рекомендую подготовить и локально проверить рабочий профиль службы TRUST, принимающий новые технические IDs без заранее перечисленного списка, с авторитетными машинными ролями, ограничением накопленных данных и сохранением всей прежней истории. Это позволит затем интегрировать DEV-29. Права владельца/сотрудника и подтверждение удаления по-прежнему проверяет будущая CMS; новая служебная политика не меняет эти бизнес-правила.

Новых программ/образов/контейнеров/сетей/томов/публичных портов нет. Используются те же три pinned images,896МиБ/1.25CPU/PIDs и наблюдаемый бюджет2ГиБ наT:. Добавляется одна небольшая неизменяемая таблица допуска в **существующую** PostgreSQL и новая ветка проверки подписи/состояния. Windows, старый сайт и VPS не затрагиваются, настоящий APP не подключается к TRUST в этой работе.

При заполнении нет автоматической очистки tombstones/истории или расширения лимита: новые опасные изменения отклоняются, точные replay/завершение ранее принятых в пределах резерва и чтение сохраняются. Пересмотр ёмкости/очистки — отдельное решение, не часть этого предложения. Публичное чтение сайта не начинает обращаться к TRUST на каждый запрос.

Если оно/ресурсы не проходят — профиль остаётся disabled, новые числа автоматически не предлагаются уже утверждёнными.

## Подписанная политика и допуск конкретного запуска

Предлагается новый closed формат файла допуска версии2 с scope `LOCAL_TRUST_BOUNDED_WRITER`. Подпись HMAC-SHA256 — существующим recovery-secret, canonical JSON тем же способом. Writer-secret подпись не создаёт; ключ не попадает в APP backup/URI/логи. Это файл оператора в существующем private каталоге, readonly bind; браузер не выбирает файл/политику/роль.

Формат логически разделяет два подписанных раздела:

- **Policy:** policyId/epoch, incarnation/DB/protocol, полные sourceFiles/fingerprint и schema fingerprint с миграциями/ограничениями/триггерами, все caps таблицы, hashes фактических unit/calibration/review evidence. Никаких operationId/fingerprint whitelist для обычной записи. Политика определяет именно этот проверенный вариант кода и ёмкость.
- **Run lease:** policy fingerprint, runtime UUID, SHA загруженного credentials config, fingerprint конфигурации и фактического operator Docker inspect/caps/networks/mounts; evidence исключения прежнего API и новой загруженной конфигурации. Отдельно≤4точных recovery-action descriptors и reconciliation/exclusion proof при явной процедуре восстановления; по умолчанию список пуст.

Весь envelope≤64КиБ. Policy row хранит только ограниченную политику/цепочку/свидетельства, без сырых ключей/тел/URL заявок. Обновление run lease при обычном перезапуске **той же** проверенной политики не добавляет policy row и не исчерпывает16версий. Новые source/schema/caps требуют новой policy revision и её evidence/review; само изменение файла или ENV не применяет её к БД. Конкретное изменение уже принятой архитектуры/caps согласуется отдельно; рутинное обновление evidence без такого изменения не требует выдуманного повторного архитектурного согласования.

Новая ветка ENV `local-bounded-writer` лишь выбирает validator. `disabled` всегда закрыт; отсутствие/подмена подписи/source/schema/config/runtime/caps/политики закрывают запись. До SQL проверяются auth/closed DTO/body/файл/HMAC/source/config/runtime/собственный API cgroup; под тем же Head lock повторяются file/schema/incarnation/текущая policy/role/активный binding/epoch/CAS/count/byte/reserve проверки. DB/ingress ресурсы — подписанное operator evidence, не фиктивный доступ API кDocker socket.

Новый prepare принимает caller-generated UUID при действительной роли/текущем epoch и свободных пределах. Точный ранее сохранённый phase replay распознаётся до новогоCAS/count расхода; другой состав/credential/terminal исход запрещён. Все текущие PENDING_DENY/UNKNOWN/terminal/tombstone правила и гарантии D-376 сохраняются. Никакого endpoint «разрешить всё» или управления политикой от writer не добавляется.

## Отделение от прежнего фиксированного тестового плана

**Не предлагается менять или очищать Head.plan_id/permitted_operations/permitted_recovery_actions, удалять trust_plan_guard, расширять прежний pin ротацией или переинициализировать MAIN.** Не меняются прежние0001/0002 и сохранённый архив.

Предлагается additive миграция0003: таблица `AdmissionPolicy` (планируемое имя, файла пока нет). Записи имеют уникальный monotonic epoch/UUID, previous policy digest, canonical policy и её digest, legacy-plan seal для первого перехода, ограниченный учтённый размер; UPDATE/DELETE запрещены DB trigger. Последняя запись выбирается только в рамках общей Head-блокировки. Новых Head-полей не требуется: текущую версию определяет последняя неизменяемая policy; новая активация сериализуется тем же Head lock и отдельно увеличивает generation/digest. Migration сама не активирует запись и не создаёт пустой permissive допуск.

Первый переход — отдельная закрытая команда оператора, **не публичный HTTP endpoint**. Она проверяет разрешённую подпись/policy, текущие incarnation/full Head/full state digest, все counts и прежний pin, учёт нового row/caps/evidence/durability, отсутствие ранее применённой несовместимой политики. Только атомарный commit создаёт первый row с seal прежнего pin/состояния и advancesHead. Для имеющегося набора ожидаемая исходная точкаhead9/epoch2/4operations/3routes/1tombstone/2recovery; при несовпадении — отказ, не reset. После перехода полное содержимое прежних операций/запретов/ключевых bindings сохраняется; изменяются только явно учтённые admission metadata и Head generation/digest/logical bytes. Writer epoch/активный ключ при этой политической активации не меняются сами собой.

Для команды существует отдельный закрытый подписанный **ActivationIntent**, не только CLI-флаги: scope активации, action UUID, точный policy digest/полная policy, predecessor epoch/digest (для первого — legacy seal), ожидаемые incarnation/full Head/stateDigestVersion/full state SHA, hashes фактических evidence и config. HMAC связывает весь intent с policy. Новая запись сохраняет intent digest/action ID и предыдущее состояние. Runtime lease затем подписывается отдельно, уже по окончательному container ID. Ожидаемый исходный Head относится только к активации: обычные операции не требуют оставаться на Head9 после их собственных commits.

Точный повтор operator-команды возвращает сохранённое подтверждение без второй policy/generation; несовпадающее expected-state/состав — отказ. Прежний fixed trial после первого policy row **retired для новых мутаций**, даже с правильно подписанным старым trial envelope. Его pin остаётся неизменяемым историческим свидетельством; новые general операции не обязаны входить в старый список. Ни mode downgrade, ни замена ENV/lease на прежний файл не возвращают старые полномочия. Политика не доказывает свежесть при откате всей TRUST вместе с ключами — это прежний внешний ARC-10.

Проверка retired обязательна также в старой ветке `local-test-permit` **под Head lock до проверки membership/мутаций**. Авторитетная policy всегда последняя применённая запись БД; validator не ищет среди старых rows подходящую политику из файла. Отказ старого scope не запрещает read/status или законный exact replay сохранённой фазы через действующий working profile для того же ещё активного credential/epoch; отозванный ключ при этом остаётся запрещённым.

После успешных unit/capacity/code-review локальная первая активация проводится при остановленных прежних API/ingress. Миграция/команда используют существующую закрытую migrator/operator роль в tool256МиБ при DB512МиБ, не одновременно с API/ingress. Подтверждается сохранность. Новый API создаётся с новым runtime в disabled, known container ID и загруженными конфигурациями; при необходимости выбора новой validator-ветки пересоздаётся с ещё недействительным envelope. Только после установленного final ID/exclusion подписывается run lease; stop→запись втотжеinode→start того же контейнера/ENV, ingress пересоздаётся для актуального upstream. Нет публикации валидного lease до знания окончательного ID или смены ENV после его подписи.

Run lease переиздаётся только после operator проверки старого API stopped/removed, нового ID/runtime/config и неизменности применённой политики; один новый UUID не является exclusion. Обычный Start по-прежнему начинает disabled и ничего автоматически не переинициализирует/не активирует. При ошибке после operator commit policy row/Head сохраняются, runtime остаётся закрытым; сохранённый точный intent/receipt позволяет проверить и продолжить тот же переход, не выпускать его заново.

## Recovery и полная сверка состояния

Обычный writer не получает права fence/activate или смены политики. Recovery остаётся с прежней отдельной ролью и **явно подписанными exact action descriptors** в run lease, ≤4сохранённых receipt суммарно, включая прежние2. Без descriptor recovery endpoint закрыт. Новая scope отделяет working recovery от retired trial; точный replay/revocation/новый secret/exclusion/reconciliation сохраняют прежние гарантии. Это восстановление только TRUST writer, не автоматическое разрешение APP/HTML.

Нельзя просто поднять Operation.count bound16 в нынешнем recovery.state_digest и считать большие списки дешёвыми. В предложение входит потоковая полная сверка **всех** persistent Head/credential metadata/operations с payload+phase receipts/routes/tombstones/recovery/**admission chain**, с прежним безопасным учётом verifier только внутри digest. Она использует bounded cursor/chunk и canonical порядок, не строит в памяти массив всех ORM dictionaries. Applied-policy count/byte пределы проверяются, credential limit20/recovery4 сохранены. Новый digest формат получает явную версию; старое reconciliation proof на нём не принимается. Payload snapshot для выдачи остаётся прежним reader protocol1; успешная сверка по-прежнему не выдаёт HTML admission.

Все физические relations/index/TOAST новой таблицы включаются в accounting;≤32КиБcharged row включает canonical bytes+консервативныйoverhead, не выдаётся за физический page size. Проверки quota и резервов сериализованы с Head; terminal completion/точный replay не отказывают только из-за достижения новых prepare-count ceilings. Неочевидная нехватка места/ошибка транзакции означает rollback/UNKNOWN и сохранение deny, а не успешное удаление.

## Сохранность и границы испытаний

MAIN/архив/ключи/старые receipts не удаляются. Прежний архив60/15360 и evidence остаются отдельным immutable corpus. Новые максимальные наборы создаются только в точной UNIT DB после проверки её принадлежности/пустоты и явной фиксации собственного attempted/evidence; старый calibrationAttempted не сбрасывается. Новый сохранённый corpus автоматически не flush/чистится. Если после него потребуются новые unit — сначала отдельная проверенная retention/archive процедура с новым фиксированным именем/подписанной квитанцией и проверкой обоих архивов; обычный test wrapper не должен стирать второй corpus. Это внутри того же volume/2ГиБ, без нового ресурса.

Штатные CAPS1000/4096/1024 должны проверяться тем же runtime validator и сервисной count/byte веткой; test calibration context не может обходить испытываемые лимиты. Там, где нужен искусственный disk/SQL fault, используется только изолированная UNIT fixture с честной отметкой injection, без заполнения реального диска/изменения Windows/падения всего Docker.

Калибровочная авторизация не ссылается на SHA собственного ещё не завершённого отчёта. Только в точной UNIT допустим code-owned test context с отличимой тестовой policy fixture: он обходит лишь отсутствующий финальный activation evidence, сохраняя те же effective caps/DTO/auth/CAS/квоты/транзакционные проверки. Такая fixture не принимается MAIN/обычной HTTP-активацией и не становится рабочим lease через ENV. Полное чтение corpus по HTTP выполняется при disabled writer. Настоящий MAIN policy создаётся лишь после готового calibration report и независимого review его SHA. Dummy/IN_PROGRESS hash не выдаётся за фактическую калибровку.

Предусмотрен конечный test/review порядок из соседнего плана. Рабочая запись включается только в изолированном TRUST после capacity/code/QA gate и затем проверяется ограниченным native набором; обычный финал — disabled/Stop/сохранённые результаты. Провал любого обязательного блока оставляет профиль закрытым, не увеличивает CPU/RAM/deadline/quota и не превращается в production PASS.
