# DEV07-SH-Q001 — предложение хранения общих HTML-снимков

2026-11-01. DEV-07 около96%, этап8 около20%. **Архитектурное предложение владельцу, не принятое изменение и не включённый профиль квоты.** Текущее поручение D-346 и результаты17тестов shared_content сохраняются. Старый сайт/VPS не затрагиваются.

## Решение, которое предлагается согласовать

Хранить канонические HTML-снимки Header/Footer в закрытых неизменяемых файлах существующего локального тома Docker. В PostgreSQL оставить короткие metadata: ID блока/версии, история, основание, автор/время, относительный server-only file key, длина, SHA256 и связи. Отдельные обычные файлы не исполняются как шаблоны и не выдаются напрямую посетителю.

Это замена первого технического проекта TextField для тела общих блоков, а не перенос страниц/БД/медиатеки на другую технологию. Новый сервис/контейнер/пакет/том/порт не нужен. Конкретная безопасная файловая область предлагается внутри существующего MEDIA_LIBRARY_ROOT/private/shared-content, отдельно от private/sources фотографий и публичных img. Не расширять публичную выдачу файлов. Новые Windows установки/системные настройки, старый сайт и VPS не нужны.

Альтернатива — сохранить всё тело в PostgreSQL и продолжить разработку резерва большого TOAST batch. Текущий безопасный отказ записи тогда остаётся до подтверждения такого профиля. Вариант2048SQL-chunks рассмотрен как иной технический проект, но добавляет длительную content transaction; он не принят и этим предложением не выбирается.

## Зачем меняется первоначальный проект

Одна большая TextField запись может создать сотни внутренних TOAST строк и их индексных вставок. Это усложняет проверяемый предварительный резерв. Приватный файл сохраняет весь HTML до1МиБ без скрытого большого SQL batch; короткие PG metadata дают небольшое фиксированное число записей. Это делает разработку квоты проще, но не доказывает автоматически правильность нового профиля. Верхние границы PG metadata, файлового места, transient growth и crash-accounting всё ещё должны пройти ревью и реальные испытания.

Сохраняются256МиБ общего бюджета,10000 immutable снимков,75% предупреждение, отдельная история двух блоков, один актуальный черновик каждого, owner-only и запрет автоматической очистки истории. Лимит HTML1МиБ не уменьшается. Большие иллюстрации не копируются в HTML-файл; существующие AssetUsage продолжают удерживать свои настоящие файлы.

## Обязательные технические условия будущего контракта

1. File IDs/пути назначает сервер; закрытая схема имён и fan-out каталогов. Никакого пути из HTML/HTTP, symlink traversal, overwrite или повторного использования ID. O_EXCL/O_NOFOLLOW, режим0600, проверка regular/nlink/owner и ограничений размера.
2. Канонические UTF8 bytes пишутся полностью, проверяются SHA/длина; fsync файла и родительского каталога до записи DB pointer. Не публиковать версию, если durable bytes не подтверждены. Отсутствие/подмена/неполный файл — явный отказ, без пустого fallback.
3. Actual quota включает собственные root PG relations/индексы/TOAST/forks, все собственные blob/orphan/journal файлы и каталоги, отдельно проверенный filesystem metadata reserve, held reservations и attributable shared metadata в общей AssetUsage. Длина HTML не выдаётся за всё потребление; WAL/целый диск PostgreSQL относятся к отдельной эксплуатационной границе.
4. До mutation создаётся ограниченная durable reservation в закрытом журнале, с фиксированными типами/максимумом размера и привязкой operation/fingerprint/block/profile. Резерв остаётся видимым scanner после crash/rollback. Повтор не бронирует его дважды. Частично/неизвестно записанный журнал закрывает приём, а не трактуется как0байт.
5. Content transaction повторяет session/owner/generation/base/Asset проверки, проверяет достаточность удержанного резерва при свежих размерах и атомарно фиксирует metadata/refs/receipt/current. Между фазами другой writer не должен израсходовать тот же reserve. Предварительный расчёт учитывает каждый скрытый identity INSERT и все indexes/forks малого PG batch.
6. После успешного commit оставшийся резерв уменьшается только после проверки фактической квитанции/результата и attributable charge. Потерянный ответ/сбой после commit не создаёт вторую версию. Unknown outcome оставляет консервативный резерв; никакого TTL release без доказанного результата.
7. Orphans после ошибки остаются учтёнными. Удаление только явно собственных подтверждённых объектов с повторной проверкой всех current/history/draft/stage/pin зависимостей. Текущая/удержанная версия не теряет файл. Автоматическую очистку истории этим предложением не разрешаем.
8. Backup/restore должны включать DB pointers, файлы и journal из одного проверяемого поколения. Будущие DEV-22/23 получают явный manifest/проверку SHA; нельзя назвать backup одного PostgreSQL полным восстановлением shared. Текущих внешних backup-сервисов не подключаем.
9. Новая migration не удаляет прежние HTML без проверенного переноса и SHA. Если существующих shared revision/draft ещё нет, это проверяется явно; при неожиданном содержимом — отказ, а не усечение/очистка. Исходный0001 не переписывается после применения.

## Что будет разрешать ответ владельца

Подготовить и локально проверить этот вариант: точная схема/FS accounting/резерв, новая migration, адаптация shared commands/read/UI и реальные положительные Draft/Apply/restore вместе с отказами. Не включать профиль, пока измерения и независимое ревью не подтвердят достаточность границ. Не выдавать само согласование варианта за доказанную безопасность формулы или за разрешение production.

До реализации требуются отдельные исполняемые сценарии: max1МиБ header/footer, exact hash/UTF8/FS guards, count/75%/256МиБ, simultaneous last reserve, failures before/after fsync/DB commit, orphan/held book после rollback/crash, exact/different replay, независимые блоки/старые контакты и сохранность RAM. Реальный Nginx/browser и целевой backup/публичная композиция не заменяются framework seam.
