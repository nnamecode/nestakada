# Архитектура системы — основа для согласования

Версия 0.6, 2026-10-28. **Обновление ранее согласованной основы v0.5 прошло независимое текстовое ревью ARC-05; AR-10–AR-22 закрыты, архитектура утверждена владельцем по D-110.** Версия 0.5 была согласована по D-049 и сохраняется в части страниц, прав, версий, Stable, публикации, удаления и медиа. Обновление учитывает утверждённый BRD v0.28 (D-109), решения D-091–D-108 по логам, входу, мониторингу, резервным копиям и заявкам, политику кэширования D-111 и защитную основу D-112/`docs/security-baseline.md`. Приложение не реализовано, тесты не выполнены. Конкретные версии зависимостей, хостинг и открытые эксплуатационные параметры остаются отдельными решениями перед реализацией/запуском.

## 1. Границы

D-066 добавляет общие редактируемые Header/Footer. Их нужно представить отдельными общими сущностями содержимого с областью действия на сайт и версиями; они видны владельцу в «Основных страницах», но не являются публичными URL. Разметка редактора проходит серверный разрешающий фильтр и не исполняет Django/Python/JavaScript. Публичная композиция использует сохранённые версии общих блоков только для опубликованных страниц; D-052 сохраняет полностью пустой ответ неопубликованной страницы. Подробные права/медиа/конкурентные правки/схема снимка и приёмочные сценарии общих блоков требуют последующей аналитики; поведение страниц не переносить на общие блоки механически.

Уточнение после согласования основы: D-051–D-053 (2026-10-27). Редактор должен поддерживать разрешённые размеры/шрифты/цвета и таблицы с сохранением оформления в версиях; окончательная схема HTML и серверной очистки уточняется в аналитике. Page получает управляемый владельцем флаг публикации. Неопубликованный существующий публичный адрес отдаёт HTTP 200 и пустой белый документ без текста, шаблона сайта или ссылки на закрытый черновик; неизвестные/удалённые адреса этим решением не определены. Исключение из меню сохраняется. Сохранение текста сотрудником не включает флаг публикации и не раскрывает неопубликованную страницу. Снятие публикации или изменение содержимого немедленно меняет валидатор публичного ответа по D-111, поэтому ранее сохранённый браузером HTML не считается актуальным без повторной проверки.

Один Django-проект с PostgreSQL, серверными HTML/CSS-шаблонами и небольшим JS. Админка и будущая публичная часть используют единые данные. Основа Django admin расширяется нужными экранами и общими серверными операциями; стандартная кнопка изменения объекта сама по себе не реализует наши правила версий и полей.

Проектируем сначала админку, затем её дизайн и публичный сайт (D-041). В MVP входит только форма заявки на главной по D-077/D-100/D-108; отдельный обратный звонок, кабинет, чат и Android/API не реализуются. Конкретные версии runtime, дополнительные библиотеки, хостинг и эксплуатационные значения подлежат отдельному согласованию перед реализацией/запуском.

## 2. Ответственность модулей

| Модуль | Ответственность |
|---|---|
| Содержимое | Разделы, страницы, главная, услуги/цены, статьи и контакты; единое дерево |
| Версии | Автоматические сохранения, ручные контрольные варианты, сравнение, восстановление, Stable и очистка |
| Публикация | Текущая публичная версия, закрытые черновики администратора, предпросмотр и меню |
| Доступ | Владелец, сотрудники, назначения страниц и разрешённые текстовые поля |
| Медиа | Файлы, альбомы, контрольные суммы и все ссылки использования |
| События | Категории логов, действия, счётчики, группировка и просмотр |
| Заявки | Приём формы, согласие, рабочая запись, назначение и история ответственного; без Telegram в MVP |
| Уведомления | Агрегированные уведомления логов через исходящую очередь; секреты и транспорт отделены от событий |
| Резервирование | Каталог точек, манифесты, проверки и запрос контролируемого восстановления через внешний исполнитель |
| Настройки/обслуживание | Разрешённые параметры, состояние фоновых операций и интеграций |
| Обзор | Сводка из этих источников; «нет данных» отличается от нуля |

Это границы ответственности внутри одного модульного Django-проекта, а не требование создать независимые микросервисы. Плановые команды и внешние исполнители используют тот же версионируемый код там, где это безопасно, но не исполняются внутри HTTP-запроса.

## 3. Концептуальные данные

- **Page**: постоянный ID, точный публичный URL, тип/родитель, currentRevision. Перемещение в дереве не меняет старый URL автоматически.
- **PageRevision**: новый непереиспользуемый ID, страница, неизменяемое содержимое/payload и версия его схемы, тип автоматический/ручной, серверные время и автор. Действующая страница имеет исходную версию до первой правки сотрудника.
- **RevisionProtection**: связь конкретной версии с Stable, владельцем и реальным временем назначения. Метаданные защиты отделены от неизменяемого содержимого. Название/комментарий/пользовательская дата также не подменяют системный момент создания.
- **AdministrativeDraft**: отдельное рабочее состояние администратора, номер редакции и исходная публичная версия. Сохранение сотрудника не публикует этот объект.
- **Asset и AssetUsage**: файл и ссылки на него из всех сохраняемых версий/черновиков. Фото между версиями не копируются.
- **PageGrant**: пользователь, назначенная страница и разрешённые текстовые поля.
- **AuditEvent**: категория, уровень, стабильный код, однозначный UTC instant, источник, результат, безопасные ссылки на пользователя/объект, request ID и IP только когда он связан с событием; это не полные копии текста. Владелец видит Europe/Moscow, экспорт сохраняет UTC и явные zone/offset представления и не зависит от локальной зоны ОС.
- **LogReadCursor**: для `nesadmin` и категории хранит границу явно отмеченных просмотренными событий. Простое открытие списка её не меняет.
- **NotificationCycle/Outbox**: один агрегированный цикл уведомления категории, состояние доставки и безопасный ключ дедупликации. Тело не содержит секретов, трассировок и персональных данных заявки.
- **LoginThrottle**: нормализованный источник/IP, окно неудачных попыток, срок ограничения и служебные метаданные без глобальной блокировки логина.
- **ServiceRequest**: заявка с серверным временем, обязательными именем/телефоном/доказательством отдельного согласия, необязательными автомобилем/комментарием, рабочим состоянием и текущим ответственным. Точные статусы и сроки хранения определяет аналитика.
- **RequestAssignmentEvent**: история назначения/переназначения заявки владельцем; вначале ответственный — `nesadmin`, сотрудник добавляется позднее.
- **BackupPoint**: дата/время, состав, размер, расположения, манифест, контрольные суммы, состояние проверки и доступность локальной/внешней копии. Секреты и ключи шифрования в эту запись не входят.
- **RestoreRequest**: выбранная точка, инициатор `nesadmin`, два момента подтверждения, состояние внешнего исполнения и безопасный результат. Не является произвольной командой shell и не хранится только внутри восстанавливаемой БД.
- **OperationReceipt**: служебное подтверждение операции для безопасного повтора после потерянного ответа. Ключ ограничен пользователем, объектом и действием; параметры сопоставляются без хранения секретов в журнале.

Точная схема полей/индексов и оформление типов блоков будут проработаны в аналитике. Сериализатор версии не принимает произвольный исполняемый код.

## 4. Каждое сохранение сотрудника

Предлагаемая операция выполняется согласованно средствами транзакций БД:

1. Проверить активную учётную запись, назначение страницы и право на разрешённые поля. Повторная отправка также проверяет действующие права.
2. Заблокировать изменение соответствующей страницы в общем протоколе. Сопоставить ключ операции и ожидаемую текущую редакцию.
3. Взять **текущую публичную версию** и наложить только разрешённый текст. Защищённые URL/SEO/структура/медиа не принимаются от сотрудника. Административный черновик не используется как основа.
4. Проверить актуальность, текущую схему, допустимость текста и связи медиа. Устаревшую редакцию/отозванные права/несовместимость отклонить без изменения сайта; дать понятное сообщение и сравнение.
5. Создать новую обычную автоматическую версию, установить её текущей публичной, создать необходимые ссылки использования, применить очистку истории, записать успешное действие и подтверждение запроса.
6. Зафиксировать всё вместе. Если запись новой версии не удалась, публичное содержимое остаётся прежним; успех не показывается.

Повтор одного подтверждённого запроса с теми же параметрами возвращает его результат без новой версии и повторного переключения сайта. С тем же ключом и другими параметрами — отказ. Срок хранения подтверждений и поведение после его окончания требуют фиксации до реализации; бессрочная гарантия не обещается.

Административный черновик остаётся закрытым, но после новой публичной правки его база устаревает. Последующая публикация администратором требует сверки, чтобы не стереть изменения сотрудника.

## 5. История, восстановление и Stable

Сотрудник видит все варианты назначенной страницы, включая ручные и Stable с цветной текстовой меткой. Восстанавливает только разрешённый текст по текущим правам и схеме. Предлагаемый интерфейс сначала показывает допустимые изменения; явное сохранение создаёт новую текущую версию. Просмотр/выбор версии сам по себе сайт не меняет. Источник восстановления не перезаписывается; URL не переносится из снимка.

Максимум **10 обычных версий на страницу**, включая текущую, если она обычная. Ручной обычный снимок тоже входит в десятку. Все Stable находятся сверх лимита. После назначения Stable число обычных может стать меньше 10; восполнять его искусственно не нужно.

При успешном сохранении система удаляет самые старые подходящие обычные версии сверх лимита. Текущая версия исключается из кандидатов удаления, но включается в подсчёт, если обычная. Stable не участвуют в обычной очистке. Уникальные ID не переиспользуются.

Только владелец может просмотреть/сравнить конкретную версию и отметить Stable. Метка не меняет содержимое и не публикует выбранную версию. Следующая правка обычная и метку не наследует. Отдельное снятие Stable не согласовано; автоматического снятия или доступной сотруднику операции нет.

Назначение Stable, сохранение и очистка используют совместимую блокировку страницы и проверку актуального состояния: ранее зафиксированная защита исключает удаление; если обычная версия уже выбыла, назначение возвращает понятный отказ. При восстановлении источник может выбыть после создания результата по общему лимиту. Журнал хранит его ID/краткие метаданные без обязательной связи, удерживающей всю историю; недоступное содержимое не показывается как существующее.

## 6. Удаление страницы — подтверждённое исключение

D-047/D-048: владелец может намеренно удалить страницу **со всеми версиями, включая Stable**. Сотруднику это запрещено. Защита Stable от обычной очистки и отдельного удаления версии сохраняется.

Предлагаемый экран подтверждения показывает название, точный URL, количество версий/Stable и предупреждение, что история этой страницы тоже удаляется. Основная явная кнопка «Удалить страницу и все версии», рядом «Отмена». Простое открытие экрана или GET-запрос ничего не удаляет.

Подтверждение связано с ID и актуальным состоянием страницы/истории. Если между просмотром и применением появились новые версии, новая Stable или изменилось родительство, показать обновлённое подтверждение. При применении снова проверить полномочия владельца и актуальность, согласовать блокировки страницы и затрагиваемых связей.

Удалить записи защиты только внутри этой специальной операции, затем версии, черновики, назначения и страницу с её публичными навигационными связями. Весь результат целиком фиксируется либо откатывается. Отдельного общего обхода Stable для удаления версии не создавать. Аудит/receipt сохраняют безопасные ID/метаданные, а не strong FK на удалённое содержимое.

Повтор запроса удаления возвращает прежний результат и не затрагивает новую страницу, созданную с тем же URL. Если у страницы есть дочерние страницы, не выполнять неявный каскад. Политика удаления раздела/поддерева требует отдельного согласования; до него такие операции отклоняются с объяснением. После удаления страницы её бывший URL не обслуживается этой страницей; поведение адреса согласуется в плане запуска/удаления с учётом рекламы.

## 7. Файлы и общие изображения

Замена фотографии создаёт новый Asset, старые версии продолжают ссылаться на прежний. Все сохраняемые версии, Stable и черновики удерживают используемые файлы. Удаление одной страницы не удаляет файл, используемый другим потребителем.

Создание ссылок и подготовка удаления согласуют блокировки Asset для любых страниц в одном порядке. Файл сначала получает состояние удаления после проверки отсутствия ссылок; новые ссылки на такой объект запрещены. Физическая очистка выполняется отдельно после фиксации и повторной проверки использования, с наблюдаемым результатом/ошибкой. До реализации зафиксировать общий порядок блокировок пользователя/назначений/дерева/Page/Asset и проверить гонки.

214 оригиналов галереи переносятся без изменения байтов, SHA-256 проверены. Архив media/source-site — исходный материал, не автоматически публикуемая медиатека. Разработка и крупные данные на T:, будущий сервер проектируется отдельно. Полные копии БД/медиа нужны независимо от Stable: её прикладная защита не защищает от физической потери хранилища.

Новые загрузки принимаются только как разрешённые растровые изображения: прокси и приложение ограничивают тело, число файлов, байты и пиксели; сервер проверяет расширение/MIME/декодирование, безопасно перекодирует изображение, назначает своё имя и не исполняет медиа. SVG/HTML не принимаются без нового решения. `MEDIA_ROOT`, статика и код разделены. Побайтная старая галерея D-024 остаётся проверяемым исключением; полный протокол определён ARC-SEC-003.

## 8. Публичные страницы и права

Публичная часть получает только currentRevision и допустимую опубликованную структуру. Новые опубликованные разделы/страницы автоматически включаются в соответствующее меню. Черновики, история и предпросмотры закрыты от обычного посетителя даже при знании адреса; сотрудник читает всю историю только назначенной страницы.

Правила скрытого родителя и снятия с публикации зафиксировать до реализации. Нельзя автоматически менять старые точные URL из-за нового дизайна или перемещения страницы. Текущие публичные фото остаются публичными, хотя те же файлы используются закрытыми версиями.

В MVP нет общего серверного/прокси-кэша готового HTML. Анонимные публичные `GET/HEAD` возвращают `ETag` и при возможности `Last-Modified`; браузер обязан перепроверить ресурс (`Cache-Control: no-cache`) и получает `304 Not Modified`, если состав страницы не изменился. Валидатор строится из стабильных версий текущей страницы, Header/Footer, навигации, шаблона приложения и влияющих динамических блоков. Успешное сохранение/публикация меняет соответствующую версию в той же согласованной операции, поэтому следующий запрос не получает старый HTML по TTL.

Статические CSS/JS/шрифты и неизменяемые изображения получают версионированные/content-hash имена и долгий публичный кэш. Для ресурсов, чей прежний путь необходимо сохранить, используются валидаторы или версия ссылки без изменения URL страницы. Админка, вход, предпросмотр, история, заявки, логи, бэкапы, подтверждения опасных операций и любые ответы с персональными данными помечаются `private, no-store`; POST не кэшируется. Полный HTML-кэш можно добавить только отдельным решением после измерений, для анонимных безопасных ответов с версионным ключом и доказанной инвалидцией; Redis заранее не требуется.

## 9. Заявки

Публичный POST формы проходит CSRF/ограничение частоты, серверную нормализацию и валидацию. Согласие фиксируется отдельно от политики: версия текста согласия, серверное время и необходимые технические доказательства связываются с заявкой. До утверждения правового процесса реальные данные не собираются. Тела заявок, телефон и комментарий не попадают в обычные логи, Telegram или URL.

Создание заявки и доказательства согласия фиксируются одной транзакцией. Повтор после потерянного ответа использует ограниченный ключ идемпотентности и не создаёт незаметный дубль; точное окно и пользовательское сообщение определяются в аналитике. Успех показывается только после подтверждённой записи. Недоступность необязательных интеграций не должна препятствовать сохранению заявки.

В MVP заявки видит `nesadmin`; позднее он создаёт сотрудника и назначает/переназначает ответственного. Назначение проверяет активность и роль сотрудника, записывает историю и не раскрывает ему другие заявки. Удаление/анонимизация, сроки хранения, экспорт и рабочие статусы требуют отдельной аналитики и юридического решения. Telegram для заявок отсутствует по D-108.

## 10. Логи и уведомления

Утверждены девять категорий D-102: «Вход и доступ», «Безопасность», «Действия пользователей», «Ошибки сайта», «Страницы и ссылки», «Обновления и окружение», «Резервирование и обслуживание», «Производительность и внешние связи», «Другие / служебные». Версии и публикация относятся к действиям пользователей; важные 404 — к страницам и ссылкам; заявка не является логом.

Массовые известные сканы обрабатываются по D-114/D-115 и `docs/scanner-defense.md`: ранний middleware до сессии/БД возвращает короткий 404, а повтор не создаёт отдельную строку AuditEvent или Telegram-сообщение. Обычные публичные 200/304, успешная статика/медиа и health-check не дублируются в прикладной журнал. Неожиданный 2xx на запрещённом пути, отказ фильтра, реальная ошибка и значимое административное действие остаются индивидуальными событиями.

Структурированные события записываются в PostgreSQL. Файловый слой использует ротируемые неизменяемые сегменты, каждый из которых относится ровно к одной из девяти категорий; низкоуровневые сообщения процесса/веб-сервера нормализуются в подходящую категорию, а не смешиваются в общем удаляемом файле. Манифест сегментов хранит категорию, период, число записей, размер и контрольную сумму. Это позволяет честно считать и удалять файлы выбранной категории. Единый request ID связывает источники без копирования персональных данных. Недоступность источника показывается как неполнота, а не как ноль; полный аудит при отказе всех хранилищ не обещается.

`nesadmin` видит отдельные списки, количество и вычисляемый общий размер категории. Повторы могут группироваться для показа, но сохраняют реальное количество и первую/последнюю даты. Кнопка «Отметить просмотренными» атомарно продвигает LogReadCursor до текущей границы; новые события после неё остаются новыми. Открытие списка ничего не отмечает.

Плановая очистка удаляет события старше 30 суток и соответствующие истёкшие категорийные сегменты. Ручное удаление категории требует актуального подтверждения категории, количества и размера; действие аудируется в другой защищённой категории/внешнем техническом журнале и не позволяет удалить само доказательство незаметно. Размер маркируется как точный либо оценочный в зависимости от доступности манифеста; общий размер категории складывается из структурированных записей и её файловых сегментов без двойного счёта.

Суммарный жёсткий предел управляемой проектом папки файловых журналов — 1 ГиБ с включёнными активными/сжатыми журнальными сегментами, журнальным манифестом и временной ротацией. Архивы резервных точек, дампы БД и медиа всегда хранятся отдельно и в этот предел не входят; в журналах остаются лишь короткие события о ходе резервирования. Фиксированных лимитов по категориям/подпапкам нет: админка показывает размер, долю общего объёма и скорость роста каждой категории. При 80% создаётся одно предупреждение, при 95% прекращается подробная запись известного шума и раньше 30 суток удаляются самые старые низкоприоритетные детали независимо от категории; важные структурированные события продолжают жить в PostgreSQL. Внешние журналы провайдера/прокси вне этой папки требуют отдельной квоты администратора и не включаются в обещанный размер.

Первое новое событие категории, подходящее под явный стабильный код уведомления, создаёт AuditEvent, NotificationCycle и Outbox одной транзакцией; reconciliation-проход находит редкие рассогласования внешних файлов и БД. До утверждения списка кодов на аналитике базовый вариант не исключает молча ни одну из девяти категорий. Отдельный исполнитель отправляет одно агрегированное сообщение в администраторский Telegram; новые повторы не создают поток. Ошибка доставки не откатывает событие, использует дедупликацию и ограниченный exponential backoff, а после лимита переводит запись в наблюдаемое `failed/dead-letter`. События самого Telegram-транспорта не открывают новый цикл в том же канале и агрегируются отдельно, поэтому рекурсивный шторм невозможен. Новый цикл возможен после явной отметки просмотра и нового события. Токен и `chat_id` хранятся вне Git/БД содержимого и не выводятся в логах.

Для известных успешно заблокированных сканов код уведомления отсутствует: они только меняют агрегат. Отдельный incident cycle открывают новый/неожиданный класс, пороговый всплеск, неожиданный 2xx, успешный вход после серии атак, отказ защиты/ротации или пороги заполнения 80%/95%; восстановление ниже 75% даёт не более одного сообщения. Колебание порога и новые повторы не создают новый поток до cooldown/закрытия цикла.

## 11. Ограничение входа и граница IP

Приложение считает подтверждённые неуспешные аутентификации атомарно по источнику/IP: пять за десять минут ограничивают этот источник на пятнадцать минут. Любой логин, включая `nesadmin`, обрабатывается одинаково; глобальной блокировки имени пользователя нет. Внешний ответ и время обработки для неизвестного логина, неверного пароля и ограниченного источника не должны раскрывать существование аккаунта. Успешный вход очищает счётчик источника. Заблокированные повторы группируются в журнале.

Клиентский IP принимается только от явно настроенного доверенного обратного прокси; произвольные `X-Forwarded-For` от клиента игнорируются. Для высокой частоты запросов обратный прокси применяет грубое ограничение до Django и до создания новых LoginThrottle, но бизнес-порог D-103 и его аудит остаются на уровне приложения. На обычной нагрузке отдельный Redis не требуется: небольшое состояние хранится в PostgreSQL с атомарным обновлением, TTL/индексом, плановой очисткой и контролем максимального роста. При достижении защитного предела система деградирует в более строгое прокси-ограничение, а не создаёт неограниченные строки по случайным IP. Решение пересматривается только по измерениям.

Административная сессия истекает после 30 минут бездействия и не живёт более 12 часов. Смена/локальный сброс пароля, подозрение на компрометацию и восстановление инвалидируют прежние сессии; отключённый сотрудник теряет доступ на следующем серверном запросе. Удаление страницы со всей историей и запуск восстановления дополнительно требуют повторного ввода пароля `nesadmin`. Обычная утрата пароля решается только локальной интерактивной management-командой без передачи секрета в аргументах/логах и без публичного email/MFA/CAPTCHA.

## 12. Резервирование и восстановление

Плановая внешняя задача, а не HTTP-процесс Django, ежедневно создаёт согласованную точку восстановления. В **резервном объектном пуле** неизменяемые медиа хранятся как content-addressed объекты; это не меняет утверждённые публичные пути `/img/...`. Каждая точка получает **полный манифест восстанавливаемого состояния**, даже если передаются только новые/изменённые объекты. Физический объект удаляется лишь когда на него не ссылается ни одна из семи точек. Проверка реконструирует полный набор по манифесту, а не только сверяет последний инкремент.

Backup epoch связывает согласованный снимок PostgreSQL с полным манифестом медиа. Неизменяемость Asset позволяет построить манифест файлов, на которые ссылается снимок, без смешения разных моментов; новые мутации после границы относятся к следующей точке. В манифест также входят commit/image digest приложения, версия схемы и список применённых миграций. Набор шифруется до отправки, получает контрольные суммы и загружается на Яндекс Диск. После проверки новой точки выполняется ротация: семь ежедневных точек снаружи и две последние проверенные локально; старейшая не удаляется до успешной полной реконструкции новой.

Авторитетный подписанный каталог и манифесты находятся рядом с резервными наборами вне основной PostgreSQL; BackupPoint в БД является отображаемым кешем. Ключ расшифрования хранится отдельно и от рабочего сервера, и от Яндекс Диска в выбранном защищённом хранилище/офлайн-копии владельца. Возможность получить ключ после потери сервера проверяется при тестовом восстановлении; точный инструмент выбирается до установки.

Админка читает кеш внешнего каталога BackupPoint и показывает дату/время отсечения, состав, размер, расположение и результат проверки. Она не получает ключ шифрования и не строит произвольные команды. Выбор восстановления показывает классы данных, которые откатятся или могут быть потеряны после отсечения: заявки/согласия, пользователи/права, версии, логи, отметки просмотра и throttle. Затем требуется отдельное предупреждение и повторное подтверждение `nesadmin` с актуальной сессией; одна ошибка сайта никогда не запускает откат автоматически.

Подтверждение превращается в одноразовую подписанную команду, ограниченную конкретной точкой, инициатором, nonce и коротким сроком действия. Команда и её статус хранятся вне заменяемой БД. Ограниченный внешний исполнитель переводит сайт в обслуживание и прекращает новые записи. Если текущее хранилище читается, он **обязательно** создаёт предвосстановительную safety-копию и отдельный экспорт новых заявок/согласий после выбранного отсечения. Если физическая потеря или повреждение делает это технически невозможным, исполнитель фиксирует причину и неизбежный диапазон потерь во внешнем аудите и требует отдельного усиленного подтверждения `nesadmin`; только после него допускается восстановление проверенной точки. Затем исполнитель проверяет подпись/манифест, совместимость версии приложения и схемы, восстанавливает БД и медиа как согласованный комплект, применяет миграционные/целостностные и smoke-проверки и только затем открывает сайт.

До отката исполнитель классифицирует подтверждённую причину восстановления. Только для несекьюрити-сбоя (например, физическая потеря диска или подтверждённая ошибочная миграция) и при читаемой текущей БД он может сохранить в краткоживущем зашифрованном safety-наборе актуальное состояние идентичности владельца: ID/логин `nesadmin`, флаги активности/персонала/владельца и текущий password hash, но не исходный пароль. После восстановления этот набор применяется только к владельцу, все прежние сессии/CSRF-состояния инвалидируются, а остальные сотрудники временно отключаются до сверки `nesadmin`; внешние секреты не откатываются.

При подозрении на компрометацию или неизвестной причине текущие hash/флаги не переносятся. Документированная локальная management-команда из панели хостинга создаёт/активирует `nesadmin` и обязательно выполняет интерактивный break-glass сброс пароля без email/MFA и без записи пароля в аргументы, логи или бэкап; остальные сотрудники остаются отключёнными, а внешние секреты/токены ротируются до открытия административного доступа. Тот же break-glass путь используется, если безопасное состояние владельца получить или применить невозможно.

Актуальный предвосстановительный список пользователей/прав и результат операции сохраняются во внешнем защищённом аудите. Новые заявки могут быть повторно перенесены только отдельной проверенной процедурой с защитой от дублей, не автоматически. Ошибка оставляет наблюдаемый внешний статус и доступную safety-копию, а не выдаётся за успех. Если Django/БД недоступны, `nesadmin` запускает ту же процедуру через панель хостинга/техническую команду.

Полный дамп содержит персональные данные заявок и доказательства согласия, поэтому копии шифруются и доступ ограничивается. Обычная политика — семь ежедневных точек и удаление вышедшей из ротации после успешной проверки новой. Если новая точка не создана/не проверена, последняя исправная временно сохраняется сверх обычного семидневного срока, а система создаёт событие и уведомление вместо опасного удаления единственной рабочей копии. Это исключение и обращение с ПД закрепляются в LEGAL-01 до реального сбора данных. Удаление/анонимизация заявки создаёт внешний защищённый tombstone по стабильному идентификатору без исходного тела; после восстановления актуальные tombstone применяются повторно, чтобы удалённые данные не воскресли из копии.

## 13. Внешний мониторинг и фоновые операции

Наблюдатель работает вне сайта и его сервера, проверяет согласованный публичный адрес и отправляет в администраторский Telegram уведомления о подтверждённой недоступности и последующем восстановлении. Частота и число подтверждений выбираются после хостинга, чтобы избежать ложных тревог. Его секреты независимы от приложения и не хранятся в Git.

Очистка логов/throttle, резервирование, физическая очистка медиа и отправка Outbox выполняются плановыми командами/отдельным рабочим процессом с блокировкой от параллельного дубля, ограниченным временем, повторяемостью и журналируемым результатом. Для MVP не вводится тяжёлая очередь задач без доказанной необходимости; конкретный планировщик зависит от хостинга.

## 14. Размещение, безопасность среды и отказоустойчивость

Базовая топология: доверенный обратный прокси/HTTPS → Django-приложение → PostgreSQL; статические файлы отдаются отдельно, пользовательские медиа хранятся вне контейнера приложения. Плановый исполнитель имеет отдельные минимальные полномочия; внешний монитор и Яндекс Диск находятся за границей сервера. Секреты поставляются окружением/хранилищем секретов, не через Git и не через редактируемые настройки админки.

Продакшен следует ARC-SEC-001–008 из `docs/security-baseline.md`: `DEBUG=False`, строгие Host/proxy/HTTPS/cookie/CSRF-настройки, production WSGI/ASGI, CSP и защитные заголовки, ограничения запросов и ресурсов, фиксированные проверяемые зависимости, отдельные минимальные учётные записи компонентов и закрытая от интернета PostgreSQL. До выпуска обязательны тесты, проверка секретов/уязвимых зависимостей и `manage.py check --deploy` с фактическими production-настройками. CSP сначала проходит report-only; HSTS вводится только после проверки HTTPS/прокси. Никакая из этих мер не добавляет MFA, CAPTCHA или email-подтверждение.

Отказ Telegram не останавливает сайт и сохраняет Outbox для контролируемого повтора. Отказ Яндекс Диска не удаляет последнюю проверенную внешнюю/локальную точку и создаёт событие. Отказ БД делает динамические операции недоступными, но внешний монитор и технические файлы остаются отдельными источниками. Заполненный диск, неуспешная очистка, повреждённый манифест и устаревшая копия показываются как ошибки, а не как успешное обслуживание.

## 15. Инварианты и проверки

- Успешный Save сотрудника меняет только разрешённый публичный текст и создаёт новую версию; ошибка не даёт частичного результата.
- Ни сохранение, ни восстановление не публикуют защищённый административный черновик и не меняют URL.
- Параллельная/повторная отправка не затирает незамеченные изменения и не создаёт неявный дубль.
- Обычных версий не больше 10 с учётом текущей; Stable сверх лимита и не наследуется новой правкой.
- Stable защищена от очистки и отдельного удаления; только явное актуальное подтверждение владельца удаления всей страницы удаляет её вместе со всей историей.
- При удалении страницы общие файлы других страниц/версий сохраняются; удаление поддерева не происходит неявно.
- Сотрудник видит все версии назначенной страницы; обычный посетитель ни одной исторической.
- При группировке логов сохраняется корректная новизна, неполнота источника не маскируется нулём.
- Пять неудачных входов ограничивают только источник/IP; знание логина `nesadmin` не позволяет глобально отключить аккаунт.
- Заявка и доказательство согласия создаются согласованно; её персональные данные не попадают в Telegram и обычные журналы.
- Telegram-сбой не откатывает событие и не создаёт поток повторных сообщений.
- Новая резервная точка не вытесняет старую до успешной проверки; восстановление не начинается без двухэтапного подтверждения `nesadmin`.
- Веб-приложение не получает произвольное выполнение команд восстановления и не является единственным путём аварийного восстановления.
- Каждая резервная точка реконструируется по полному манифесту; дамп, медиа, версия приложения и схема относятся к одному backup epoch.
- Каталог, команда/статус восстановления и ключ расшифрования не зависят только от восстанавливаемой БД или потерянного сервера.
- После отката старые сессии недействительны, сотрудники повторно проверяются, а удалённые персональные данные не воскресают вопреки внешним tombstone.
