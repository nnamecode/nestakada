## Явное соответствие canary принятой структуре — SH-REV-001

Синтетический ввод прежнего acceptance `<header><p>CANARY</p></header>` не является разрешённой новой schema header-v1. Новый binding извлекает единственный простой текст canary из инертно разобранной синтетической команды; неоднозначные/вложенные/исполняемые варианты не преобразуются. Canary помещается в **реальный допустимый текстовый slot** полной безопасной Header-структуры: `header.es-header > div.es-header-contacts > a.es-header-address > span`. Остальные обязательные элементы, READY Assets и trusted menu marker строятся по техническому контракту, а не из произвольного клиентского HTML. Для Footer slot — `footer.es-footer > div.es-footer-left > p`. Это только преобразование старой семантической тестовой команды в конкретный новый полный fixture перед настоящим Check; продуктовый sanitizer не получает исключения для canary или свободного p в Header.

Независимый oracle после Draft/Apply читает **фактически сохранённый canonical snapshot**, а после Apply делает настоящий HTTP GET собственной Page через доверенную публичную композицию. Инертный parser извлекает указанный точный slot из реального response body и сравнивает textContent с исходным canary. Дополнительно проверяются единственность slot, неизменность другого блока/текста Page и отсутствие canary в остальных областях. Нельзя заменить публичный GET ORM-строкой, дописать p вокруг canary в observer, удалить canary, объявить случайное вхождение в script/атрибут положительным результатом или получить expected из результата sanitizer.

**Граница замороженных тестов:** acceptance/shared-block-contracts.spec.js содержит независимый `paragraph()` oracle, требующий p непосредственно в currentHtml и headerHtml. Для допустимого Header выше это несовместимо. Старые файлы не меняются, их Header-экземпляры не объявляются PASS по новому slot oracle; возвращать им вымышленный p/переписанный public HTML запрещено. SH-REV-001 закрывается для **нового явно описанного binding и сценариев SHH ниже** после их реализации/ревью/успеха; совместимость прежнего frozen paragraph binding остаётся отдельным открытым gate до явного пересмотра его контракта. Footer, где p действительно существует, также использует фактический HTML, а не synthetic projection.

Синтетические контакты: Header phone содержит буквальный `+70000000001`/`+70000000002` в strong и соответствующий tel href. Для Footer буквальный контактный canary размещается в разрешённом copyright p только тестовой fixture; это не требование добавить телефон/ссылку в реальный дизайн Footer. При compare/restore проверяются сохранённые буквальные значения без подстановки из текущего global contact registry.

## Общие oracle и свидетельства

Каждый kind проверяется отдельно: Header/Footer не Page, не получают URL/SEO/Stable10 и не переписывают друг друга. OWNER-SECOND — второй независимый сеанс того же nesadmin. S-EDIT имеет настоящее назначение Page, но не получает shared права. Все действия идут через реальные авторизованные UI/HTTP и действительные CSRF/source/base/proof/operation IDs. Fixtures могут подготовить собственную историю/границы; они не выполняют проверяемый Apply прямой записью БД.

До/после читаются actual current/draft/history/schema/Asset references/pins/receipts и соответствующая Page; неизменные снимки сверяются по полному отсортированному ID/schema/payload/reference manifest и фактическим байтам выбранных файлов. Большая история передаётся bounded count+digest по **всем** строкам, без10000HTML в stdout. Явно выбранные current/restore/protected снимки имеют отдельные ID/hash-свидетельства. Session/audit accounting не смешивается с content-state, физический PG bloat не маскируется logical digest.

Публичный oracle — реальный GET с актуальными двумя блоками и Page; conditional GET после Apply должен вернуть200/новый ETag. Исторический read показывает сохранённый payload/schema как безопасные данные. Trusted live menu в historical display обозначается отдельно: он не выдаётся за точную историческую навигацию. Настоящий renderer trace наблюдает вызовы выбранного компонента без подмены результата; unsupported schema не вызывается даже при поддельном Apply.

## Квота: реальный PostgreSQL и точные границы

Единый бюджет двух блоков:256МиБ=268435456B,10000 immutable snapshots включая current; drafts занимают bytes, но не притворяются immutable snapshot. Единственный draft каждого kind сохраняется при отказе. Предупреждение при измеренной занятости не менее201326592B не блокирует допустимую запись. Нельзя автоматически удалять историю/Stable/пины/файлы для освобождения места.

Перед product write требуется independently reviewed fixed relation inventory/accounting и проверенный conservative prospective reservation для **той же операции**. Actual PG measurement включает heap/index/TOAST/forks и явно назначенные shared metadata/refs/transient расходы без double count. Пользовательский count/usedBytes/название таблицы не являются измерением. Неизвестный профиль, неверное измерение или недостаточная reservation приводят к отказу, а не разрешению записи. Ни count cache, ни fake measurement не заменяют independent COUNT/pg_total_relation_size.

Новая универсальная reservation formula не выводится из прежних трёх probe. Если reservation/actual limits не доказаны, product Apply остаётся закрытым; подготовленный тест не является разрешением скрытно расширить ресурсы или SQL права.

## Ввод остаётся у владельца

SHH-005/006 и SHQ-001/003 наблюдают настоящий открытый owner editor: до запроса native fill полного разрешённого fixture, после отказа — точное значение прежнего поля/документа, без навигации и автоматического повтора. Canary отсутствует в URL/localStorage/sessionStorage; password/CSRF/proof/HTML не выводятся в отчёт. Framework/state digest не заменяет эту браузерную проверку. Recovery требует отдельного ручного Check/Apply; silent retry после quota/conflict/fault запрещён.

## Gate к коду и отчёту

Технический контракт должен зафиксировать marker/Asset resolver/menu handling, source/draft/stage binding, schema compatibility, SQL relations/indexes/locks, accounting/reservation и конкретные проверяемые paths/codes. Затем независимое ревью точных fixtures/adapters и тестов; root выполняет serial прогоны на immutable snapshot. Отчёт по каждому ID различает фактический PASS/FAIL/не исполнено и вид свидетельства service/framework/realHTTP/nativeUI/physicalPG.
