# Разбор применимости advisory базовых образов

2026-10-30. Технический разбор исходного снимка D-312/D-313 по поручению устранить остаток безопасности. Это не независимое ревью собственного исправления и не принятие риска владельцем. Аналитик не запускал Docker, не устанавливал пакеты и не менял образы. Исправления и проверки после них выполняет координатор; фактическое состояние после исправления необходимо сверять с его новым инвентарём.

## Вывод для текущей подготовки

Исходные **190 совпадений image/source/advisory** сводятся к **118 уникальным advisory ID (114 CVE и 4 TEMP)**. Файл [base-image-advisory-triage.csv](base-image-advisory-triage.csv) сохраняет каждую запись с постоянным ID, условием применимости и требуемым действием. Отсутствие эксплойта в пробе не является доказательством отсутствия уязвимости.

Требуется новое сопоставление фактически установленных source versions. Исправление Alpine-пакетов Nginx не закрывает Debian- или bundled-native запись.

## BASE-PAM-001: CVE-2025-8941

Условие — выполнение `pam_namespace` с контролируемыми пользователем путями и локальными файловыми гонками. Debian оставляет `undetermined` и указывает возможную специфику неполного исправления Red Hat. Это не подтверждение уязвимости Debian и не статус исправления. [Первичный tracker](https://security-tracker.debian.org/tracker/CVE-2025-8941).

В исходных Python/PG-образах PAM-пакеты установлены. Сохранённый `dev-pg-hba.conf` использует SCRAM для host-подключений, не PAM; тестовые процессы не реализуют вход пользователей ОС. Поэтому подтверждённый путь PostgreSQL-аутентификации не вызывает описанный PAM-механизм. Вывод ограничен этим путём. Появление PAM-login/интерактивного входа/произвольных процессов требует нового разбора. Без vendor fix или точной проверки source исправление пакета не заявляется. Удаление PAM-пакетов без анализа зависимостей не рекомендуется.

## BASE-ZLIB-001: CVE-2026-85091

В исходном инвентаре — upstream `really1.3.1` (binary `1:1.3.dfsg+really1.3.1-1+b1`). Описание CVE ограничивает уязвимый механизм более поздним nonblocking gzip writer; Debian при этом помечает trixie vulnerable. [Tracker](https://security-tracker.debian.org/tracker/CVE-2026-85091) и [вводящий механизм upstream commit](https://github.com/madler/zlib/commit/81cc0bebedd935daeb81b0b6e475d8786b51af3d) показывают основание для проверки диапазона, а не для автоматического подавления записи.

[Upstream discussion](https://github.com/madler/zlib/issues/1310) содержит стороннее исследование диапазона. На первом проходе оно не заменяло собственного чтения исходника; последующая узкая проверка ниже выполнена уже непосредственно по официальным source-файлам. Позиция Debian по записи остаётся отдельной от нашей технической оценки. Не нужно заменять стабильную zlib пакетом из sid только ради совпадения с номером fixed_version.

### Уточнение BASE-ZLIB-001: собственная проверка исходного пути

По отдельному поручению координатора получены в памяти официальные файлы upstream tag v1.3.1 и Debian source **1:1.3.dfsg+really1.3.1-1**, без исполнения, установки, Docker и записи исходников на диск. Все пять файлов побайтно совпали. [Debian gzwrite.c](https://sources.debian.org/src/zlib/1%3A1.3.dfsg%2Breally1.3.1-1/gzwrite.c/), [upstream gzwrite.c](https://raw.githubusercontent.com/madler/zlib/v1.3.1/gzwrite.c).

| Файл | SHA256 одинакового upstream/Debian содержимого |
|---|---|
| gzguts.h | `716fa648aca1bb06c219d7b97ad4846d8479206143bc39557bfd8283f5783e04` |
| gzlib.c | `042c2be8ec67ad525a2812e508de7381c6766dde903acf5ae6ac4fa6b541946d` |
| gzread.c | `72e481aca07b0b85a9783237b85dc67ff3a4c1d19878d0cec69f58d38634867b` |
| gzwrite.c | `469b1e58932ea11bdda2a153f6655f7b3c13254240fae157181b49ed1bc93b47` |
| zlib.h | `8a5579af72ea4f427ff00a4150f0ccb3fc5c1e4379f726e101133b1ab9fc600c` |

В [Debian patches API](https://sources.debian.org/api/src/zlib/1%3A1.3.dfsg%2Breally1.3.1-1/debian/patches/) найден один файл series размером 0; его [реальное содержимое](https://sources.debian.org/data/main/z/zlib/1%3A1.3.dfsg%2Breally1.3.1-1/debian/patches/series) также пусто. Неприменимость не выведена из одного номера версии.

Проверены обе ветви записи и стандартная/старая varargs-реализации printf. В старом gz_comp отрицательный write, включая EAGAIN/EWOULDBLOCK, устанавливает Z_ERRNO и немедленно возвращает ошибку. gzvprintf после отказа gz_comp возвращается до последующего memmove; следующие публичные write/printf-вызовы отвергают сохраняющуюся ошибку. В этих файлах нет gz_vacate или state->again.

Во [вводящем commit 81cc0be](https://github.com/madler/zlib/commit/81cc0bebedd935daeb81b0b6e475d8786b51af3d) появляются retry-состояние, новый gz_vacate, разрешение повторного вызова после write stall и очистка ошибки при повторе. [Fix df84af2](https://github.com/madler/zlib/commit/df84af25dc1942490e1d1c899a07619152a46148) сбрасывает оставшийся input state при ошибочном выходе именно нового gz_write-пути.

**Технический вывод:** описанный CVE автоматический nonblocking retry/stale-input путь отсутствует в проверенном exact source. Это основание для ограниченного `source-path-absent`, а не утверждение, что Debian изменил vendor status или что zlib вообще не имеет других дефектов. Внешний явный вызов gzclearerr меняет состояние ошибки и не покрывается доказательством о последовательности без такого сброса; отдельные способы использования старого API не объявляются безопасными. Для финального статуса конкретного runtime надо связать фактически загруженный libz с этим source/binary-пакетом. GPG-проверка source index и воспроизводимая компиляция здесь не выполнялись; передавались байты с официальных HTTPS origin.

## BASE-XML-001: libxml2, 10 записей

Исходный PG-образ содержит libxml2 `2.12.7+dfsg+really2.9.14-2.1+deb13u3`. В его полном dpkg-инвентаре нет `python3-libxml2`; Python-образ вообще не содержит пакет libxml2. PostgreSQL поддерживает XML-процессинг при сборке с libxml; сама архитектура SQL может достигать библиотеки, даже если сайт не имеет XML-страницы. [Документация PostgreSQL](https://www.postgresql.org/docs/18/functions-xml.html).

Для остальных восьми использован сохранённый полный Debian JSON snapshot с отдельными CVE URL; ссылка на upstream patch в tracker не выдаётся за лично прочитанный diff.

Практический приоритет — совместимое stable-исправление или проверенная сборка библиотеки с backports и сохранением происхождения/ABI, затем проверки PostgreSQL, ролей и XML. Нельзя удалить libxml2 из динамически связанного PG-образа и считать проблему решённой. Отзыв EXECUTE у нескольких XML-функций не доказывает блокировку всех casts/XMLPARSE/input функций. Сетевое `internal` ограничивает внешний выход, но не предотвращает локальный DoS/повреждение памяти в процессе PG. Эти девять записей не закрываются одной конфигурацией сети.

## BASE-NATIVE-001: Python, PostgreSQL и psycopg-binary

CPython 3.14 находится в bugfix-поддержке с плановым EOL 2030-10; [3.14.10](https://www.python.org/downloads/release/python-31410/) — текущий проверенный security-релиз с исправлениями CA/tarfile/cookies. Это не аудит всех системных библиотек Python-образа. [Политика веток](https://devguide.python.org/versions/).

PostgreSQL 18.6 — поддерживаемый minor ветки 18 до 14.11.2030. Он включает исправления, перечисленные в [актуальной таблице PG security](https://www.postgresql.org/support/security/); поддерживаемый сервер не означает автоматически исправленную libxml2/libssl. [Политика версий](https://www.postgresql.org/support/versioning/).

В зафиксированном psycopg-binary 3.3.6 реально измерены libpq 18.6 и OpenSSL 3.5.8; имена 15 библиотек сохранены в `evidence/bundled-native-versions.json`. У остальных файлов версия по имени/hash не доказана. SHA256 wheel и пустая PyPI advisory metadata не заменяют native audit.

**OpenSSL 3.5.8 требует отдельного исправления/оценки:** официальная [таблица 3.5](https://openssl-library.org/news/vulnerabilities-3.5/) описывает сентябрьские исправления в 3.5.9. Часть касается QUIC/DTLS/CMP/SM2; они не тождественны обычному SCRAM TCP-пути. Однако есть и обработка сертификатов (например CVE-2026-35189), поэтому production TLS нельзя считать закрытым по отсутствию QUIC. Локальная проба не включала TLS; это лишь ограничение проверенного пути, не исправленный bundle.

[Psycopg installation](https://www.psycopg.org/psycopg3/docs/basic/install.html) объясняет, что binary-вариант содержит свои библиотеки; apt-обновление образа их не заменяет. Для production upstream предпочитает local/C-сборку, связанную с системными библиотеками. Варианты исправления: новый проверенный wheel, безопасно воспроизведённый binary build либо согласованный переход на `psycopg[c]` той же версии и системные libpq/libssl с отдельным lock/проверкой. Самовольной смены D-311 в этом разборе нет. [Release notes](https://www.psycopg.org/psycopg3/docs/news.html) на момент проверки называют 3.3.6 текущим релизом, 3.3.7 ещё unreleased.

**Не путать upstream version и Debian backport.** Координатор прочитал candidate `libssl3t64=3.5.7-1~deb13u3` в trixie-security. [Debian CVE-2026-35189](https://security-tracker.debian.org/tracker/CVE-2026-35189) прямо относит этот полный номер к исправленному. В сохранённом tracker тот же fixed_version указан для CVE-2026-42772/54872/75805/77696. Строка `OpenSSL 3.5.7` без dpkg revision не позволяет признать системную библиотеку уязвимой: важно происхождение Debian-патчей. И наоборот, этот вывод не распространяется на wheel OpenSSL 3.5.8, не получающий Debian patches. После C/system-варианта нужно подтвердить фактически загруженную shared library, полный package version и отсутствие импортированного binary bundle.

## Кандидат смены PG base: Debian → Alpine

Если координатор проверяет PostgreSQL 18.6 на Alpine для получения исправленной libxml2, это отдельная новая сборка/инвентарь, не закрытие строк текущего Debian snapshot. Сохраняется major/minor PG, но glibc → musl меняет ОС и поведение libc-locale. По [документации PG locale](https://www.postgresql.org/docs/18/locale.html) от provider/locale зависят порядок строк и обработка регистра; одинаковое имя locale не гарантирует одинаковые результаты на разных платформах.

Для эксперимента нужна новая PGDATA и явная запись provider/locale/encoding/версии ICU, проверки русских строк и case mapping. Нельзя молча выбрать codepoint sorting как бизнес-правило. ICU менее зависим от libc, но зависит от своей версии; builtin C.UTF-8/PG_UNICODE_FAST имеет иные правила, чем естественная русская сортировка. Старый том сохраняется, не подключается к другой libc как готовая миграция. Для реальных данных нужен проверенный логический перенос с пересозданием индексов. [REFRESH COLLATION VERSION](https://www.postgresql.org/docs/18/sql-altercollation.html) обновляет метаданные и сам не перестраивает/не проверяет индексы.

## Границы результата

Разобраны исходные 118 advisory, но не все они технически исправлены. CSV явно различает vendor classification, отсутствующий конкретный runtime path, спорный affected range и необходимые исправления. Это не риск-акцепт владельца и не полный security-pass. Для финального результата нужны фактический post-inventory исправленных образов, обновлённое сопоставление advisory и независимое ревью исправлений.

Критерий закрытия адресной записи: точный исправленный пакет/библиотека с происхождением и hash **либо** проверяемое объяснение неприменимости к конкретному артефакту и конфигурации. Неприменимость конкретного пути не переносится на другую сборку/расширение/production. До выпуска повторяются базы advisory, тесты реального приложения, настройки и ограничения production; текущая локальная подготовка не заменяет этот этап.

## Runtime-привязка zlib после D-315

В C-runtime фактически измерены zlib1.3.1 и Debianbinary1:1.3.dfsg+really1.3.1-1+b1. SHA256 загруженного /usr/lib/x86_64-linux-gnu/libz.so.1.3.1:85590dd58edf5445e18bc7193e5ebc01ac5841f1ae187e97705a662e90c6421e. +b1 — binaryrebuild исходной sourceversion1:1.3.dfsg+really1.3.1-1; инвентарь source:Version связывает её с проверенными исходниками. dpkg-V указывает только отсутствующие gzip-файлы документации штатного slimобраза, не изменение библиотечного бинарника. Локальный результат evidence/system-zlib-identity.json. Это привязка исходного анализа конкретного CVE-пути, не патч zlib и не закрытие vendorstatus.
