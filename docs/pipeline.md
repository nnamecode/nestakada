# Процесс полной разработки

Статус на 2026-10-27: инструменты и команда согласованы, BRD уточняется. По D-041 сначала проектируется админка, затем публичная часть. Приложения и действующего CI ещё нет.

D-075: владелец принял текущий макет админки как основу и разрешил движение дальше. Подготовлены предварительные публичные направления по уже принятым требованиям; это не утверждение BRD целиком и не переход к реализации. Открытые вопросы BRD/эксплуатации остаются явными и должны закрываться на соответствующих воротах перед кодом/запуском.

## Этапы и ворота согласования

| Этап | Результат | Проверка и условие перехода |
|---|---|---|
| 1. Инициализация | Git, документы, таблица задач, предложение навыков и ролей, план окружения | Владелец согласовал набор навыков и команду; доступы/окружение отражены честно |
| 2. BRD | Цели бизнеса, пользователи, границы MVP, будущее развитие, критерии успеха, ограничения | Согласование владельцем до дизайна; неизвестные данные помечены вопросами |
| 3. Область админки | Разделы, роли, сценарии, страницы/версии, логи; docs/admin-design-brief.md | Согласовать область админки перед архитектурой, включая границы логов |
| 4. Архитектура | Общая архитектура с приоритетом админки: контент, версии, права, медиа, логи, публикация, безопасность и расширение | Независимое ревью; замечания устранены или приняты владельцем; финальное согласование |
| 4а. Дизайн админки | Несколько направлений интерфейса, прототипы ключевых экранов и состояний | Владелец выбирает и согласует направление админки |
| 4б. Публичный дизайн | Несколько направлений главной на телефоне/компьютере, затем нужные внутренние страницы | После админки; выбор и утверждение владельцем с учётом старых URL и новой компоновки |
| 5. Аналитика | Требования REQ-xxx, страницы и поля, состояния публикации, права, ошибки, SEO, миграция URL и критерии AC-xxx | Независимое ревью и согласование владельцем |
| 6. План реализации | Небольшие задачи с зависимостями, результатами и связями с REQ/AC | Согласование порядка и объёма; оценки не выдаются за гарантии |
| 7. Приёмочные e2e | Исполняемые сценарии по согласованным AC, тестовые данные и матрица браузеров | Ревью тестов до реализации. Первоначальные падения/отсутствие приложения ожидаемы и явно отмечаются |
| 8. Код | Реализация небольшими проверяемыми изменениями, документация запуска | Проверки каждого изменения; основной набор e2e проходит |
| 9. Unit-тесты | Правила, права, валидация, изображения, публикация и граничные случаи | Содержательные unit/integration-тесты проходят; допустимо писать вместе с кодом, итоговая проверка на этом этапе |
| 10. Code review | Независимая проверка корректности, безопасности, совместимости и сопровождения | Исправления, повторные целевые проверки, финальный отчёт владельцу |
| 11. Приёмка и запуск | Предпросмотр/стенд, проверка владельцем, план переноса, резервные копии и откат | Отдельное разрешение на продакшен. Существующий сайт до этого не меняется |

Три направления публичного дизайна и этап запуска — предложения по конкретизации процесса. Приоритет админки изменён владельцем в D-041; этот порядок заменяет прежний переход от BRD сразу к публичной главной. Если при проектировании выявляется ограничение выбранного дизайна, вернуться на точечное согласование, не переписывать утверждённые решения молча.

## Предлагаемый CI после появления приложения

GitHub Actions на push/PR: установка зафиксированных зависимостей → форматирование/линт → системные проверки Django и миграций → unit/integration с PostgreSQL → e2e Chromium/Firefox/WebKit → сборка контейнера → отчёт. Проверка зависимостей и секретов в пределах доступных инструментов. Версии действий фиксировать проверенными commit SHA, давать минимальные permissions.

Эмуляция WebKit не заменяет проверку реального Safari/iPhone. Яндекс Браузер и реальные мобильные устройства проверять отдельно перед приёмкой. Скриншоты и трассы хранить как диагностические артефакты без секретов.

Автодеплой на продакшен не включать. Миграции перед выпуском проверять с резервной копией и понятным планом восстановления.

## Контроль изменений

Связь: бизнес-цель → REQ → AC → задача → тест → изменение/PR → результат ревью. Проверять только релевантное изменение, затем обязательный набор перед слиянием/выпуском. Изменения документов не требуют запуска несуществующего приложения.

## Завершение смены

Обновить задачи и решения → просмотреть diff → исключить секреты и пользовательские данные → выполнить соответствующие проверки → создать осмысленные коммиты → обычный push в согласованный репозиторий → проверить результат → сообщить ветку, commit и незавершённые вопросы. При сетевой ошибке или отсутствии входа явно сообщить, что копия осталась только локально. Не считать Git резервной копией базы и медиа.
