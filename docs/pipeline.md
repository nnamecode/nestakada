## Рабочее разделение реализации

После этапов аналитики, плана и приёмочных e2e-сценариев этап 8 выполняется законченными функциональными областями. Для каждой крупной области можно создавать отдельный чат; мелкие связанные правки остаются в чате своей области.

1. Основа проекта: Django, PostgreSQL, настройки окружения, структура приложений и общих шаблонов.
2. Модели данных и правила: страницы, разделы, пользователи, права, обычные, ручные и Stable-версии.
3. Админка: вход, редактор, публикация, история версий, восстановление, медиа и подтверждённое удаление.
4. Публичная основа: адаптивные общие шаблоны, Header, навигация, Footer и базовые компоненты.
5. Перенос старого сайта: точные URL, структура, тексты и побайтный перенос фотографий галереи по D-023/D-024.
6. Главная и согласованные блоки: утверждённый дизайн, цены, контакты, бренды, отзывы, фотополоса и заявка только после закрытия соответствующих требований и правового процесса.
7. Служебные функции: SEO, обработка изображений вне галереи, диагностика и только отдельно утверждённый объём логов.

Это навигационное разбиение, а не готовый план программирования. Точные задачи, зависимости и критерии приёмки формируются на этапах 5–7. При завершении этапа координатор сообщает владельцу, какой этап завершён, какой идёт следующим и какое согласование требуется для перехода.

Три направления публичного дизайна и этап запуска — предложения по конкретизации процесса. Приоритет админки изменён владельцем в D-041; этот порядок заменяет прежний переход от BRD сразу к публичной главной. Если при проектировании выявляется ограничение выбранного дизайна, вернуться на точечное согласование, не переписывать утверждённые решения молча.

## Предлагаемый CI после появления приложения

GitHub Actions на push/PR: установка зафиксированных зависимостей → форматирование/линт → системные проверки Django и миграций → unit/integration с PostgreSQL → e2e Chromium/Firefox/WebKit → сборка контейнера → отчёт. Проверка зависимостей и секретов в пределах доступных инструментов. Версии действий фиксировать проверенными commit SHA, давать минимальные permissions.

Эмуляция WebKit не заменяет проверку реального Safari/iPhone. Яндекс Браузер и реальные мобильные устройства проверять отдельно перед приёмкой. Скриншоты и трассы хранить как диагностические артефакты без секретов.

Автодеплой на продакшен не включать. Миграции перед выпуском проверять с резервной копией и понятным планом восстановления.

## Контроль изменений

Связь: бизнес-цель → REQ → AC → задача → тест → изменение/PR → результат ревью. Проверять только релевантное изменение, затем обязательный набор перед слиянием/выпуском. Изменения документов не требуют запуска несуществующего приложения.

## Завершение смены

Обновить задачи и решения → просмотреть diff → исключить секреты и пользовательские данные → выполнить соответствующие проверки → создать осмысленные коммиты → обычный push в согласованный репозиторий → проверить результат → сообщить ветку, commit и незавершённые вопросы. При сетевой ошибке или отсутствии входа явно сообщить, что копия осталась только локально. Не считать Git резервной копией базы и медиа.
