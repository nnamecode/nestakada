# Защита от массовых автоматических сканирований

Статус: утверждено владельцем 2026-10-28 по D-114/D-115. Документ задаёт кодовую защиту Django и управляемых проектом журналов. Правила Nginx/CDN/WAF являются дополнительным усилением, а не условием корректности приложения.

## ARC-BOT-CODE-001. Ранний фильтр

До сессии, авторизации, шаблонов и БД middleware возвращает короткий `404`/`no-store` для невозможных в проекте путей: PHP/WordPress/phpMyAdmin, dotfiles и репозитории, резервные/служебные файлы, известные веб-шеллы и обход каталогов. Список строится как ограниченный набор сигнатур и проверяется против полного реестра легитимных URL. Нужные `/.well-known/` исключаются явно. Запрос не перенаправляется на главную и не создаёт индивидуальную запись в PostgreSQL.

## ARC-BOT-CODE-002. Настоящие 404

Публичная страница разрешается только по точному нормализованному опубликованному URL. Неизвестный адрес возвращает лёгкий 404 без тяжёлого общего контекста; catch-all не подменяет его главной с кодом 200. Регистр, повторные/кодированные разделители, query-параметры и старые рекламные URL получают отдельные приёмочные сценарии.

## ARC-BOT-CODE-003. Целевые ограничения

Приложение ограничивает вход, заявку, загрузку, закрытый предпросмотр и дорогие административные POST-операции. Общий поток случайных GET не создаёт строк throttle в PostgreSQL. Для заявки допускается доступное скрытое поле-ловушка без CAPTCHA после отдельной UX/правовой проверки. Искусственные долгие задержки ответа не используются.

## ARC-BOT-CODE-004. Агрегация шума

Распознанный и успешно отклонённый скан не становится отдельным AuditEvent/Telegram-сообщением. Компактный категорийный файловый сегмент может хранить минимальную запись, а админка получает агрегат по сигнатуре и временному окну: реальное/оценочное число, число источников, первый/последний момент и наиболее частые пути. Потеря части приблизительного счётчика при аварии помечается как неполнота и не выдаётся за точный аудит.

Индивидуально сохраняются административные действия, изменения прав, успешные/значимые входы, подтверждённые критические операции, неожиданный 2xx на запрещённом пути и отдельные реальные ошибки. Повтор одной ошибки группируется по fingerprint с первой/последней датой и количеством; полная трассировка сохраняется для первого/диагностически нового экземпляра, а не для каждого повтора.

## ARC-BOT-CODE-005. Неподходящая среда для PHP-атак

Образ не содержит PHP, WordPress или phpMyAdmin; приложение работает не от root, код/секреты находятся вне публичного web root, а доступные для записи каталоги ограничены медиа/временными/журнальными данными. Загруженные файлы не исполняются. PostgreSQL не публикуется наружу.

## ARC-BOT-CODE-006. Проверки

Приёмочные и автоматические тесты подтверждают короткий 404 и отсутствие запросов к БД для известных сигнатур, сохранение всех легитимных URL, безопасное поведение кодированных вариантов, отсутствие раскрытия черновиков/файлов и отсутствие шторма событий/Telegram. Полный HTML-кэш не используется как защита от сканирования; неизвестные URL не кэшируются.

## LOG-CAP-001. Предел управляемой папки

- Суммарный предел управляемой проектом папки файловых журналов — **1 ГиБ = 1 073 741 824 байта**, включая активные, закрытые, сжатые сегменты, манифест и временный файл ротации.
- Каждый сегмент имеет конечный размер; одна нормализованная запись ограничена и не содержит тела запроса/ответа. Закрытые сегменты сжимаются. Писатели используют общий процесс-безопасный протокол ротации и не создают файл на инцидент.
- Фиксированных квот для категорий/подпапок нет: любая категория может использовать свободное место общего лимита. Админка показывает её текущий размер, долю общего объёма и скорость роста за сутки/семь суток, чтобы владелец мог очистить категорию или изменить правила логирования по фактическим данным.
- При 80% создаётся одно предупреждение цикла; при 95% прекращается подробная запись известного шума, удаляются самые старые низкоприоритетные сегменты и сохраняются агрегаты/критические события; после снижения ниже 75% отправляется не более одного сообщения о восстановлении. Колебание порога не создаёт новый цикл без cooldown/закрытия предыдущего. Приоритет очистки не является квотой: сначала удаляется наименее полезная старая детализация независимо от категории.
- Писатель проверяет общий занятый объём до создания/расширения сегмента, учитывает ограниченный размер активного и временного файла и при исчерпании предела отказывается от новой низкоприоритетной детализации, а не превышает 1 ГиБ и не останавливает сайт. Критические структурированные события продолжают записываться в PostgreSQL.
- Жёсткий размер имеет приоритет над 30-дневной детализацией низкоприоритетных файлов. Структурированные важные события в PostgreSQL сохраняют обычную политику 30 суток; шум может потерять детализацию раньше, что явно показывается в админке. Ошибка ротации не должна остановить сайт и сама фиксируется доступным независимым способом.
- Логи провайдера, панели, Nginx/systemd или контейнерного runtime вне проектной папки не входят в этот байтовый предел. Для управляемого нами Docker/runtime задаётся отдельная конечная ротация; абсолютное ограничение чужих каталогов возможно только квотой/настройкой администратора хостинга.
- Дампы PostgreSQL, медиа-манифесты, зашифрованные архивы и другие файлы резервных точек всегда находятся вне папки логов и не учитываются в 1 ГиБ. Их объём контролируется отдельной политикой D-101/D-105/D-107: две последние проверенные точки локально и семь внешних.

## LOG-NOISE-001. Что не записывать подробно

- Нормальные публичные `200/304`, успешную отдачу статики/медиа и успешные health-check — не дублировать в прикладной журнал.
- Известные отклонённые `wp-login.php`, `.env`, `.git`, phpMyAdmin и аналогичные пробы — только компактный сегмент/агрегат, без строки AuditEvent на каждый запрос.
- Повторяющиеся 404 обычных посетителей, CSRF-ошибки и одинаковые исключения — группировать; полезные старые/рекламные URL выделять отдельно.
- Никогда не писать пароли, токены, cookie, Authorization, тела форм/заявок, содержимое загруженных файлов, полные request/response bodies и неочищенные query-параметры.
- В production отключить DEBUG, SQL debug и безусловный дамп заголовков/локальных переменных. Клиентский разрыв соединения и заведомо ожидаемый отказ не повышать до отдельной критической ошибки.

## TG-NOISE-001. Telegram без шторма

Известный успешно заблокированный скан сам по себе не уведомляется. Один цикл уведомления создаётся для нового/неожиданного класса, резкого порогового всплеска, неожиданного 2xx на запрещённом пути, успешного входа после серии атак, отказа защиты/ротации, достижения 80%/95% лимита или подтверждённого критического события. Повторы меняют счётчик существующего инцидента; транспорт Telegram имеет дедупликацию/backoff/dead-letter и не запускает уведомление о собственной ошибке в том же канале.
