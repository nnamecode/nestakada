## Реальный будущий стенд

Профиль `auth-login-isolated-sources` создаёт синтетические OWNER/S-EDIT и три первоначально анонимных контекста LOGIN-A/LOGIN-A2/LOGIN-B. Первые два имеют один фактический адрес источника A, третий — другой B. Пароли находятся только в секретных fixture refs OWNER-CURRENT-SECRET/EMPLOYEE-CURRENT-SECRET/WRONG-SYNTHETIC-SECRET, не в Git/отчётах. Неверный ref действительно не соответствует ни одному аккаунту, актуальные refs проверяются положительными входами.

**Разные browser contexts сами не создают разные IP.** Нужен проверенный собственный изолированный ingress/сетевой стенд, реально соединяющийся с приложением из разных назначенных тестовых источников. Если один локальный origin требует маршрутизации contexts через тестовый ingress, она готовится только в контуре стенда и должна быть независимо доказана по фактическим соединениям/событиям limiter, а не по имени роли или входному пользовательскому заголовку/cookie. Одно HTTP-имя сервера не является доказательством разных источников. Нельзя дописывать x-forwarded-for в произвольный запрос и объявлять IP подлинным. Глобальная production-конфигурация proxy/trusted hops этим набором не выбирается и не проверяется. Без реального ingress/независимой проверки binding сценарии не получают pass.

Существующий UI/HTTP-драйвер не расширяется: `submit-login-direct` — настоящий POST штатного входа с действительными CSRF/логином и значением passwordRef из секретной fixture; accepted требует фактического результата, не HTTP200. Каждый успешный вход дополнительно подтверждается настоящим закрытым `read-authenticated-identity-direct` из того же контекста: реальный текущий userId и синтетический приватный canary выбранного пользователя. Анонимный/отклонённый вход не получает эти canaries. `logout-auth-session` — явный штатный защищённый выход; закрытое чтение после него отвергается.

`auth-fixture-identifiers` возвращает фактические ownerUserId/employeeUserId/sourceAIp/sourceBIp. `auth-source-state({actor})` читает реальные записи текущего собственного limiter/аудита и коррелированный ingress-запрос: sourceIp, lastRequestId, failedCount, blockedUntilUtc|null, nowUtc, observedFrom=actual-ingress-and-limiter. Метка не доказывает источник сама; конкретное подключение проверяется независимо. lastRequestId связывается с реально выполненным запросом из указанного context; read-only probe не увеличивает/не очищает число неудачных входов. failedCount — фактический счётчик выбранного backend, не вычисленный наблюдателем ожидаемый ответ; после успеха наблюдается реально очищенное состояние. Таймстемпы нормализуются из реального хранилища, а nowUtc — из собственного контролируемого серверного источника времени.

Для `seed=four-failures-aged` fixture создаёт **начальные** четыре реальные записи/состояние limiter источникаA, все возраста ageSeconds относительно frozen server now, без действующей блокировки. Для `seed=five-failures-blocked` — начальное ограничение источникаA, начавшееся ageSeconds назад и заканчивающееся через900секунд после начала. Это подготовка начальных данных в выбранной реальной схеме, не запуск ожидаемого результата проверяемого POST и не реализация лимитера в адаптере. Порог5 и полная длительность отдельно проверяются пятью настоящими неудачными запросами на свежей fixture. Тестовый now фиксирован во время отдельных последовательностей; реальный Windows/VPS clock не меняется. Чтение/настройка выбранного backend/источника часов ещё требуют независимого ревью после разрешения реализации.

Наблюдения `auth-fixture-identifiers`/`auth-source-state` используют actual-db/actual-http существующего транспорта. Они не подменяют действия прямым изменением БД; живые пользователи/адреса/пароли не используются. Секреты/тела входа/cookie не выдаются в наблюдениях. Физические IP/тестовые session refs не становятся новыми endpoints продукта ради теста.
