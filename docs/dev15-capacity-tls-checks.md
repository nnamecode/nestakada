# DEV-15 — полный TLS-снимок сохранённого набора

2026-11-02, D-380, RP15-011/012/020, продолжение DEV15-CLOSE-02. Временный readonly UNIT API уже входит в согласованный профиль. Это конечные проверки до исполнения, не PASS; продуктовый код/лимиты/образы не меняются. DEV-15 около92%, этап8 около28%.

1. Проверить source30/5fbcb9d9…, положительный B и его подписанную квитанцию; после обычного Start с disabled записью остановить API/ingress. Read-only audit UNIT должен полностью совпасть с B: Head2002/epoch1,1000FINAL/4096адресов/1024tombs, v2SHA116bb54…; MAIN и старый архив отдельно сверяются.
2. Снять исходный ACL точной UNIT/OID32563 и существующего trust_runtime, сохранить baseline и подписанный intent до GRANT. Временно дать CONNECT/USAGE, SELECT только Head/Credential/RoutePolicy/Tombstone, UPDATE(id) только Head для SELECT FOR UPDATE. Изменение id защищено существующими constraint/trigger; UPDATE остальных полей, INSERT/DELETE/MAINTAIN и прочие права запрещены. Новых ролей нет. Проверить настоящее runtime SSL-подключение, rowlock с rollback и permission-denied42501 для UPDATE(mode)/INSERT с rollback. Если минимума недостаточно — восстановить права, не расширять их.
3. Пересоздать тот же API с точной UNIT, trust_runtime, writer disabled и новым runtime UUID; Nginx пересоздать для его адреса. Те же3pinnedimages/internalnetworks/caps896МиБ/1.25CPU, никаких host ports. Дополнительные tool-контейнеры запускаются только при остановленном front.
4. Readiness до измерения — только TLS socket, без HTTP-запросов в rate zone. Один существующий consumer.read_snapshot/HTTPSReader:30с на весь снимок,6с на запрос,54успешных запроса (manifest+52page+head),5120items/wholeSHA5933ad…, точный Head2002. Pacing0.11с между началами запросов соблюдает существующий10rps, включён в общий30с и вычитается из timeout запроса. Нет retries/изменения consumer/Nginx limits/deadline.
5. Зафиксировать peak/event/OOM периода UNIT API до удаления, затем остановить front и восстановить исходные effective ACL. Сравнение canonical aclexplode/default нормализует допустимое NULL→явный owner ACL; raw before/after и их SHA сохраняются, равенство сырых catalog bytes не обещается. Не писать pg_catalog напрямую. Cleanup вооружён до первого GRANT и повторяется из baseline при потере ответа/ошибке.
6. Повторить readonly UNIT/main/archive проверки. Пересоздать API обратно из базовой MAIN-конфигурации, проверить новый container ID, actual current_database/current_user, Head9/epoch2 и disabled. Затем Stop/0running/permit{}; корпус/ключи/предыдущие FAIL и Tests guard сохраняются.

TLS-REV-001 закрывается перед запуском: effective witness включает PostgreSQL18 MAINTAIN и требуетFalse, новых GRANT нет. Синтаксис проверяется с реальным непустым stdin и SHA каждого файла. Предыдущие capacity AST-smokes без --interactive могли разобрать пустой ввод: они не считаются отдельной проверкой тех исходников; фактические A/B и131UNIT результаты остаются независимыми действительными свидетельствами.

Первый фактический preflight остановился до GRANT: SQL22023 «ACL arrays must be one-dimensional» в column ACL witness. Readonly диагностика установила точный запрос: aclexplode(COALESCE(attacl,'{}')); пустой массив недопустим для этой функции. Исправление TLS-REV-003 нормализует явный empty ACL в NULL перед aclexplode, сохраняя default ACL для объектов. Исходный FAIL сохранён как tls-preflight-acl-failure.json; это не попытка самого TLS-чтения и не изменение прав или данных. Перед продолжением — новый source/AST/code gate.

Исправленный ACL preflight фактически прошёл: verify/grant и restore PASS, effective ACL baseline восстановлен. Raw ACL ожидаемо отличается из-за явного owner ACL вместо NULL. Следующий процесс вернул пустые stdout/stderr; контроллер сохранил TLS_HOST_FAILED, но не сохранил exit/error метаданные Docker exec, поэтому причина и факт успешного TLS-чтения не установлены. Стенд остановлен, временные права сняты. Отдельный network-none smoke того же launcher/исходника с пустым ARG вернул ожидаемый JSON отказа настройки: само framing работает, это не объясняет первоначальный исход.

Продолжение допускается только после отдельного code gate исправления наблюдаемости. Единственный Resume использует отдельный каталог resume-001 и подписанный дочерний intent, сверяет исходный FAIL/восстановление прав и родительскую подпись. Не заменяет исходный отчёт или intent. Вывод процесса сохраняется в существующем /tmp API и извлекается до остановки; exit/error/signal и cgroup фиксируются до разбора результата. Программа снимка, её 30 секунд, данные и ресурсы не меняются.

Resume-001 фактически остановился до probe с TLS_SOCKET_NOT_READY; verify/grant/restore PASS, effective и raw ACL восстановлены, Stop0. Прежние исходы не заменяются. Дополнительный network-none file-capture smoke остался inconclusive: контейнер создан, но запуск не подтверждён; незапущенный контейнер удалён по проверенным ID/labels/image, без томов. Это не PASS file-capture или TLS.

Выявлена отдельная startup-несовместимость: точный локальный wheel Django5.2.18/SHA92ed81… безусловно выполняет check_migrations до bind; PostgreSQL introspection видит django_migrations без SELECT, а recorder читает её. Минимальный UNIT grant правильно не выдаёт этот SELECT. Независимое ревью подтвердило исходники, но без старых runtime-логов конкретная причина прежнего empty output остаётся неизвестной.

Один ResumeStartup/resume-002 связан с исходом resume-001 и его подписанным intent. До bind новая UNIT-команда проверяет actual DB/OID/роль/disabled/source, фактически выполняет обычный check_migrations и требует ровно SQL42501 для django_migrations. После этого только UNIT-подкласс той же команды пропускает повторную migration check: точная схема уже сверена host-аудитом до grant. Никаких дополнительных SQL-прав, новых HTTP-серверов, зависимостей или ресурсов. MAIN возвращается к исходной команде без исключения. До HTTP требуется настоящий bind8000 и TLS socket, marker42501 фиксируется из логов API; затем единственный read_snapshot в30с. Readiness теперь сохраняет коды/ошибки всех попыток и при отказе — состояния, память и приватные логи до Stop. Старый FAIL не объявляется успешным задним числом.
