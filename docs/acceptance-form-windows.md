# Форма: приватная связь результата и окна намерения

2026-10-30. Часть TEST-04/этапа7 по D-301–303/D-307/D-308. Источники: analytics-content-detail.md §6 и PR-01 analytics-protocol-contracts.md, существующие AT-030–032/108–112/403–404. Это тестовые действия/утверждения и контракты наблюдений, не код приложения или новый публичный API. Старый сайт/VPS/реальные люди/интеграции не используются.

## Изменение прежних74проверок

`form-contracts.spec.js` сохраняет74экземпляра по home/contacts. Убрано требование `result.requestId`: ни при новом приёме, ни при повторе тест не требует внутренний ID из публичного HTTP/DOM. Поля новой заявки читаются только через отдельные закрытые actual-db наблюдения. Это устраняет известный остаток предыдущего SEO/request-ревью, а не разрешает утечку ID при новом обращении.

`form-intent-records({source,context})` возвращает фактическую приватную связь проверенного подписанного намерения с сохранённым результатом: непустой intentKey, массив уникальных нормализованных requestIds, boolean receiptCommitted. Контекст получен настоящим open-form; наблюдение не получает expected, не вычисляет результат вместо сервера и не публикуется посетителю. Положительный accepted требует именно один Request и подтверждённый receipt. request-by-id читает реальную запись с совпадающим ID/original. Привязки/observer позже должны доказать, что читают настоящий committed result, а не таблицу модели тестового драйвера.

Parallel по-прежнему выполняет два POST через Promise.all, не сериализует их в адаптере. Принятый §6.2п4 допускает фактический accepted либо явный pending/retry до известного результата. Pending — отдельная нормализация наблюдаемого ответа с marker/JSONполем и HTTPстатусом; один200/202/timeout не является доказательством ожидания или успеха. После двух ответов read-only poll ожидает фактическую единственную committed связь в собственной быстрой тестовой fixture, затем выполняется **один явный POST прежнего context/ввода** с accepted и неизменной связью/одной вставкой. Драйвер не повторяет POST тайно и не создаёт новый ключ.8секунд poll — предел тестового ожидания в изолированной fixture, не обещанное время обслуживания/реакции владельца.

Все счётчики до/после проверяются как целые неотрицательные; два undefined не могут пройти noAccepted. Один новый accepted даёт Request+Consent,0–1цель (directHTTP безJS не обязан отправить цель); два явных новых intent дают две записи/согласия,0–2цели. ТГ не получает тело/новое уведомление заявки. Полная доставка Метрики/LEGAL/privacy всех каналов остаётся отдельно.

## Fixture: настоящая выдача до управления временем

`form-preissued-controlled-window({source,tokenAgeSeconds? receiptAgeSeconds?,rotateCsrfAfterIssue?,changeConsentAfterIssue?})`:

1. Изолированный тестовый процесс с управляемыми часами открывает **настоящую** серверную форму через GET под своим VISITOR-контекстом. Сохраняет фактический context/issuedAt. Нельзя forge/подписать ожидаемый токен средствами адаптера или получить новый context уже после старения.
2. Для receipt-варианта ровно через600тестовых секунд выполняет настоящий штатный POST с тем же valid payload; действительно создаются Request/Consent/receipt. Сохраняет фактические acceptedAt и закрытый requestId. Только после этого старит **тот же** принятый результат на86399/86401/60сек по варианту. При token-only результат заранее не создаётся.
3. Для CSRFварианта меняет секрет штатным механизмом изолированного приложения после принятия; старый context остаётся неизменным. Для consentварианта после issue/accept меняет текущую тестовую версию согласия на другую, не переписывает принятую версию/канонический original. Это начальная подготовка, не подмена проверяемого POST записью БД.
4. До теста часы заморожены, поэтому разность actual serverNow/issuedAt/acceptedAt проверяется точно. Меняется только время **тестового процесса**, не Windows/host/VPS. Маски/подписи/куки берутся из реального приложения, не из модели expected.

`prepared-form-window` — закрытое наблюдение фактической подготовки: source/context/issuedAt/acceptedAt?/serverNow/requestId?/issuedConsentVersion/currentConsentVersion/csrfSecretChanged/clockScope/issuedByActualFormGet. Метки происхождения — декларации, не доказательство; реальный bridge и логи локальной выдачи/приёма требуют независимой проверки. requestId не уходит в публичный ответ. Начальный принятый Request доказан существующим с исходным FORM-WINDOW-OWN-INPUT, а не одним флагом receipt.

`refresh-old-intent-csrf({source,context})` — настоящее явное обновление CSRF-защиты для прежнего проверенного подписанного intent. Возвращает действительный context с актуальным CSRF, не создаёт receipt/Request/Consent и не посылает форму автоматически. Не заменять это слиянием ожидаемых полей в драйвере или новым intent. private form-intent-records после повторного POST обязан указать на тот же исходный Request.

R025: перед обновлением CSRF читается непустой закрытый form-intent-records.intentKey, сразу после обновления он должен остаться тем же; совпадения requestId/счётчиков недостаточно. В каждой оконной ветви explicit-new исходный непустой intentKey сравнивается с ключом нового принятого результата и обязан отличаться. Context и случайная CSRFмаска могут меняться целиком, поэтому их буквальное равенство не навязывается. Для ещё не принятого/истёкшего намерения стабильный intentKey должен происходить из реального ранее выданного подписанного контекста/его проверенного внутреннего ID, а не из expected или побочного создания receipt-строки наблюдателем. Само закрытое чтение не создаёт рабочую запись на GET.

R027: `form-consent-evidence({source,context})` — отдельное actual-db чтение настоящего сохранённого синтетического доказательства согласия. Обязательны непустые id/requestId/version и фактическое допустимое время acceptedAt; requestId совпадает с закрытой связью принятого intent. До повторной отправки после смены политики evidence.version равна issuedConsentVersion и отличается от currentConsentVersion; после повтора весь неизменяемый evidence остаётся прежним. В новой вставке через явный актуальный context после отказа старой версии evidence.version обязана быть currentConsentVersion. Это не пересчёт expected из новой политики и не подмена доказательства одним счётчиком Consent. Представление содержит неизменяемые поля фактического доказательства, не меняющиеся timestamp самого чтения/диагностические счётчики. Правовые тексты/личные сведения людей в fixture не используются, LEGAL-01 не закрыт.

`form-storage-counters` измеряет реальное число receiptRows/databaseSessionRows именно изолированного стенда. Независимые наблюдательные запросы не создают сессии/receipt за посетителя. Штатный короткий first-party context/CSRFcookie не считается записью сессии БД и не запрещается этим тестом.

## Транспорт и честный остаток

submit-form-direct/open-form/explicit-new-form-intent/refresh-old-intent-csrf — настоящие согласованные UI/HTTPдействия с текущей сессией/CSRF, не служебные production endpoints. Названия тестовых полей/источников не выбирают реальные URL/ORM. Прямой payload не обрезается/не нормализуется вместо сервера. Отказ/ожидание требуют реального ответа, а не исключения транспорта. Временная fixture не обращается к действующему сайту.

Не подготовлены все окна точного равенства, реальный открытый браузер с сохранённым вводом/историей/JS-off, условные ETag/IMS/HEAD, квоты и переполнение20тыс/16МиБ, ротация подписывающего ключа, реальные потеря ответа/изменение cookie/сеть/транзакционные faults, полный privacy детектор внутренних ID/токенов во всех rawHTTP/URL/логах/ТГ/Метрике/резерве. Из отсутствия публичного требования requestId не следует доказательство отсутствия его утечки. Проверки expired-body содержат согласованное общее сообщение, но не навязывают JSONэхо присланного ввода; сохранение UIввода остаётся отдельной ветвью.

Конкретные bindings/fixture bridge/приложение отсутствуют. Наборы на отсутствующем приложении не запускались; фактические сборка/самопроверки/независимое ревью заносит координатор. Созданы только разрешённые тесты/документ, код сайта/VPS/установки не затрагивались.
