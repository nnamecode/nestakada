# План реализации «Эстакады» — PLAN-01

Версия 0.1, 2026-10-30. **Согласовано владельцем по D-302 после PLAN-02**, этап 6 принят, разрешён этап 7. Аналитика принята по D-301: 63 REQ/140 AC. По последующим D-316/317 разрешена и выполнена ограниченная очередь DEV-02/DEV-28 этапа 8; по D-318 затем выполнена DEV-04, по D-320 — DEV-03; отдельные условия D-310/ENV-05/ARC-10/UX/READY для других модулей и запуска сохраняются. Статусы — tasks.md.

## 1. Порядок для владельца

1. Согласовать этот план. Затем отдельно разрешить этап 7: подготовку и независимую проверку приёмочных тестов.
2. До соответствующих тестов и разработки согласовать конкретные версии инструментов, среду сервера и недостающие экраны. Утверждённую главную заново не проектируем.
3. После тестов и отдельного разрешения на этап 8 создать основу и админку: вход, права, медиа, версии, Stable и управление страницами.
4. Собрать публичные страницы и перенести старые адреса, тексты, цены и фотографии. Затем подключить главную, заявки и согласованные внешние ресурсы.
5. Добавить логи/уведомления, полные копии и ручное восстановление, ночную HTML-копию и независимое аварийное переключение.
6. Проверить всё вместе: права и безопасность, сканы ботов, отказы, восстановление и реальные браузеры. Показать рабочий стенд владельцу. Живой сайт менять только после отдельного разрешения.

Разработка идёт небольшими законченными изменениями. Для каждого: сценарии до кода, реализация, содержательные unit/integration, релевантные e2e и документация результата. Логи и защита закладываются с основы; их полные панели появляются позже. Никаких сроков обязательной реакции владельца этот план не вводит.

## 2. Основания и границы

Нормативная основа — [свод REQ/AC](analytics-spec.md) и перечисленные в нём технические контракты, решения до D-301, защитная основа и утверждённые макеты. Поздние решения имеют приоритет над историческими альтернативами. План не добавляет бизнес-правил и не заменяет аналитику схемами кода.

Независимый отчёт ANA-02 относится к аналитике, не к работоспособности приложения. Архив [манифеста -04](analytics-review-manifest-04.csv) сохраняет состав перед согласованием; последующие изменения статусов/плана не являются новым входом ANA-02. Доказательства исходников не изменяем. Версии библиотек, провайдеры и платные подключения сейчас не выбраны.

Сохраняем Python/Django/PostgreSQL, серверные HTML/CSS и небольшой JavaScript. Точные старые адреса не заменяем редиректами; 214 оригиналов галереи переносим побайтно. Только nesadmin ставит/снимает Stable и управляет паролями сотрудников. Заявки автоматически не удаляем. Удаление раздела не меняет главную; ночная главная со старыми ссылками/ценами допустима по D-300, но собственный удалённый URL не воскресает.

HTML-резерв — две исправные ночные публичные копии, без сообщения посетителю о техническом сбое; форма не выдаёт ложный приём. Это не восстановление БД. Полные копии — отдельно 7 внешних и 2 локальных. Проверка здоровья приложения и БД — 5 минут, два отказа/два успеха каждого контура по PR-03. При неизвестном состоянии защищённый контур прекращает опасную операцию, а не предполагает успех.

## 5. Связь требований, задач и тестов

[implementation-traceability.csv](implementation-traceability.csv) содержит **140 строк — по одной на каждый постоянный AC**, покрывает все **63 REQ**. Постоянные AC остаются ID будущих тестов/ручных протоколов. Исходная формулировка/ожидаемый результат живёт в указанном source_document; CSV не сокращает и не переписывает контракт.

| Колонка | Назначение |
|---|---|
| ac_id / requirement_ids | Исходный AC и все явно связанные REQ; для HTML/OPS/MIG связь конкретизирована по содержанию сценария |
| delivery_task / supporting_tasks | Основной ответственный за результат и другие области, нужные для сквозной проверки; LEGAL-01 — документальный результат, а не код |
| test_design_task | Кто готовит сценарий до приложения в рамках TEST-03–06 |
| verification_tasks | Где фиксируется итог; TEST-08 общий отчёт, TEST-09 отказы/защита/ресурсы, TEST-10 реальные браузеры |
| gate_refs | Связанные READY; момент исполнения задаётся §3, не каждый READY блокирует все работы с данным AC |
| source_document | Нормативный документ AC |

Проверка одного компонента не закрывает сквозной AC до готовности остальных областей. Например, DEV-09 переносит набор данных, DEV-10 добавляет представления галереи; общий сценарий галереи завершается после обоих. Поэтому supporting_tasks обозначают совместный результат, а не неявные обратные зависимости, создающие цикл.

Общий отчёт TEST-08 включает автоматические и документальные/ручные проверки с честным статусом: «пройдено», «не пройдено», «не проверено», с причиной и артефактом. Документальные AC по карте переноса нельзя подменить HTTP-200. Непроверенное обязательное условие блокирует соответствующую приёмку. Результаты TEST-09/10 добавляются до RELEASE-01, не объявляются пройденными в TEST-08 заранее.

## 6. Приёмка изменений и доказательства

- Контент/миграция: все 115 MAP, 115 RTE и 316 MED имеют исход; точный адрес/текст/таблица/медиа проверяются отдельно. Старый вложенный адрес автомойки и новый корневой работают, 17 альбомов/page=2 и 214 SHA сохранены. Источник v3 сам по себе не доказывает полноту.
- Права/сохранение: прямые запрещённые запросы, отзыв прав/сессии, две конкурентные правки, подмена защищённых полей, Stable/ручные снимки/истечение лимита и отказ записи не дают частичного успеха.
- Заявки: форма без JS, потеря ответа/повтор/смена CSRF/согласия/поля/лимит; один результат, без ПД в URL/логах/ТГ/Метрике. После удаления и restore старая заявка не появляется снова.
- Логи: граница удаления категории/новые события/ротация/нехватка места, независимые read cursor/critical/recovery, суммарные квоты и агрегация сканов.
- Резервы/отказы: проверенное восстановление данных в изоляции, доступ к ключам и внешнему порядку; отказы SQL/Django/head/контроллера/TG/диска, отсутствие актуального снимка, дневные hide/delete/301/SEO при ночном HTML; не обращаться к SQL для выдачи аварийной страницы.
- Ресурсы: измеряем целевую среду на согласованных профилях, включая короткие пики сканирования, токены/receipt, HTML/медиа и резервные точки. Миллион запросов в месяц не описывает пиковую нагрузку; производительность не обещаем по среднему.
- Браузеры: восемь принятых семейств и три основные стабильные версии на дату приёмки, реальные Safari/iPhone и мобильные MIUI/Samsung; точные ОС/версии/устройства и недоступные комбинации отмечены по OPS.
- Выпуск: линт/миграции/unit/integration/e2e, независимое ревью, приёмка владельцем и отдельное разрешение на production. Секреты, дампы, ПД и оригиналы фотографий в Git не входят.
