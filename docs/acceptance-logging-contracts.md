## Подготовка и фактические действия

Все имена ниже — внутренние тестовые представления, не выбранные HTTP-endpoints/модели/SQL продукта.

- `nine-category-source-events`: девять известных полезных синтетических исходных событий проходят **настоящий обработчик журналов**, каждое с уникальным ID и набором raw canary. Нельзя напрямую вставить уже очищенную строку БД или изготовить expected в observe. Подготовщик должен доказать исходное событие, реальный путь ingestion и конечные surface. Это проверяет каталог/обработку источника, но не все бизнес-триггеры. В Git нет паролей/токенов/телефонов людей.
- `grouped-user-events-1284`:1284реальных одинаково группируемых полезных события категории, непрочитанные; исходные события не заменяются одной записью с вручную выставленным счётчиком.
- `unread-category-with-open-critical`: полезные непрочитанные события, открытые обычный цикл и подтверждённый critical; baseline recovery-сообщений0. Состояние critical независимо от удаляемого тела. P-LOG-PROBE — настоящая тестовая страница владельца с отличающимся публичным текстом.
- `category-delete-with-shared-segment`: заранее существующие полезные события user_actions и site_errors, фактические файловые байты/маппинг события в общий сегмент. P-LOG-PROBE реально сохраняется через общий `save-text({page,base,text})` и создаёт новое событие; альтернативный fields.text/default-преобразование не требуется. Записи первичного журнала могут быть сгруппированы, но в этом профиле каждому исходному полезному событию соответствует собственный ID; это не требование отдельной строки на каждый скан.
- `scanner-clean-baseline`: реальный изолированный edge/front с разрешёнными легитимными путями и известными сигнатурами, отдельная инструментальная область счётчиков. **До reset** read-only inspectInfrastructureAdmission должен подтвердить ARC-10/isolation/evidence и scanner-observe-v1; отсутствие даёт отказ, не skip. Код самого фильтра/инфраструктура не создаются сейчас.

view-log-category-direct читает настоящее доступное владельцу представление. prepare-log-read-boundary показывает реальную стабильную границу; mark-log-category-read выполняет явную отметку. Перед подготовкой фиксируются непустой исходный unread IDset и прежний cursor; новая граница отличается, после отметки исходные IDs уже прочитаны, а ID последующего настоящего сохранения остаётся новым. Принятый UI prepare-category-log-delete показывает category/boundary/count/bytes и opaque confirmation/operationId; полного списка исходных ID в интерфейсе не требуется. Точный состав читается отдельно через prepared-log-deletion-set(operationId) из настоящего серверного manifest, связывается с показанными category/boundary/count и проверяется существующим в БД/файлах до запроса. confirm-category-log-delete-direct выполняет настоящий POST того же обработчика с изменённым только контекстом роли/валидными защитными токенами для положительных контролей. Прямой GET с теми же допустимыми аргументами не должен изменять состояние. Нельзя выдавать отказ невалидного ID за проверку прав.

Подмена category/boundary — валидные по типу значения другой существующей категории/более поздней границы, а не случайный синтаксический мусор. Актуальное подтверждение обрабатывается приложением, не тестовым мостом. Повторный пароль для удаления категории не навязывается этими тестами: принятый MAN-03 требует подтверждения выбранного состава, отдельные требования пароля restore/удаления страницы не переносятся автоматически на категорию логов.

## Наблюдения

log-category-state возвращает фактические category/readBoundary/visibleEventIds/fileEventIds/activeCriticalIds/notificationCycleId/notificationCycleOpen/unreadCount/physicalBytes. Все ID/границы — непустые нормализованные строки; счётчики — целые неотрицательные. fileEventIds читаются из настоящих оставшихся сегментов, не копируются из БД. Для сохранности site_errors заранее известен непустой protectedOtherCategoryEventIds из log-delete-fixture-identifiers, он должен реально существовать в БД/файлах до и после; два пустых массива не доказывают положительный эффект/сохранность. Физические байты — реальное измерение всей управляемой папки, включая временные файлы; одна конечная проверка ≤1ГиБ **не доказывает пиковую квоту при записи/ротации**.

processed-category-evidence: sourceEventId/category/primaryCategoryCount/dbEventIds, реальные databaseText/fileText/diagnosticText/telegramBodies; sourceAcceptedByRealEventPipeline — декларация, её происхождение подлежит независимому ревью конкретного bridge. synthetic-sensitive-canaries возвращает только синтетические значения тестового источника. Наблюдение не получает expected из теста. Источник каждой категории включает независимый безопасный маркер SAFE-LOG-{category}; он обязателен в реальном UI/БД/файле, пустое тело не проходит. Пустая диагностическая поверхность/отсутствующие ТГ-сообщения не доказывают доставку/полноту всей redaction-политики.

latest-page-save-log-event связывает реально созданное событие с конкретным сохранением P-LOG-PROBE; не «последняя случайная строка». log-delete-operation-evidence читает retained audit за пределами подтверждённого набора и фактический статус операции. Открытие и удаление могут создавать собственный безопасный технический аудит; сравнение не запрещает его и не считает его прочтением/recovery.

scanner-effects измеряет SQL/сессии/AuditEvent/принятые сообщения локального ТГ-sink **самих проб**, отделяя наблюдательные запросы/положительный контроль. Это атрибуция настоящей инструментальной телеметрии, не константы адаптера. aggregateKeys сравнивается с отдельно зафиксированным конечным configuredAggregateKeyLimit из проверенной конфигурации; не подстраивать предел под фактический рост. probe-known-scanner-path отправляет настоящий HTTP GET с выбранным path/query, не подменяет404. cacheControl читается из реального заголовка ответа; HTMLпарсер его не выдумывает. scanner-legitimate-public-response — реальное200с независимым canary.

Конкретные bindings/fixture bridge/обработчики отсутствуют. Тесты не исполнялись против приложения; сборка/самопроверки/целевое ревью записываются координатором отдельно. Полное TEST-07 остаётся открытым.

### Проверка утечки до маскирования отчёта

fixture.logSensitiveCanaries содержит **тот же** непустой синтетический корпус, который читал настоящий обработчик событий и возвращает synthetic-sensitive-canaries.values. Ни expected, ни очищенный вывод не используются для его изготовления. В decode исходный HTTP-ответ проверяется до возврата scrubbed body: JSON проверяется также после декодирования, HTML — инертным DOMParser по исходнику/декодированному тексту/атрибутам. Возвращается только sensitiveCanaryCheck={checkedCount,detected}; сырые секреты не выдаются в этом доказательстве. Каждый LOG-category требует совпадения числа зарегистрированных canary и detected=false. Нулевая регистрация/отсутствующее поле не проходит. Конкретное связывание обеих коллекций и всех surface ещё подлежит независимому ревью bridge, одна метка/число не является доказательством происхождения. В качестве запретных canary выбираются тестовые значения, не нужные в легитимных CSRF-полях самой страницы.

Маскирование известного synthetic password/cookie в отчёте сохраняется, но больше не служит доказательством отсутствия его утечки из UI журнала. Отдельные JSON/HTML самопроверки детектора возвращают только безопасный флаг и не имитируют обработку сайта. Предел128canary/16КиБ — ресурсное ограничение тестового детектора, не бизнес-политика секретов.
