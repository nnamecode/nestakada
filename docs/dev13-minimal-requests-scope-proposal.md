# DEV-13 — минимальные заявки: ограниченное предложение области

Дата: 2026-11-12. Статус: `DEV13-Q001` утверждён владельцем в D-856; идёт независимое scope review, продуктовый код не начат.

Основание: D-593–D-596, `docs/simplification-refactoring-plan.md`, REF-AC-022–026 и REF-AC-030. Это предложение объединяет прежние DEV-13, DEV-14 и DEV-16 в один законченный минимальный инкремент. Оно не разрешает реальные персональные данные, внешнюю отправку, публикацию или production.

## 1. Зачем объединить три задачи

Форма, запись, уведомления, закрытый просмотр и удаление одной заявки образуют один короткий пользовательский маршрут и используют одну модель прав. Отдельные реализации DEV-13/14/16 потребовали бы три раза поднимать одинаковые fixtures, проверять одни и те же права и проводить повторные ревью. Один инкремент уменьшает объём работы, не объединяя несвязанные подсистемы.

## 2. Входит в DEV-13

1. Новое небольшое Django-приложение `service_requests` внутри существующего проекта, без API, фонового worker, очереди, cache и отдельного сервиса.
2. `ServiceRequest` в PostgreSQL:
   - случайный UUID;
   - `created_at` как единственная показываемая дата заявки;
   - обязательные имя, нормализованный телефон `+7` и принятое отдельное согласие; до LEGAL-01 используются только synthetic consent version/evidence, а простой boolean не объявляется окончательно достаточным юридическим доказательством;
   - необязательные автомобиль и комментарий;
   - внутренний уникальный digest намерения отправки для защиты от дубля после потерянного ответа.
3. Не добавляются `status`, `assignee`, `notes`, история обработки, `updated_at`, CRM-события и delivery-outbox.
4. Одинаковая форма на главной и `/contacts`; безопасный идентификатор источника принимает только два заранее известных значения. До LEGAL-01 публичный приём остаётся fail-closed, а проверки используют только синтетические данные и локальный test profile.
5. После успешного commit выполняются две независимые немедленные попытки:
   - plain-text email на один адрес из owner-only настройки в админке;
   - plain-text Telegram в один chat ID из окружения.
   SMTP-параметры/пароль и Telegram bot token/chat ID хранятся только в окружении. Отказ одного канала не мешает другому и не откатывает заявку. Уведомления запускает только обработчик, чья транзакция впервые вставила строку; duplicate/concurrent loser возвращает тот же нейтральный результат и не отправляет их повторно. Повторов, scheduler и outbox нет. Если процесс погиб после commit до попытки, заявка сохранена, но без outbox доставка не гарантируется; этот честный предел не маскируется повторной отправкой.
6. Владелец `nesadmin` и авторизованные сотрудники видят закрытые список и карточку. Сотрудники не изменяют и не удаляют заявки и настройки. Список имеет фиксированную серверную пагинацию по 25 строк и стабильный порядок `created_at DESC, UUID DESC`; неограниченного queryset/HTML, поиска по ПД и экспорта нет. Ответы имеют `private, no-store`; прямые запросы проверяют права на сервере.
7. Только `nesadmin` меняет email получателя и удаляет одну конкретную заявку через POST+CSRF после обычного подтверждения. Повторный пароль, корзина и массовые действия отсутствуют.
8. Перед удалением UUID и время без ПД надёжно и идемпотентно добавляются в маленький внешний append-only deletion ledger. Если запись ledger не удалась, строка БД не удаляется. Подтверждённая delete operation обязана сходиться к удалённому состоянию при повторе после crash: наличие durable ledger при ещё существующей строке позволяет безопасно повторить DB-delete; отсутствие строки вместе с ledger подтверждает уже завершённое удаление. Отказы после durable ledger/до DB commit и после DB commit/до ответа входят в приёмку; конкретный малый протокол и сериализация фиксируются в implementation plan. Ledger используется только проверяемой процедурой restore и не становится общей tombstone-платформой.
9. Существующий аудит получает только ограниченные коды результата: заявка принята, канал уведомления успешен/ошибся, настройка изменена, удаление выполнено/отклонено. Имя, телефон, автомобиль, комментарий, consent text, email назначения, токены, cookies и тела запросов не журналируются.

## 3. Безопасность и устойчивость, которые не сокращаются

- Django ORM/параметризованные запросы; динамический SQL, произвольные sort/filter и поиск по телам заявок не вводятся.
- POST-only, CSRF, allowlist полей, один value на поле, малый body limit, серверные пределы строк и запрет NUL/control characters.
- Серверная нормализация российских телефонов; клиентская маска не считается проверкой.
- Autoescape в HTML; уведомления без HTML/Markdown parse mode; пользовательский текст не становится шаблоном, заголовком письма или адресом назначения.
- Уникальный digest намерения в той же таблице обеспечивает ровно одну строку при безопасном повторе; отдельная receipt-платформа не создаётся.
- Уведомления запускаются только после commit, имеют короткий bounded timeout и не влияют на факт приёма заявки.
- Закрытые страницы не попадают в sitemap, HTML-резерв, публичный cache и аналитику.
- Приложение ограничивает метод, размер и стоимость валидации. Для Nginx локально проверяется только конфигурационный контракт rate limit; реальное включение является обязательным launch gate, а до него public intake остаётся fail-closed. Собственный распределённый rate-limit сервис не создаётся.
- Все отказы показывают нейтральный ответ без SQL, traceback, секретов и содержимого заявки.

## 4. Не входит

- статусы, ответственные, заметки, история обработки и любые CRM-функции;
- редактирование заявки, массовое удаление/экспорт, поиск по ПД;
- Celery/RQ, broker, outbox, retry scheduler, delivery dashboard;
- CAPTCHA, SMS-проверка, email-подтверждение и второй фактор;
- реальные SMTP/Telegram credentials, реальные адресаты и реальные ПД до LEGAL-01 и отдельного разрешения запуска;
- тексты политики/согласия, окончательное доказательство согласия, сроки хранения и окончательный состав внешнего уведомления — это LEGAL-01; текущие consent/payload проверки только synthetic partial/deferred и не закрывают эту зависимость;
- Метрика, рекламные query-параметры, внешняя CRM, чат и клиентский кабинет;
- изменение живого сайта, VPS или production.

## 5. Минимальные приёмочные границы

- `DEV13-AT-001`: валидная синтетическая отправка home/contacts создаёт ровно одну строку с нормализованными полями и `created_at`.
- `DEV13-AT-002`: пропущенные/лишние/повторённые поля, NUL, over-limit и неверный телефон отклоняются без записи и уведомлений.
- `DEV13-AT-003`: server-issued bounded intent, повтор и два конкурентных POST одного намерения дают одну заявку; только впервые вставивший строку обработчик запускает уведомления, loser не отправляет их повторно; ответ не раскрывает внутренний UUID.
- `DEV13-AT-004`: email и Telegram запускаются после commit независимо; отказ каждого/обоих сохраняет заявку и даёт безопасный audit без ПД. Проверка payload до LEGAL-01 использует только synthetic placeholder и является partial относительно REF-AC-023.
- `DEV13-AT-005`: владелец и сотрудник видят список/карточку; anonymous получает отказ; все закрытые ответы `private, no-store`.
- `DEV13-AT-006`: только `nesadmin` меняет email; employee direct POST получает 403, а секреты и Telegram destination отсутствуют в БД/HTML.
- `DEV13-AT-007`: только `nesadmin` удаляет одну заявку POST+CSRF; employee direct POST запрещён; GET и массовый delete отсутствуют.
- `DEV13-AT-008`: отказ deletion ledger блокирует DB-delete; fault после durable ledger/до DB commit и после commit/до ответа безопасно сходится при повторе; restore старого синтетического backup применяет ledger и не воскрешает заявку.
- `DEV13-AT-009`: SQLi/XSS/CSRF/scanner payloads не меняют структуру SQL, не исполняются и не раскрываются в logs/errors.
- `DEV13-AT-010`: public form fail-closed вне явно разрешённого synthetic profile до LEGAL-01; HTML fallback не обещает приём заявки; Nginx rate-limit проверяется локальным config contract и обязательно включается отдельным launch gate.

## 6. Предлагаемый порядок после утверждения

1. Независимое scope review этого документа.
2. Короткий implementation plan с существующими слоями, точными миграциями и связью с REF-AC-022–026/030. LEGAL-зависимые consent/payload части остаются `partial/deferred`, а не объявляются полной заменой до LEGAL-01.
3. Независимое plan review.
4. Отдельное разрешение владельца на реализацию.
5. Tests-first небольшими срезами: model/validation/idempotency → public POST → уведомления → read-only admin/settings → delete ledger → combined security/regression → independent code review.
