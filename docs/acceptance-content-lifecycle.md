# Дерево, доступ и история: дополнительные assertions TEST-03/04

2026-10-30. Файл `acceptance/content-lifecycle.spec.js` содержит **33 параметризованных теста** по согласованным состояниям D-307. Это код тестовых действий/утверждений до приложения, а не код сайта, не реализация бизнес-правил и не завершённые e2e. Адаптер, привязки к фактическим UI/HTTP/fixture и их независимая проверка готовятся отдельно координатором. Сайт, VPS, установки, внешние сервисы и тестовые запуски при подготовке этого поднабора не затрагивались.

## Новые синтетические fixture-профили

Связи с принятыми состояниями D-307 через постоянные AT в interface-states-matrix.csv: UI-S004/005 (сессия), UI-S008/009 (сравнение/восстановление), UI-S010/011 (ручные версии), UI-S014/016/017/018 (дерево/подтверждение), UI-S037/038/058 (сотрудники/пароль). Это **частичные проверки поведения**, не прохождение всех текстов/кнопок/состояний и не визуальная приёмка; полный expected остаётся в утверждённых документах.

Все aliases ниже — тестовые имена, не выбранные URL/ORM/API продукта. Ключи observe являются нормализованным тестовым представлением фактических данных; адаптер не вычисляет expected за приложение.

- `tree-parent-published-child`: P-PARENT и опубликованная P-CHILD; P-OTHER-PARENT существует. Дочерний публичный текст содержит CHILD-PUBLIC-CANARY. Родитель/ребёнок имеют разные непереиспользуемые реальные ID и точные URL. Все защищённые поля определены.
- `tree-two-published-siblings`: P-PARENT с ровно двумя опубликованными детьми и исходным публичным порядком; новая «А новая тестовая» намеренно раньше по алфавиту. Новые `/acceptance/new-a/` и `/acceptance/free-path/` — свободные **синтетические пути fixture**, не новые реальные URL сайта.
- `tree-parent-hidden-child-and-empty-parent`: у P-PARENT есть скрытый ребёнок; отдельный P-EMPTY действительно без детей. Положительный prepare на P-EMPTY доказывает допустимый контекст владельца перед отрицательным prepare родителя.
- `empty-page-delete-confirmation`: P-EMPTY без детей, несколько обычных и Stable-версий, точные name/URL/ID. Начальный состав меньше ordinary-лимита. Late-child/late-named создаются через настоящие действия приложения, а не через фиктивное изменение snapshot. `submit-stale-page-delete` с устаревшим составом должен отказать на проверке актуальности до destructive-стадии.
- `page-url-collision({occupiedBy})`: занятый путь fixture-identifiers.occupiedPath занят Page либо redirect; свободный синтетический путь действительно свободен. Один и тот же корректный name/parent используется для отрицательного и положительного создания.
- `employee-active-old-session`: S-EDIT активен, действующая старая сессия OLD и назначенная P-ASSIGNED с ASSIGNED-PRIVATE-CANARY; OWNER управляет паролем. `OWNER-CURRENT-SECRET` и `NEW-SYNTHETIC-SECRET` — ссылки на генерируемые тестовые секреты, **не сами пароли**; не сериализовать их значения в отчёты/трассы.
- `controlled-session-boundary({kind,ageSeconds})`: реальный серверный механизм сессии использует управляемое время **тестового процесса**, не изменение часов Windows/VPS. Для idle absolute-age безопасно меньше12часов; для absolute idle безопасно меньше30минут. Вкладка уже содержит «Несохранённый допустимый ввод», не localStorage. Время заморожено до проверки, иначе ±1секунда даст гонку. Проверяются1799/1801секунд idle и43199/43201 absolute, без нового правила точного равенства.
- `page-history-restore`: P-ASSIGNED назначена S-EDIT, actual V-OLD содержит HISTORICAL-ALLOWED-TEXT; V-INCOMPATIBLE существует, но несовместима по реальной схеме, а не просто неизвестный ID. Есть непустой другой текущий текст, отдельный draft и несохранённый ввод. Все protected fields различимы от исторического снимка и доступны фактическому observe.
- `employee-assigned-open-and-closed-requests`: R-OPEN — открытая заявка S-EDIT с REQUEST-PRIVATE-CANARY, R-CLOSED — закрытая с историческим назначением S-EDIT. Исходники, время и история заданы. Не использовать клиентов/production данные.
- `manual-version-delete-matrix`: P-ASSIGNED имеет существующие реальные версии V-CURRENT, V-STABLE, V-USED-BASE и V-ELIGIBLE (ordinary, не current/Stable/used). История ниже лимита, shared Asset используется другим сохранённым потребителем. S-EDIT назначен странице, имеет просмотр её истории, но не owner-операции. Положительный prepare/delete владельца использует те же методы/цели/валидные значения; различается только авторизация или подтверждённый HTTP-метод.

## Новые наблюдения

`public-page-response({page})` возвращает фактические status/body; опубликованная P-CHILD читается тем же точным путём, скрытый родитель даёт пустое body без элементов общих блоков. `public-navigation` содержит фактические groups с pageId/alias/childIds в публичном порядке. `tree` — нормализованный полный состав дерева для сравнения неизменности, не HTML с меняющимся CSRF/временем.

`page`/`page-by-id` дополнительно показывают реальные id/name/position/grants/stableIds/headerRevision/footerRevision; отсутствие поля вызывает отказ проверки, не сравнение двух undefined. `employee-auth-state` содержит только непрозрачные credentialRevision/sessionGeneration, **не пароль/хэш**. `shared-asset-state` читает реальное существование Asset. request.assignee/history — нормализованные роли и реальная история, не данные из предполагаемого результата действия.

`compare-page-version` возвращает comparison.proposedText, `prepare-page-version-restore` — preparation и requiresInputReplacementConfirmation; они отражают настоящий экран. stage меняет открытый ввод после подтверждения, но не Page; save-open-editor — отдельное действительное сохранение. safeReasons берутся из реального отказа, а не заранее выбираются адаптером из reason fixture.

`prepare-delete-page` возвращает confirmation с фактическими pageId/url/name/versionIds/stableIds/requiresOwnerPassword. `prepare-delete-version` — confirmation.versionId, привязанный к конкретной версии. Подтверждения остаются opaque для теста и передаются обратно без изготовления в адаптере.

## Новые действия и ограничения bindings

Дерево: set-page-publication, create-page, publish-created-page, rename-page, move-page, reorder-page-siblings, prepare-delete-page, submit-stale-page-delete. Пароли/сессии: read-assigned-page-direct, reset-employee-password, login-with-password-ref, change-own-password-direct, recover-own-password-direct. История: compare-page-version, prepare-page-version-restore, stage-page-version-restore, save-open-editor, revoke-page-grant, prepare-delete-version, delete-version-direct, probe-GET-version-mutation. Сотрудник: disable-employee, enable-employee; используются также существующие view-request-direct, create-named-version, assign-stable.

Прямые запросы исполняются по настоящему маршруту/методу, без клиентской валидации; их поля должны быть валидны и принадлежность объектов доказана fixture/положительными контролями. GET-проба не «отказывает сама»: она делает настоящий GET того обработчика с допустимыми аргументами, после чего observe проверяет отсутствие мутации. Confirmation/operationId для POST повторяются буквально, secret refs разрешаются только в защищённом тестовом контексте.

Подготовка fixture может работать с тестовой БД/временем; проверяемые действия не заменяются записью БД. Локальный адаптер и вывод о реальности приложения ещё должны пройти ревью. Файл не содержит реализации сайта/ORM/тестового сервера, не меняет системные часы и не выполняет удаление Page/restore полной БД/head/fault. После создания координатором bindings необходимы проверка сборки и независимое ревью; автор этого файла тесты не запускал.
