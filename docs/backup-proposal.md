# Резервные копии системы — предложение для согласования

Дата: 2026-10-28. Основания: D-012, D-101, D-105, BACKUP-01. Это политика системного резервирования, а не версии отдельных страниц.

## Что сохранять

- Ежедневный согласованный дамп PostgreSQL.
- Загруженные медиа и необходимые связи/манифесты.
- Несекретное описание версии приложения и схемы БД, нужное для восстановления.
- Секреты резервировать отдельным защищённым способом; не помещать их в Git или обычный незашифрованный архив.

Код и миграции хранятся в Git, но Git не заменяет резервирование базы и медиа. Кеши, временные файлы и обычные журналы не включаются без необходимости.

## Предлагаемая схема

1. На сервере создаётся локальный временный полный дамп БД и снимок/набор изменений медиа. Локальная копия ускоряет восстановление после логической ошибки, но не защищает от поломки диска.
2. Сформированный набор шифруется, получает контрольные суммы и загружается на Яндекс Диск через отдельную учётную конфигурацию/API.
3. После загрузки проверяются наличие, размер и контрольные суммы. Результат записывается в категорию «Резервирование и обслуживание».
4. Хранятся семь ежедневных точек восстановления. Старейшая удаляется только после успешного создания и проверки новой.
5. База из-за небольшого объёма копируется полным дампом ежедневно. Для медиа предлагается передавать только новые/изменённые файлы с манифестом, периодически проверяя полный набор; конкретный инструмент выбирается после оценки хостинга и объёма.

Семь ежедневных точек находятся на Яндекс Диске. Две последние проверенные копии дополнительно остаются на сервере для быстрого доступа; они не заменяют внешние копии при поломке диска/сервера.

## Раздел «Бекапы» в админке

Только `nesadmin` видит список семи точек с датой/временем, составом, размером, местоположением, контрольной суммой и результатом последней проверки. Можно выбрать точку, просмотреть состав и начать контролируемую процедуру восстановления после отдельного предупреждения о перезаписываемых данных.

Раздел админки — удобный интерфейс, но не единственный путь. Если Django или база не запускаются, восстановление выполняется внешней технической командой по той же документированной процедуре.

## Восстановление

Автоматическое восстановление по факту одной критической ошибки не предлагается. Ошибка может быть временной, а автоматический откат способен перезаписать более новые исправные данные или вернуть уже повреждённую/скомпрометированную копию.

При критическом сбое система уведомляет владельца в администраторский Telegram. Владелец устанавливает причину, выбирает проверенную точку, останавливает запись новых данных, лично подтверждает восстановление под `nesadmin`, после чего БД и медиа восстанавливаются по документированной процедуре и проверяются перед открытием сайта. Создание и проверка копий автоматические; решение о полном восстановлении всегда контролируемое. Если админка не запускается, используется внешняя техническая команда.

До запуска выполнить хотя бы одно полное проверочное восстановление в отдельное окружение. После запуска повторять проверку по согласованному расписанию и после существенного изменения схемы резервирования.

## Открытые вопросы

- Измерить длительность технической процедуры при учебном восстановлении. По D-275 срок реакции/действий владельца не задаётся; предложенные 4/24 часа не приняты.
- Доступный объём Яндекс Диска и выбранный отдельный каталог/учётная запись.
- Конкретный инструмент шифрования, инкрементальной передачи и проверки; перед установкой объяснить владельцу варианты и изменения на сервере.
- Спроектировать двухэтапное предупреждение/подтверждение в админке и внешнюю аварийную процедуру по утверждённому D-107.
