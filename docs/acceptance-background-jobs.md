# Дубли и отказы фоновых задач: частичный AT-060

2026-10-30. Этап7 по D-301–D-303/D-305/D-308 и поручению владельца. Основания REQ-060/AC-060, ARC-SEC-006, D-107, действующие правила резервных точек/ночного HTML. Только тесты и контракт контролируемого стенда. Ни приложения/его команд/воркера, ни production-конфигурации здесь нет. Старый сайт/VPS/ОС/данные не меняются.

`acceptance/background-jobs.spec.js`:6экземпляров для backup/html-build. Два сценария повторного запуска одного логического задания с двумя отдельными invocationId и барьером перед фиксацией; четыре сценария отказа записи/завершения собственного работника перед commit. Числа параллелизма между разными задачами/расписание/lease-timeouts не выбираются.

Повтор одной логической команды не создаёт двух подтверждённых результатов и не входит одновременно в её критическую секцию фиксации. Допускается фактическая реализация с отклонением, объединением или безопасным ожиданием дубликата; контроллер подтверждает исполнение попытки запуска, а не обязанность второго worker выполнить работу. Число1 относится к **эффекту одного logicalTaskId**, не глобальному запрету параллельных разных задач. Проверяются обе реально завершённые попытки, один ledger committed effect и фактическая новая head/manifest/байты результата.

При подтверждённом precommit-отказе нет success и committed effect, прежняя проверенная head и все её прочитанные байты сохранены. Текущая БД с более новой sourceEpoch/страницами не откатывается к старой копии; чтение собственной здоровой публичной страницы работает. После снятия fault часы собственного стенда явно переводятся на следующий допустимый тестовый slot, новое явное задание успешно создаёт результат. Это не автоматический retry неоднозначного commit/restore и не требование к реакции владельца.

## Допуск и управление

До reset требуется реальный preflight ARC-10/изолированной инфраструктуры; перед каждой control-командой транспорт повторно получает текущий допуск **background-job-control-v1**. Отдельный controlOrigin/session/run/instance/admission/capability и случайный operationId обязательны; обычного fallback/backup/html-build допуска недостаточно для этого домена.

Fixed test-команды: start-isolated-job-invocation, hold-isolated-job-phase, release-isolated-job-barrier, fail-isolated-job-phase, clear-isolated-job-fault, advance-background-test-time. Это интерфейс тестового контроллера, не команды/endpoint продукта. Он принимает только jobKind backup/html-build, логические задания/worker refs собственного run и фазу before-commit. fault — отказ записи кандидата либо завершение **собственного тестового worker**, не PID/путь/команда от клиента. Изоляция и атомарная проверка допуска до действия ещё требуют доказательства конкретного контроллера; имя/маркер не считаются им.

Освобождение барьера остановленного собственного invocation допускается как очистка тестовой блокировки, не новый запуск. Без старта настоящего worker и наблюдаемой фазы положительная/отрицательная последовательность не проходит. Управление часами меняет только инъецируемый источник собственного стенда, не Windows/VPS/cron. Два slot заданы fixture как допустимые ночные/плановые моменты; новую бизнес-частоту/дневную HTML-пересборку тест не вводит.

## Fixture и фактические наблюдения

`background-job-own-workers({jobKind})` создаёт только собственную минимальную синтетическую среду: действительный источник с JOB-HEALTH-CANARY, прежний good result из более старой sourceEpoch, новый источник для проверяемого задания, два допустимых логических slot. Хранилища backup включая условное external — отдельные локальные зоны; настоящий Яндекс Диск не подключается. Выбор crypto/подписей/размещения/инструмента и физический ARC-10 остаются отдельными.

- background-job-identifiers: исходные logicalTaskId/nextLogicalTaskId/nextEligibleSlotUtc/sourceEpochId. Это не ожидаемый результат операции.
- background-worker-phase: фактический workerInstanceId/invocationId/phase, actualWorkerObserved; при остановке executionStopped/failureObserved/reportedSuccess из реального процесса и состояния задачи, не из отправленного fault-параметра. Остановка не равна автоматическому объявлению неизвестного commit отказом: сценарий ограничен подтверждённой before-commit фазой.
- background-logical-task-state: фактические попытки/settled и неизменяемый committedEffects ledger с effect ID/sourceEpoch/outputHeadId; peakConcurrentCommitSections — максимум реально вошедших работников, не объявленный лимит. Обе попытки должны действительно завершиться/безопасно отказать, не скрывать второй отложенный worker за флагом settled.
- background-published-output: out-of-band фактическая head и все manifest/ciphertext либо manifest/HTML файлы выбранного небольшого результата. Каждый file: уникальные id/role, bytesBase64/size/sha256; тест сам пересчитывает байты/SHA и сравнивает before/after. Одна role=manifest, её SHA проверяется по headManifestSha256 из внешней head/catalog ссылки, не из самого manifest. 256КиБ на файл — ограничение минимальной синтетической fixture, не лимит сайта/архива; отсутствие файла не заменяется пустым массивом.
- background-output-manifest: реальные ссылки manifest на payload artifact ID/SHA и sourceEpoch, **без собственного файла manifest**; самоссылочный hash не требуется. observedFileSha256 — отдельно вычисленный hash фактически прочитанных bytes manifest в envelope наблюдения, не поле внутри документа; он связан с внешней head reference. Нельзя достраивать ссылки из expected inventory. Полнота/crypto/full reconstruction резервных точек проверяются другими наборами и здесь не объявляются пройденными.
- background-source-state: реальные текущие sourceEpoch/pages из собственной SQL, без меняющихся probe timestamps. Fixture гарантирует различие текущей БД и старого good result, чтобы незаметный restore не проходил как совпадение двух одинаковых наборов. Полнота всей БД/правил восстановления этим частичным чтением не доказывается.
- read-job-health-page-direct: настоящий GET собственной синтетической опубликованной страницы, status200/реальный JOB-HEALTH-CANARY; noops-контроллер/fixture echo вместо приложения не разрешены.

Наблюдения actual-db/actual-http и физические чтения выполняются через действующий отдельный подготовщик, никогда не меняют бизнес-состояние за worker. Его метки/ledger сами по себе ещё требуют независимой проверки конкретной привязки.
