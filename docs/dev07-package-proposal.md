Tiptap starter-kit содержит больше расширений, чем разрешённый HTML-профиль: неподходящие code/codeBlock/horizontalRule и другие функции будут отключены, а серверная allowlist остаётся независимой. Изображения/доверенные компоненты связываются собственными закрытыми Asset/node-ID контрактами; обычный произвольный img-src plugin не становится разрешением внешних изображений. HTML-режим и общие блоки проходят тот же серверный контроль. Не нужны AI/Cloud/Collaboration, CDN, регистрация сервиса или API-ключи.

## Что предлагается разрешить

1. Скачать официальные пакеты и их необходимые транзитивные зависимости, зафиксировать полный lock и хеши, изучить лицензии/исходники и известные advisories. Точные прямые версии выше не повышать автоматически. Git/URL-зависимости и lifecycle install scripts не выполнять; платформенный esbuild binary проверить и запускать явно как часть сборки.
2. В уже установленном Docker подготовить временный JS-сборщик с согласованными Node/pnpm из существующего Playwright-образа; отдельные Node/Python в Windows не устанавливать. Предлагаемые границы builder: до 1 ГиБ RAM, 2 CPU. Плановый дисковый бюджет кэша на T: — 2 ГиБ с учётом перед каждой загрузкой/распаковкой и остановкой при невозможности уложиться; это не уже настроенная жёсткая квота Windows. Реализация контроля проходит проверку до использования. Постоянного нового контейнера нет. По окончании измерить фактический bundle/кэш/время; предварительно их размер не объявляется проверенным.
3. Подготовить производный образ приложения от уже принятого Python-образа с пятью Python-пакетами выше. Использовать хешированные готовые wheels без установки компиляторов/системного XML-стека. Нативный nh3 требует проверки ABI/динамических библиотек/известных проблем. Django/Python/PostgreSQL/Nginx и worker не обновлять. Worker остаётся на прежнем проверенном образе; guards должны различать базовый Python, производный app и независимый worker, а не молча менять его основу.
4. В изоляции без БД/секретов и производственных файлов проверить совместимость, фактическое поведение HTML/CSS, запрет активного содержимого, повторную сериализацию, пределы/ресурсы и JS-enabled browser controls. Новый код/образы подключать к локальному приложению лишь после этих проверок и независимого ревью; при открытой блокирующей проблеме кандидат не подключать и не заменять другим без решения владельца.

Разрешение ограничено локальной подготовкой и последующим подключением проверенного состава к DEV-07. Оно не разрешает изменение VPS/старого сайта, публикацию, платные сервисы, добавление новых прямых библиотек или ослабление CSP/лимитов.

## Серверная граница и правила

Парсер сам по себе не даёт права публиковать HTML. Сначала bounded HTML5-дерево и CSS tokens проверяются по TECH-01/текущим правам; опасные элементы/атрибуты/URL/шаблонные конструкции отклоняются целиком. Нормализация обычного Word-ввода показывается человеку до явного принятия. Затем строится закрытое безопасное представление; nh3 используется как дополнительная проверка, а неожиданное изменение уже разрешённого дерева не принимается молча. Нужны проверки повторной сериализации и различий серверного/браузерного разбора.

Сырой HTML не попадает в исполняемый preview DOM. Первоначально только server-approved HTML допускается в визуальную область; опасная вставка/переход из HTML-режима требуют проверки до подстановки. Клиентский редактор не считается санитайзером. Доверенный producer передаёт Snapshot/TextPricePatch в проверенные DEV-05 commit API; права/base/generation/медиа повторно проверяются перед короткой транзакцией. Сохранённое содержимое никогда не компилируется как Django/Python/JavaScript.

Default paste/drag-drop Tiptap не заменяет эту границу: до помещения в визуальный DOM нужны проверенные данные. Проверка node/depth после полного parse сама не доказывает ограниченность CPU/RAM: нужны патологические входы и измерения/контроль выполнения. Если изолированные испытания не подтверждают безопасный ресурсный профиль выбранного парсера, подключение останавливается.

Ввод остаётся только в памяти открытой вкладки; ошибки/конфликт/повторный вход не публикуют его автоматически. Restore сначала заменяет ввод после подтверждения, затем отдельный Save создаёт новую automatic. Header/Footer имеют отдельные owner-only current/draft/history и принятый общий бюджет 256 МиБ/10000 снимков с предупреждением 75%; Page10+Stable на них не переносится.

## Что ещё детализируется до соответствующего кода

Выбор пакетов не разрешает молчаливое расширение HTTP-body или unsafe-inline/unsafe-eval. Транспорт должен доказанно вмещать принятый максимум прайса и текстов без усечения; существующие 11 МиБ сами по себе этого не обеспечивают. Конкретный budget/streaming и безопасная CSP-сериализация разрешённого оформления проходят техническое ревью, а при существенном изменении принятой настройки — отдельное согласование. Пока эти вопросы не решены, соответствующий обработчик не объявляется готовым.

Для прайса стабильная идентичность ячейки — пара rowUUID+columnUUID, не новый бизнес-идентификатор. Общие блоки требуют отдельного учёта реального storage overhead/защищённых зависимостей, проверки отказа и ручного подтверждения очистки. Полные публичная композиция/ETag и главная с прайсами зависят от DEV-08/12/29; их не заменяет fake renderer.

## Альтернативы

- Собственный WYSIWYG и HTML-парсер: меньше внешних пакетов, но существенно больше собственного кода обработки браузерных деревьев/вставки/таблиц и риска ошибок. Не рекомендую для этой задачи.
- Другой готовый редактор: возможен, но потребует отдельного сравнения лицензии, расширений и точного состава. Нельзя молча заменить выбранную библиотеку.
- Пока оставить только существующую закрытую историю DEV-05: ничего нового не устанавливать, DEV-07 не выдавать за реализованный редактор.
