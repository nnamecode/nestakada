# DEV-15 — независимый журнал запретов: техническое предложение

2026-11-02. **Локальный профиль согласован владельцем по DEV15-Q001/D-374 после независимого ревью.** D-373 разрешил предложение, D-307 ранее принял логическую схему. Первоначальные формулировки предложения ниже сохранены; фактическая реализация/проверки — dev15-results.md. Физическое ARC-10/внешнее размещение не закрыты. Старый сайт/VPS не затрагиваются.

## 1. Зачем это нужно

Если владелец удалил страницу или заявку, восстановление вчерашней копии не должно вернуть её посетителям или сотрудникам. Для этого сведения о запрете хранятся отдельно от восстанавливаемого сайта. Здесь `head` — актуальный номер состояния и идентичность этой отдельной службы; `tombstone` — минимальная запись «объект с этим техническим ID удалён», без текста/телефона заявки.

Это не ещё одна копия сайта и не внешний монитор. Служба не хранит HTML, фотографии, тексты заявок, пароли сотрудников или дампы основной БД. На обычное посещение страницы обращения к ней не добавляются. Она нужна при изменении политики публикации/удалении и проверке состояния после запуска/восстановления.

Основания: REQ-002/007/024/037/044/046–050; AC-002/007/024/037/044, AC-HTML-003/009/012, AC-PRO-009/010; PR-04/08, analytics-html-reserve.md §6/11/12, admin-architecture-draft.md §12; принятая fallback-scheme-proposal.md §3/4/6. Главную из-за удаления источника не переделывать — D-300.

## 2. Рекомендация и альтернативы

| Вариант | Оценка |
|---|---|
| **Отдельная закрытая служба с собственной PostgreSQL вне отката сайта** | Рекомендую. Упорядоченная транзакционная запись, ID операций, сравнение поколения и независимое восстановление соответствуют принятой логике D-307. Сначала локально проверяем протокол; реальный внешний ресурс отдельно. |
| Управляемое внешнее транзакционное хранилище с ограниченным API | Возможная альтернатива после проверки CAS/долговечности/идентичности/доступа/стоимости. Совместимость конкретного провайдера сейчас не установлена. |
| Файл/ещё одна БД на том же основном VPS, подпись внутри его бэкапа, Яндекс Диск с ZIP | Не выполняют принятую независимость от общего отката. Это не равноценная дешёвая замена; изменение требования потребовало бы решения владельца. |

**Для ноутбука предлагается модель независимости, не вторая физическая площадка.** TRUST получает отдельный compose project/том/секреты; команды rollback APP/EDGE не имеют права их менять. Поломка ноутбука/Docker-диска затронет обе зоны. По такой модели нельзя закрыть физическое ARC-10, доказать внешний SLA или обещать работу после потери всего VPS.

Провайдер, отдельный сервер/тариф, регион, стоимость, внешние ключи, его собственное резервирование и защита от отката ещё не выбраны. Покупок/регистраций/подключений не предлагается выполнить сейчас. Для продакшена понадобится действительно независимый ресурс; основной существующий VPS сам по себе им не становится.

Нет опубликованных портов, доступа к интернету и подключения к сети старого сайта. DB не подключается к CLIENT; APP не получает пароль TRUST DB. Присоединение локального APP к CLIENT, когда оно потребуется интеграции, отдельно отражается в wrapper/manifest; произвольный контейнер не добавляется автоматически.

TLS на входе с проверкой CA/имени; TLS API→DB с verify-full и SCRAM. Изолированный ingress→API HTTP допустим только внутри закрытой API-сети. CA/серверные ключи новые для TRUST, создаются после разрешения существующими средствами проекта, не меняют Windows trust store. В pinned Nginx SSL module подтверждён прежним read-only nginx-compiled-options.txt; работоспособность нового TLS ещё надо испытать.

API — отдельный минимальный Django settings/URLConf/schema, без сайта, админки, сессий, auth.User и импортов основного estakada.settings/content. Для **локальной проверки** используется имеющийся runserver --noreload за закрытым Nginx. Это не выбранный production-сервер; поддерживаемый HTTP runtime внешней службы и его hardening остаются физическим ARC-10/ENV. Старые сайт/БД/schema/services не меняются при подготовке этого предложения.

## 4. Данные и границы доверия

| Запись | Минимальный состав |
|---|---|
| TrustIdentity/Head | Непереиспользуемая incarnation UUID, протокольная версия, monotonic bigint generation, writer_epoch, режим ACTIVE/FROZEN, контрольная сумма состояния |
| Operation | operationId UUID UNIQUE, машинный principal/epoch, вид, точное основание/затронутые ID и ключи, canonical payload hash, стадии/поколения/результат |
| RoutePolicy | Точный request target, object UUID, назначенное поколение/тип запрета либо подтверждённый redirect target; старое/новое имя не смешиваются |
| RequestTombstone | Непереиспользуемый request UUID, operationId/tombstoneId, поколение/момент фиксации; без тела, имени, телефона, заметок, IP посетителя |

Пути сравниваются побайтно в принятом UTF-8 представлении, включая значимые legacy query; без lowercase/добавления слеша/переписывания рекламы. Существующий предел exact_target2048байт сохраняется. URL сам по себе не идентичность объекта: новый объект на прежнем пути получает новую привязку/поколение и не наследует прежний HTML. Старый tombstone объекта при этом не удаляется.

Технический профиль сообщений: JSON UTF-8 до1МиБ, закрытая schema/типы/поля, максимум256 target keys на операцию. Если **весь** набор входящих redirect/действительно закрытых зависимостей не помещается, отказ до prepare/основного коммита; не обрезать список и не делать половину операции. Это предел предлагаемого локального стенда, не обещание вместимости любого будущего дерева. В head нет произвольных SQL, путей ОС, callback URL, команд, Django/Python/JS и скачивания произвольных внешних адресов.

Предлагаемые машинные роли: writer (prepare/сведения об исходе), reader (head/snapshot/operation status), recovery (fence/reconcile/смена incarnation после отдельной процедуры). Случайные256битные секреты в отдельных файлах, constant-time сравнение; без cookie/login/emails и без ключа в URL. Авторизация/метод/размер проверяются до SQL. Writer не получает recovery-secret; reader не меняет данные. Это служебная аутентификация, не новый второй фактор владельца. Реальные owner-права/подтверждение/пароль проверяет приложение по DEV-29/16; служба не доверяет произвольному actorId из браузера.

**Binding ключа серверный, не поле доверенного клиентского JSON.** TRUST хранит credential-id/principal→role/writer_epoch/ACTIVE-or-REVOKED; API загружает ограниченный набор ключей из собственной защищённой конфигурации. Форма/роль/неверный secret отсекаются до SQL. Для прошедшего раннюю проверку запроса актуальность credential binding повторно проверяется под Head lock: запрос, начавшийся до отзыва, не проскочит после его фиксации. Сырой writer-secret не хранится в БД/receipt/log; TRUST хранит его односторонний verifier и credential-id, а private файл выдаётся конкретному клиенту.

Recovery перед restore отзывает **старый credential**, а не только увеличивает числовое поле epoch; после доказанной reconciliation создаёт новый случайный secret с новым серверным binding. Его доставка/ключи TRUST не восстанавливаются из APP backup. Пока новая конфигурация ключей/отзыв не применены API, активация нового writer не подтверждается; операция остаётся закрытой. Writer и GET head не могут перепривязать credential или выпустить новый. Старый настоящий secret с подставленным свежим epoch отвергается; общий вечный writer-secret для всех поколений запрещён.

## 5. Упорядоченная запись и повтор

В короткой `transaction.atomic()` TRUST блокируется одна Head строка `SELECT FOR UPDATE`, затем затронутые записи в устойчивом порядке. После проверки incarnation/credential binding распознаётся точный ранее записанный phase replay; для **нового перехода** дополнительно проверяются ожидаемое generation, operation hash, отсутствие конфликтующего pending на тех же объектах/ключах и резерв квоты. Изменение состояния, Operation/запрет и новое поколение фиксируются одним коммитом TRUST. `fsync=on`, `synchronous_commit=on`, `full_page_writes=on`; успех отправляется после коммита. Это не общая транзакция с основной БД.

У Operation неизменяемый **prepare_fingerprint** (principal/epoch, вид, объект/основание, полный состав target keys/политик) и отдельные phase fingerprints для report-result. Transport expectedGeneration не входит в semantic fingerprint; это условие новой записи, не способ превратить прежнюю операцию в другую. После auth/incarnation/актуального credential binding сначала распознаётся сохранённый phase replay, только для **нового** перехода проверяется CAS. Поэтому точный retry после потерянного ACK работает и с прежним expectedGeneration, не увеличивая head; отзыв credential по-прежнему запрещает старому writer новую запись.

Prepare с тем же ID/составом возвращает сохранённый prepare receipt и актуальную стадию, без новой строки/поколения; иной prepare_fingerprint —409. Report-result не переиспользует fingerprint prepare: отдельный phase key/строгая schema и fingerprint исхода связывают operationId с типом результата, main DB incarnation/receipt fingerprint и точным итоговым набором политик. Один terminal_fingerprint назначается только один раз. Тайм-аут после COMMIT означает RESULT_UNKNOWN **для клиента**: проверяется тот же ID/phase, не создаётся второе действие. Поколения на wire — десятичные строки, чтобы bigint не потерял точность JavaScript; переполнение запрещено до записи.

| Текущая стадия | Допустимый новый переход | Replay/запрет |
|---|---|---|
| Отсутствует | prepare→PENDING_DENY | До durable prepare report-result запрещён |
| PENDING_DENY | report unknown→MAIN_RESULT_UNKNOWN; подтверждённый main commit→FINAL_RESTRICTION; доказанный main abort→RECONCILE_REQUIRED | Подмена prepare/неполный набор отвергаются |
| MAIN_RESULT_UNKNOWN | Подтверждённый main commit→FINAL_RESTRICTION; доказанный main abort→RECONCILE_REQUIRED | Нет автоматического открытия по времени/отсутствию ответа |
| FINAL_RESTRICTION | Нет смены terminal outcome обычным writer | Тот же terminal fingerprint возвращает сохранённый receipt; другой result/target/receipt→409 |
| RECONCILE_REQUIRED | Только отдельный recovery после актуальной сверки | Обычный writer не снимает запрет и не объявляет main success |

FINAL_RESTRICTION содержит точный HIDDEN/DELETED/REDIRECT состав, но ещё не означает пользовательское завершение/gate ack. Для точного ранее записанного nonterminal replay после финала возвращаются сохранённый phase receipt **и актуальная terminal стадия**, без понижения состояния. Новый/изменённый поздний UNKNOWN поверх terminal —409. Две конкурирующие разные terminal reports не меняют уже зафиксированный исход. RECONCILE_REQUIRED остаётся deny до отдельного доказанного решения; новое публикационное изменение — другая разрешённая операция, не переписывание старого terminal receipt.

Предлагаемые внутренние HTTPS endpoints v1: чтение head/operation status/согласованного snapshot, POST prepare и POST report-result. Никаких публичных product URLs/GET mutations/эндпоинта «очистить все запреты». Результат report-result — **подтверждённая запись TRUST**, а не доказательство полного пользовательского удаления.

Снимок большой истории читается страницами с одним snapshot generation+digest. При изменении поколения во время чтения клиент не принимает смешанные страницы за целый снимок: ограниченно начинает заново либо остаётся закрытым. Snapshot/история закрыты от посетителей; ответы no-store, без произвольных payload/tracebacks в ошибке.

## 6. Связь с основным коммитом и аварийным допуском

| Граница | Действие / честный результат |
|---|---|
| Подготовка | Приложение проверяет owner/основание/состав. До долгого сетевого вызова освобождает контентный lock PR-08. |
| TRUST prepare | Durable PENDING_DENY по всему составу. Потеря ACK выясняется по тому же ID. Нет подтверждённой записи — нет основного коммита. |
| Локальное закрытие gate | Закрываются новые допуски на затронутые ключи; фиксируется ack конкретного gate incarnation/operation/generation. Старый/неотвечающий gate исключается из выдачи либо операция остаётся незавершённой. |
| Основной коммит | После закрытия gate приложение снова проверяет пользователя/права/основание/зависимости под PR-08; пишет изменение и receipt в основной БД одной короткой транзакцией. Сеть не удерживает её блокировку. |
| Фиксация исхода | TRUST хранит фактический FINAL_RESTRICTION с точным HIDDEN/DELETED/REDIRECT составом либо MAIN_RESULT_UNKNOWN. Pending при ошибке сохраняет безопасную недоступность. |
| Пользовательское завершение | Только после сверки результата основной БД, TRUST и реального gate. Отдельный ack head не выдаётся за полный успех удаления. После main commit/без finalize — «Изменение записано, проверка аварийного доступа не завершена»; неизвестный commit — «Результат операции пока не подтверждён». |

Успешный отзыв требует обоих свидетельств: durable TRUST и закрытие **всех** выдающих процессов. Уже допущенный медленный ответ может завершиться; новый после подтверждённой границы не проходит. Нельзя подменить это `on_commit`, асинхронным уведомлением или двумя чтениями файла. Main commit/receipt и настоящий gate — интеграции DEV-29/16/26/27, не существующие готовые функции DEV-15.

**Первый локальный инкремент DEV-15 проверяет службу/клиентский протокол и долговечные записи.** Если реального gate/команды удаления ещё нет, его ack не выдумывается: соответствующий workflow остаётся явно incomplete. Изолированные участники теста проверяют границы протокола, но не доказывают работу отсутствующей аварийной HTML-выдачи. В полной матрице AT037/203/209/409/410 и ARC-10 интеграционные части остаются открыты.

Pending не открывается по TTL/таймеру/откату часов. Отмена с доказанным отсутствием main commit и повторный допуск требуют отдельной reconciliation с актуальной БД/поколением/gate, не команды writer «разрешить всё». D-300 не включает главную в deny set лишь из-за старой публичной ссылки/цены. Ночная сборка тоже не снимает более новый запрет.

Для Request tombstone — сначала его durable запись, затем основное удаление; потерянный ответ не повод выполнить новое удаление. До повторного открытия восстановленных данных актуальные tombstones применяет DEV-23 ко всем связанным payload/заметкам/согласиям по принятому процессу/LEGAL. Один существующий tombstone ещё не доказательство полного восстановления. Обычные пользователи/сотрудники не получают прямого API или списка удалённых request IDs.

## 7. Старт, старый writer и восстановление TRUST

После APP/EDGE restart/restore старое локальное «разрешено» не открывает HTML. Контроллер сверяет актуальную независимую incarnation/generation, main receipt и целостность восстановленных данных; при неполной/недоступной сверке — контактный503. Обычное исправное Django не должно падать от одного отказа gate; новые опасные мутации без подтверждения запрета блокируются.

Writer_epoch — отдельная граница допуска изменений, не просто прочитанное последнее generation. Перед восстановлением APP внешний порядок процедуры отзывает старый writer epoch и исключает старые процессы; новый активируется только после доказанной reconciliation восстановленной БД. Откатившийся клиент не получает право записи одним GET head/подстановкой свежего номера. Recovery-полномочия не лежат в APP backup. Регистрация нового/замена gate также требует исключить прежний активный экземпляр, а не только объявить UUID нового процесса.

При непрерывном проверенном gate публичное чтение использует локальный реестр, без head HTTP/SQL на каждый запрос. Отказ внешней службы не удаляет уже подтверждённые запреты, не создаёт минутный polling БД и не разрешает новый непроверенный набор. После потери непрерывности действует стартовый барьер.

**TRUST нельзя автоматически восстанавливать дампом сайта или заново инициализировать при потере каталога.** В bootstrap новой тестовой среды identity создаётся один раз явной закрытой bootstrap-командой. Ожидаемая incarnation дополнительно закрепляется в TRUST private-конфигурации вне DB volume и APP/EDGE backup; обычный API не создаёт identity по факту пустой БД и не переписывает этот pin. Отсутствие/несовместимость уже зарегистрированной TRUST DB/этого pin означает FROZEN, не пустой permissive head. Подпись/digest не доказывает свежесть откатившейся самой TRUST.

Восстановление самой внешней службы требует независимого от её дампа подтверждения последнего подтверждённого состояния, исключения старых writers/gate и закрытого recovery-порядка. Конкретный внешний источник такого подтверждения/резервирование TRUST пока не выбраны: это **блокер физического ARC-10/подключения**, а не якобы решённая PostgreSQL репликацией задача. Локально проверяем APP/EDGE rollback, при котором TRUST не подвергается откату; не обещаем автоматическое обнаружение произвольного валидного rollback всей TRUST вместе с её ключами.

## 8. Ограничения ресурсов и эксплуатация

Предлагаемые локальные admission:4 активных API-запроса, общий10rps/burst10 без ожидания, короткий429/no-store; Nginx shared zones суммарно1МиБ внутри его128МиБ. Header5с/body10с interread, proxy5с; клиент connect2с/весь request6с. Неожиданный транспортный исход мутации сверяется по operationId. Длительные snapshot/recovery не маскируются бесконечным HTTP: bounded страницы/явное состояние. DB lock_timeout500мс, statement_timeout2с, idle_in_transaction_session_timeout3с, CONN_MAX_AGE0; max_connections16/runtime role connection limit4/shared_buffers64МиБ. Все числа — кандидат для проверки, не ёмкость внешнего сервиса.

Для служебных manifest/operation/tombstone данных предлагается64МиБ логического бюджета и16МиБ отдельного резерва завершения уже принятых операций. Максимумы локального профиля:10тыс operation IDs,10тыс tombstones и50тыс policy references; любой предел может остановить новый prepare раньше. Учёт/резерв под той же Head блокировкой; переполнение не удаляет старые запреты и не считает pending успешным. Prepare резервирует также место для допустимых финальных стадий/receipt, чтобы новая работа не забрала резерв незавершённой.

Эти80МиБ **не равны физическим PostgreSQL байтам**: индексы/страницы/мёртвые tuples/WAL/служебные файлы измеряются отдельно. Первый разрешённый технический шаг — калибровка схемы и худших записей/повторов, физический high-water и запас для fault/recovery в бюджете2ГиБ. До её положительного ревью persistent write profile не разблокируется; если доказать запас не получится, результат — открытый finding/отказ без самовольного расширения. Дисковый hard quota средствами имеющегося Windows Docker не объявляется существующим.

Нет автоматической очистки tombstones/ID операций по возрасту и нет кнопки удаления журнала запретов в админке. Сжатие/выбытие допустимы только по отдельному доказательству, что ни допустимый старый backup/клиент/набор не вернёт удалённое и идемпотентность сохранена. До такого решения заполнение безопасно отклоняет новые опасные действия, обычные чтения сайта продолжаются.

Safe process logs — фиксированный код/результат/operation UUID/поколение без URL, auth headers, payload или исходных exceptions. Инфраструктурные error/access logs не допускают утечек; ограничения шума действуют до SQL. Ограниченный внешний статус failure/pending сохраняется отдельно от main DB; полноценные админка логов/история/Telegram доставляются будущими DEV-17/18/21. Новую публичную диагностику или секрет в readiness URL не добавляем.
