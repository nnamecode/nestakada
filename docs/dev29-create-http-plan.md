# CP29-011: локальная HTTP-проверка создания

2026-11-03, D-408/D-409, дополнение к dev29-create-proposal.md. Код приложения проходит backend-регрессии; этот план и инструменты должны пройти отдельное code/QA-review до HTTP/seed. DEV-29 около 20%, этап 8 около 31%.

Используются прежние UNIT ACL/MAIN snapshot/закрытый journal/APP/Nginx/ресурсы из D-406. Базовый Compose не меняется. Временный override задаёт UNIT и ESTAKADA_DEV29_CREATE=1; оба параметра контролируются по runtime inspect. По умолчанию создание выключено. Публикации/APP↔TRUST нет.

1. Проверить source/code/review SHA, локальный Docker Desktop, ownership и единственный coordinator. Остановить HTTP, снять baseline MAIN и UNIT ACL. Временно выдать прежние ограниченные права runtime только в UNIT. Переключить тот же APP, не добавляя контейнерных служб/ресурсов.
2. Helper сначала подготавливает manifest и затем создаёт прежние 2 synthetic users/6 base Pages/3 routes только на пустом домене UNIT. Прежние UNIT receipt/UUID/audit и прочие модели не сбрасываются ради допуска; MAIN не используется для seed. Обычная очистка истёкшей пустой throttle допускается как в D-406, реальные error/block counters не сбрасывать.
3. До каждого POST создания host сохраняет в private journal точные плановые PageID/name/kind/url. Всего пять extraPages, по одной на каждый согласованный тип. Эти ID известны даже при потерянном ответе; возможное подмножество учитывается при cleanup. Первым готовится также пятый тип для проверки stale-основания, затем тот же UUID проходит явный preview перед успешным созданием.
4. Реальные Nginx формы: GET/POST preview без durable create, CSRF403, hidden create303, exact replay303, stale409 с исходным token/вводом, переход в фактический OwnerDraft, GET editor/state, JSON check→draft, повтор создания с актуальной draftRevision2. После пяти типов employee GET/POST403. Private/no-store/VaryCookie обязательны. Только GET readiness имеет bounded ожидание старта; никакой POST автоматически не повторяется.
5. Независимый CLI подтверждает пять hidden Page, их точные primary, по одной initial revision/current, OwnerDraft revision2 с ожидаемым synthetic текстом и base pin, пять create receipts/аудитов. Публичная выдача и Stable не создаются. Снимки старых UNIT моделей исключают только собственный связанный aggregate; прежние permanent ledgers проверяются отдельно.
6. Перед cleanup запрещены неожиданные Stable/RestoreStage/AssetUsage/чужие pins/routes. Удаляется только собственный synthetic aggregate: pins→draft→current→метаданные→версии→routes→Pages; затем прежняя base fixture. Минимальные operation receipts/UUID/audit остаются. Это внутренний test helper, не реализация пользовательского удаления и не разрешение удалить реальные версии/Stable.
7. После остановки HTTP cleanup выполняется через тот же освобождённый APP-слот. ACL возвращаются даже при ошибке cleanup; свои init helpers отслеживаются по полным CID и завершаются до следующих ACL-действий. MAIN fingerprint/права/роли/последовательности и source сверяются. При незавершённости журнал блокирует обычный Start/UnitTests. Конец — override отключён, журнал CLOSED, контейнеров foundation-test 0, данные/ключи сохранены.

Raw HTTP/пароли/cookies/токены остаются в существующем закрытом private, вне Git. Отчёт содержит только synthetic результаты, SHA, счётчики и cgroup-пики/OOM. Старые FAIL сохраняются. Реальная потеря питания/перезапуск ОС, browser visual acceptance, полный PERF, VPS/production не заявляются пройденными.
