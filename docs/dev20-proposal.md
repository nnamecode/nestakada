# DEV-20 — предлагаемый локальный профиль защиты

2026-11-02. Профиль согласован владельцем по DEV20-Q001/D-372; первоначальные условия gate ниже сохранены как история предложения. Фактические проверки и границы — dev20-results.md. Основания: D-114/D-115, scanner-defense.md, REQ-041/052/053/060, AC-041/052/060/OPS-009, DEV-20. Новые пакеты, Redis/CDN/WAF, службы и образы не требуются. Старый сайт/VPS не затрагиваются.

## Что получит владелец

Известные пробы чужих движков и секретных файлов получают короткий отказ до сессии и БД. Слишком частые запросы ограничивает существующий Nginx без искусственного ожидания. Сканирование не создаёт запись БД/сообщение ТГ/строку process log на каждый запрос. Поисковые роботы и посетители проходят одну проверку адресов; User-Agent не является основанием доверия или блокировки.

Это локальный профиль-кандидат, не измеренная ёмкость VPS и не защита от произвольного внешнего DDoS. Числа ниже применяются только после ответа владельца, испытаний и ревью. При неудаче лимиты не увеличиваются автоматически.

## 1. Ранний фильтр Django

Новый request_guard — небольшой пакет без моделей/миграций, ScannerMiddleware первым в MIDDLEWARE. До get_response он читает только путь/метод, не читает тело, cookie, сессию, пользователя или БД. Известный скан — text/plain 404, короткое константное тело до256B, no-store/nosniff/запрет фреймов и исполняемого содержимого; HEAD без тела. Остальные запросы проходят прежнюю цепочку с тем же исходным адресом. CSRF/вход/права и принятые transport/media/editor caps сохраняются.

Классификатор сравнивает ограниченную копию пути: исходная строка и максимум два дополнительных percent-decode прохода, регистр/повторные слеши только в копии сравнения. Путь для роутинга не переписывается, query не используется для блокировки. Обработка пути свыше8192 символов ограничивается сразу; окончательный статус транспортного отказа проверяется отдельно от известных404.

Фиксированные10ключей: traversal, dotfile, wordpress, php-tool, phpunit, executable, backup, cgi, malformed, oversize. Предлагаемые сигнатуры:

- сегменты `.`/`..`, обратные разделители и их кодированные формы;
- dotfiles/репозитории; первый сегмент `/.well-known/` сам по себе разрешён, вложенные dotfiles/traversal не получают исключение;
- корневые `/wp-admin`, `/wp-includes`, `/wp-content`, `/wp-login.php`, `/phpmyadmin`, `/vendor/phpunit/`, `/cgi-bin` с границами сегментов;
- расширения PHP/PHTML/PHAR/ASP/ASPX/JSP, включая конечный ограниченный PHP digit suffix;
- резервные/служебные окончания `.bak/.old/.orig/.swp/.sql/.sqlite/.sqlite3/.tar/.tar.gz/.zip/~`.

Точные шаблоны до включения снова сверяются реализацией Python со всеми115 MAP/старыми эффективными путями и316 MED. Предварительный scratch JS-кандидат проверил543целевых пути: коллизий0,13negative/7allowed vectors пройдены; это **не** доказательство работоспособности будущего Python middleware. Нужный ACME/security.txt только пропускается фильтром — реальная выдача этих ресурсов остаётся задачей среды/публичного сайта.

Зарезервированные технические адреса нельзя будет создать как новый публичный URL; новая проверка в new_target использует тот же pure classifier. Импорт точных легитимных адресов не получает молчаливой замены: конфликт с утверждённым реестром блокирует включение фильтра и требует разбора. Никакого SQL lookup allowlist на скан. Обычный вложенный slug вроде `/services/wp-admin/` не блокируется одним словом wp-admin.

## 2. Шум и ограниченные счётчики

На DEV-20 — фиксированные счётчики текущего процесса:10signature keys, total с начала процесса и current/previous окна60секунд, насыщение на2^63−1. Фиксированное число ячеек, без новых ключей по IP/URL/заголовку. Бюджет рабочего состояния проверяется до64КиБ на процесс. При contention/сбросе/насыщении статистика явно неполная; отказ учёта не мешает вернуть404. Сырые IP/пути/query/тела/секреты не сохраняются.

Это внутренняя bounded snapshot-функция, не новый публичный endpoint и не обещание глобальной/30-дневной статистики. Процесс/перезапуск обозначаются явно; нельзя представить сумму нескольких workers как уже измеренную. Историческое хранение, детализация источников/частых путей, общий журнал/размеры/ротация/админка остаются DEV-17/18; доставка/инциденты — DEV-21. Подключение этих потребителей потребует их принятых квот и проверок. Здесь они не считаются выполненными.

ExpectedScanner404Filter на существующем safe logging handler убирает только действительно ожидаемый known-scan404 из django.request/django.server. Нельзя подавлять500/неожиданный2xx/обычный важный404/прямое AuditEvent. Не форматировать record.msg/args и не выводить URL. Для django.server используется строго проверенная структура status_code/requestline из фактически установленного Django: read-only image inspection сохранён. Nginx access_log уже off/error_log=/dev/null; пользовательские данные туда не добавляются. Production WSGI access logging потребует отдельной проверки при выборе сервера.

## 3. Предлагаемые ограничения существующего Nginx

| Назначение | Локальный кандидат |
|---|---|
| Запросы с одного фактического IP Nginx |20/с, краткий burst60, nodelay |
| Общий поток на сервер |50/с, burst100, nodelay |
| Одновременно обрабатываемые запросы |8 всего, общий фиксированный ключ сервера |
| Исчерпание ограничения |короткий429/no-store; без искусственной задержки и индивидуального лога |
| Вход |прежний отдельный10/с/burst20 и Django5неудач/10мин→15мин, без изменения |
| Память новых зон |3МиБ внутри существующего128МиБ контейнера:2МиБ per-IP rate,512КиБ global rate,512КиБ global active requests |
| Бюджеты тела |прежние16КиБ/11МиБ/64МиБ по точным действиям; общий1МиБ фиксирует прежний default |
| Тайм-ауты |header10с, body15с между чтениями, send15с, keepalive15с; прежние editor absolute body120/child20/proxy150 сохраняются |

Глобальные8 выбраны с учётом фактического app_runtime CONNECTION LIMIT10 и CONN_MAX_AGE0; остаётся небольшой резерв для служебных обращений. Это не пул/очередь и не обещание достаточности на VPS; отдельные служебные соединения проверяются тестами. На общем IP несколько посетителей делят лимит — измерить нормальную загрузку страницы/админки до включения. Частота не определяется по присланному X-Forwarded-For: используется remote_addr Nginx, его прежняя очистка proxy-заголовков остаётся.

Зоны имеют фиксированный размер. Общий ключ не зависит от Host/URI; per-IP зона не растёт на диске и имеет ограниченную ёмкость/LRU согласно Nginx. Глобальные rate/active caps применяются и при смене множества IP. Проверить наследование limit_req/limit_conn в каждом существующем location; настройка в дочернем location не должна отменить общие ограничения. Ошибки429 Nginx получают отдельный internal response; ответы429 приложения не перехватываются/не подменяются.

body timeout Nginx ограничивает паузу между чтениями, а не полную длительность бесконечной капельной отправки. Не называть его абсолютным deadline и не расширять уже принятый editor body120 на все routes молча. Это ограничение профиля отражается в тестах/эксплуатационных границах; полная атака медленными соединениями и production-профиль — TEST09/READY02.

## 4. Проверка и предел завершения

Сценарии до кода — dev20-checks.md. До DEV20-Q001 не менять app/config/лимиты. После ответа — минимальная реализация, unit/real DB fences, HTTP через ordinary Nginx, normal auth/editor/media regression и независимый code/result review. Не запускать сканы на живом сайте. Без новых packages/ports/volumes, повышения container caps, очистки предыдущих данных или деплоя.

Полный публичный positive200 и смысл unknown/hidden URLs принимает DEV08/29; сейчас публичный renderer отсутствует. DEV20 доказывает passthrough полного реестра и настоящую раннюю границу, не подменяет отсутствующие страницы canary-страницей. Ступени PERF-SCAN10/50/100rps по5мин, mixed и реальные VPS/браузеры сохраняются TEST09; короткие локальные component bursts не объявляются прохождением всей нагрузки.

Источники технической проверки: [Django5.2 middleware](https://docs.djangoproject.com/en/5.2/topics/http/middleware/), [Nginx limit_req](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html), [Nginx limit_conn](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html). Общая память/пустые ключи/наследование и различие active requests от всех TCP проверяются по этим primary docs и затем фактическим бинарником1.30.6.
