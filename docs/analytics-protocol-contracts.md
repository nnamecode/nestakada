# Завершающие технические контракты ANA-01 — проект к ANA-02

Версия 0.1, 2026-10-30. Уточняет проекты analytics-content-detail.md, analytics-runtime-detail.md и analytics-html-reserve.md. Все новые механизмы, численные профили и ограничения этого файла — **предложения для независимого ревью и согласования общего пакета**, а не новые ответы владельца. Приоритет решений до D-300 сохраняется. Приложение, конфигурация, SQL-схема и исполняемые тесты не создаются.

## PR-01. Форма без JS, CSRF, receipt и условный HTML

Связи: REQ-030–REQ-032/REQ-050/REQ-057/REQ-060, AC-DTL-008–AC-DTL-012. Профиль предложения сохраняет окно начала 30 минут, распознавание результата 24 часа, отдельное согласие и нулевое создание receipt на публичный GET. Не требует CAPTCHA, кабинета, SMS или постоянного хранения полей в браузере.

### 1. Представление формы

Полноценный обычный HTML содержит серверную POST-форму с CSRF, подписанным намерением и версией согласия. JS лишь улучшает UX: отсутствие JS не лишает возможности корректно отправить заявку. Аварийный HTML не содержит действующих токенов и использует ранее согласованный ответ «позвоните».

Для обычной формы предлагается **контекст нового обращения** — случайный подписанный несекретный nonce клиента в коротком first-party cookie; он не содержит телефона/ID заявки/текста и не даёт доступа к записи. CSRF-cookie имеет своё назначение; контекст намерения его не заменяет. Cookie не является сессией БД/профилем посетителя, не устанавливается для известных сканов и не отправляется в сторонние интеграции. Срок/необходимость и точное описание cookie включаются в LEGAL-01/COOKIE-Q001, до этого реальный приём не включается.

Подписанное намерение содержит ограниченные поля: случайный/криптографически производный непредсказуемый ID, ID формы/страницы-источника, момент выдачи, профиль и версию согласия. Не переносит введённые персональные поля. Серверный ключ ID не основан на телефоне/IP. Для одного контекста/формы/интервала выдачи может сохраняться один intent-ID, чтобы перепроверка страницы не становилась незаметно новым обращением. Канонический HMAC принятого ввода не включает случайную маску CSRF/транспортный заголовок.

### 2. Контракт валидатора

Для двух страниц с формой — предложение `private, no-cache` и `Vary: Cookie`; общего HTML-кэша по-прежнему нет. Закрытые/POST/персональные ответы остаются `private, no-store`. Это не перевод всего публичного сайта в no-store.

Слабый ETag формы отражает публичные версии всех влияющих данных, шаблон, политику формы/версию согласия, непрозрачный производный признак текущего CSRF-секрета и контекста намерения, а также тридцатиминутный интервал защиты. В сам ETag не помещаются исходный CSRF-секрет, nonce, receipt или персональные поля. Подписанный непрозрачный признак не служит входным токеном. Значение `W/` не объявляет разные случайные маски побайтно одинаковыми.

- Без корректного cookie/контекста или при его смене — полный 200 с актуальной формой, не 304 чужого/непроверенного варианта.
- В том же защитном интервале и контексте 304 допустим только если ранее выданное намерение/CSRF-представление ещё допустимы. Возвращённое из браузера тело семантически пригодно для отправки, хотя новая случайная маска могла бы выглядеть иначе.
- При новом интервале защиты/новой версии согласия/смене CSRF-секрета или контекста — новый ETag и полный 200. Один Last-Modified для таких страниц не является достаточным условием 304: без подходящего составного ETag возвратить 200.
- Уточнить выдачу времени так, чтобы токен, выданный в начале интервала, не считался допустимым дольше своего срока. Если это доказать нельзя, безопасная ветка — полный ответ, а не 304 с просроченной формой.
- HEAD не выпускает новую рабочую запись/receipt. Его статус/валидаторы согласованы с GET; нельзя считать HEAD источником подтверждения отправки.

На POST сначала CSRF/подлинность/размер, затем попытка распознать уже принятый intent, и только для новой вставки — текущая версия согласия/срок начала/лимит приёма. Успешный повтор не создаёт вторую заявку или вторую цель принятой заявки. При сменившемся тексте согласия прежняя принятая отправка остаётся распознаваемой в своём окне.

### 3. Явное новое обращение и потерянный ответ

После подтверждённого результата сервер может выдать новый контекст формы вместе с ответом/переходом к новой форме, не меняя CSRF-секрет. Повтор прежнего intent после этого всё равно распознаётся по подписи/receipt, а не требует совпадения с уже обновлённым cookie нового контекста. Не разрешать новую вставку старым intent только потому, что cookie сменился.

Действие «Новое обращение/обновить защиту» явно выдаёт новое намерение; это не автоматическая повторная отправка введённых полей. При неопределённом исходе посетителю предлагается повторить **старое** намерение/проверить результат, а не молча начать новое. Возврат из истории браузера проверяет срок/receipt; истёкший intent после очистки receipt не становится новой вставкой.

Если CSRF-секрет изменился, например после входа, старый CSRF не пропускается ради receipt. Безопасная ошибка сохраняет ограниченный введённый посетителем текст и старое подписанное намерение в открытой форме, предлагает актуальную защиту и явный повтор. Страница ошибки `no-store`, без чтения закрытых полей заявки из БД. Невалидный intent не отражается как исполняемый HTML. Допустимость чтения полей при CSRF-отказе определяется только безопасным ограниченным выводом самого присланного ввода, не доверенным выполнением POST.

**Источники механики, не выбор версии:** Django описывает изменение маски при неизменном CSRF-секрете, смену секрета при входе, условные ответы и подписанные поля: [CSRF](https://docs.djangoproject.com/en/5.2/ref/csrf/), [условные ответы](https://docs.djangoproject.com/en/5.2/topics/conditional-view-processing/), [подписи](https://docs.djangoproject.com/en/5.2/topics/signing/), проверено 2026-10-30. Составной валидатор и контекст намерения выше — проектная конструкция, а не готовая гарантия Django.

## PR-02. Минимальный профиль Header/Footer

Связи: D-066/D-110/D-111, REQ-013/REQ-017/REQ-022/REQ-050. Предложение первой версии: две самостоятельные истории безопасного содержимого, один текущий и один рабочий черновик у каждой; буквальные контакты/ссылки принятого HTML входят в снимок. Восстановление возвращает именно их, с явным сравнением старого телефона/ссылки до применения. Не создавать универсальную систему плейсхолдеров/отдельный реестр контактов только ради истории.

Интерактивное мобильное меню, разрешённая навигация и согласованные внешние интеграции — доверенные компоненты шаблона, не JavaScript/iframe от редактора. Предлагаемая схема компонента допускает только фиксированные типы/поля. Она не позволяет автору исполнить Django-выражение, выбрать файл сервера или объявить новый тип действия. Сохранённая структура не может превратить доверенный компонент в произвольный eval.

Снимок удерживает свои Asset и исходную схему. При изменении доверенного компонента не выдавать живую отрисовку истории за побайтный старый экран: показать сохранённый payload/версию компонента и разницу. Если совместимая безопасная отрисовка невозможна, просмотр текста/данных доступен владельцу, применение несовместимого снимка отклоняется целиком. Обычная Page использует текущий Header/Footer; её восстановление их не меняет.

Для рассмотрения предлагается единый профиль §7 analytics-content-detail.md: без автоматической очистки истории по лимиту страницы, но с ограниченным бюджетом 256 МиБ/10 000 снимков двух общих блоков, предупреждением 75%, проверкой до записи и ручной очисткой владельцем после списка/подтверждения. Текущий/используемый/защищённый снимок и живые Asset не очищаются. Новые Stable-операции общим блокам не предоставляются без явно принятого профиля; если исходная защита уже есть, её сохраняют. Это конкретное предложение к согласованию пакета, не «10+Stable уже принято» и не бесконечное хранилище.

## PR-03. Рекомендуемое разделение мониторинга

Связи: REQ-045/REQ-046/REQ-049/REQ-060, D-104/D-276–D-278/D-282. Вместо выбора неизвестных функций конкретного бесплатного сервиса предлагается разделить обязанности двух независимых контуров, каждый с пятиминутным периодом:

| Контур | Проверка и порог | Область сообщения/действия |
|---|---|---|
| Независимый от Django локальный контроллер | Раз в пять минут реальный запрос приложения к его БД; две неудачи/два успеха, один ID проверки не считается дважды | Отказ движка/БД, подтверждённый факт включения/выхода HTML и ошибка переключения. Состояние/ограниченная исходящая доставка не зависят исключительно от основной БД |
| Внешний сервис вне хоста | Раз в пять минут защищённый HTTP-запрос реальной готовности Django/его БД, обходящий HTML-резерв; две неудачи/два успеха | Внешний отказ/восстановление приложения/БД либо всего хоста/TLS. Готовая статическая страница никогда не подменяет его ответ |

Это **два независимых readiness-потока**, каждый с периодом пять минут. Внешний включает реальную доступность БД по D-276/REQ-045; локальный нужен для независимого переключения, когда внешний сервис не умеет управлять хостом. Топология — предложение к согласованию, а не уже утверждённое удвоение числа SQL-проверок. Экономичный единый источник остаётся альтернативой только после доказанного общего канала результатов/управления; без него нельзя объявить внешний 200 статики проверкой БД.

Бюджет: 288 локальных и 288 внешних readiness HTTP/SELECT за сутки, всего **576 проверок/сутки и 17 280 за 30 суток**, без retries/дополнительных точек. Это вдвое больше прежнего расчёта одного источника; средняя частота обоих вместе около 0,0067 SELECT/с, пиковая совместность также измеряется. Дополнительное чтение главной не входит в базовую схему. Если оно добавляется для проверки рендеринга, отдельно считать HTTP и обычные SQL страницы — не обещать их нулевую стоимость.

Принятые пороги не складываются между контурами: одна локальная и одна внешняя ошибка не образуют две подряд. Сбой сторонней Метрики/виджета не причина объявить БД недоступной. Предлагаемый владелец уведомления об общей внешней readiness — внешний контур; локальный не создаёт второе одноимённое critical-уведомление, а сообщает отдельно только подтверждённый факт включения/возврата HTML либо неудачу переключения. Поэтому возможны два содержательно разных сообщения («готовность недоступна» и «HTML действительно включён»), но не дубли одного события на каждую проверку. Разделение классов/каналов входит в согласуемый пакет; межсервисная exactly-once-дедупликация без общего протокола не обещается. Общий журнал сохраняет безопасную связь с одним эпизодом отказа.

Контроллер не импортирует работоспособность Django как условие своего запуска: он вызывает ограниченный readiness, а не выполняет бизнес-код сайта у себя. Лимиты подключения/SQL/HTTP и no-store из эксплуатационного проекта сохраняются. Служебная авторизация endpoint проверяется до БД; посетители/сканеры не могут заставить контроллер выполнять SQL на каждый запрос.

Надзор процесса в выбранной среде обнаруживает остановку/зависание контроллера по ограниченному heartbeat и поднимает наблюдаемый отдельный статус; допустим технический перезапуск без отката данных. После перезапуска не выдавать старую локальную «здоровую» запись за свежую проверку. Частота надзора процесса не является дополнительной проверкой БД. Если выбранный хостинг не поддерживает независимый контроллер/надзор/переключение, это непригодная среда для предложенной схемы, а не повод молча отказаться от D-280.

Провайдер/тариф должны действительно поддерживать период и подтверждения; при неподдерживаемых двух успехах нужен другой совместимый сервис/согласуемая схема. Не обещать webhook, тело/заголовки проверки или exactly-once Telegram без проверки. Секреты/учётные записи сейчас не создаются. Топология и её дополнительный публичный HTTP-бюджет включены в пакет согласования; это не уже установленная настройка.

## PR-04. Единая граница допуска и внешний head

Связи: REQ-002/REQ-046–REQ-050, AC-HTML-002–AC-HTML-009, REV-DTL-001/002. Предложенный профиль: все ответы аварийного HTML проходят через одну логическую точку допуска, общую для выдающих процессов. Прямая выдача защищаемых файлов мимо неё запрещена, каталог наборов не находится в общедоступном autoindex/web root. Прямые ссылки на неизменяемые допустимые медиа имеют отдельные правила и не открывают закрытый HTML.

Точка допуска синхронизирует «допустить запрос на маршруте X/поколении Y» и «закрыть X». Подтверждение отзыва требует долговечного запрета и исключения старого допуска у всех выдающих процессов; отставший процесс отсоединяется от выдачи либо операция остаётся явно незавершённой. После допуска сам сетевой ответ не держит глобальную блокировку: медленный ранее допущенный клиент может закончить, но новые допуски после подтверждения закрыты. Набор/медиа удерживаются до окончания ранее допущенных ответов.

Внешний head/журнал отзывов — отдельная защищённая область **вне домена отката локального диска и обычных точек БД/HTML**. Требуемые свойства: однозначное поколение/ID операции, проверка целостности и полномочий записи, упорядоченная долговечная фиксация, обнаружение отставшей записи/повтора, запрет замены актуального head старым поколением. Ни один конкретный облачный API не объявляется поддерживающим эти свойства без проверки. Простого хэша в том же восстанавливаемом ZIP недостаточно.

При отзыве собственного маршрута предлагается сначала долговечно записать запрет во внешнем журнале/локальной точке допуска, затем основную транзакцию, затем финальный результат; сбой оставляет консервативный pending, а не раскрытие старой страницы. D-300 исключает автоматическую переделку главной из-за публичной ссылки/цены удалённой цели. Остальные стадии/receipt соответствуют §6 HTML-проекта.

**Операционная цена строгого профиля:** если невозможно долговечно зафиксировать запрет, действие удаления/снятия публикации не выдаётся за успешно завершённое. В зависимости от достигнутой границы — отказ до коммита либо честное «записано, завершение допуска не подтверждено». При недоступной сверке после рестарта возможен контактный 503, даже если старые HTML целы. Эти ограничения предложенной схемы не скрываются под словом «атомарно» и должны оцениваться ANA-02/владельцем вместе с пользой защиты.

На каждом публичном запросе обращаться к облаку не нужно: используется уже проверенное текущее поколение в контролирующей плоскости. Но его свежесть после рестарта/восстановления нельзя доказывать самим откатившимся локальным файлом. Стартовый барьер сверяет актуальный head и восстановленное состояние; при неизвестности допуск остаётся закрытым. Тестируется откат валидных подписанных файлов/БД, а не только повреждение байтов.

Выбор физического сервиса/примитива синхронизации — условие инфраструктуры до реализации этой части, а не бизнес-вопрос владельцу о каждой блокировке. Если на доступной среде требуемые свойства недостижимы, рецензент возвращает архитектурное замечание; нельзя отметить весь протокол доказанным одним чтением документа.

## PR-05. Главная после удаления источника — D-300

Это принятая граница поведения, способы хранения ниже — предложения. Действующий опубликованный источник продолжает менять связанную сумму по D-255. После удаления источника главная не переделывается автоматически; её прежние публичные элементы владелец проверяет/правит отдельно. Для снятия публикации без удаления обычное правило D-256 отдельно не отменялось.

Предлагается у каждой настроенной позиции главной иметь собственное последнее подтверждённое публичное представление (подпись/адрес/цена/пометка и необходимые Asset), фактическое состояние отображения и устойчивую ссылку на исходный объект/строку прайса. Пока источник действует, представление согласованно обновляется по нему. При удалении сохраняется именно фактическое состояние главной непосредственно перед удалением: видимое не исчезает, уже скрытое не появляется. Связь помечается как утратившая источник, выдуманной новой суммы нет. Это ограниченные поля действующей главной, не новая бесконечная история удалённых страниц.

Новый объект на прежнем URL не перехватывает старую связь. При следующей правке владелец видит, что источник удалён, может убрать/исправить позицию или выбрать другой реальный источник; это не автоматическая подстановка. Нельзя незаметно потерять картинку главной из-за очистки Asset удалённой услуги: собственные ссылки текущей главной/её версий/HTML по-прежнему удерживают используемые байты.

Ночная сборка берёт фактическое настроенное публичное содержимое главной с такими представлениями; старые допустимые элементы не делают её непригодной. По удалённому целевому URL остаётся 404, по скрытому — пустой 200. Показ HTML — переключение отдачи, не восстановление БД/удалённых версий/заявок.

## PR-07. Детерминированное предложение URL новой страницы

Связи: D-242/D-243, REQ-006/REQ-007, AC-006/AC-DTL-002. Только для предложения **нового** адреса; исходные старые пути/тексты не преобразуются. Профиль к ревью: NFC/нижний регистр названия, сохранение ASCII a–z/0–9, последовательности пробелов/разделителей в один дефис, без дефисов по краям. Отображаемое название не переписывается этой процедурой.

| Кириллица | Предложенное преобразование |
|---|---|
| а б в г д е ё ж з и й | a b v g d e yo zh z i y |
| к л м н о п р с т у ф | k l m n o p r s t u f |
| х ц ч ш щ ъ ы ь э ю я | kh ts ch sh sch (убрать) y (убрать) e yu ya |

Это проектная таблица, не заявление соответствия какому-либо ГОСТ. Неотображаемые/неподдерживаемые символы не образуют произвольный исполняемый путь. Если после преобразования нет непустого сегмента или он превышает предложенные 80 символов/общую границу пути, показать владельцу поле и причину для ручного ввода; не выдумывать страницу «page», не молча обрезать/перенумеровывать коллизию.

Путь предлагается с учётом выбранного родителя и принятого правила слеша для нового типа; владелец видит весь адрес до сохранения. Системные/служебные/занятые/редиректные пути зарезервированы. Проверка свободного пути повторяется в операции сохранения: две одновременные новые страницы не получают один маршрут. После сохранения смена названия/родителя не пересчитывает URL; явная смена действует только по D-243, со старой рекламой отдельно.

Минимальные примеры проверки: «Ремонт ёмкости» → `remont-yomkosti`, «Шины и диски» → `shiny-i-diski`, «Щётки / 2026» → `schyotki-2026`; повторные дефисы не накапливаются. Пример задаёт предложение сегмента, не утверждённый публичный путь реальной услуги.

## PR-08. Границы согласованной записи и конкуренции

Связи: REQ-017/REQ-018/REQ-022–REQ-024/REQ-028/REQ-029/REQ-032/REQ-036, AC-017/AC-018/AC-DTL-019/AC-HTML-003/AC-HTML-005. Предлагается для первой небольшой системы сериализовать короткую **фиксацию** контентных изменений в одном логическом домене: дерево/маршруты, страницы/общие блоки, защиты версий и ссылки Asset. Чтения посетителей и предварительная обработка изображения в этот домен не входят. Это проверяемый профиль безопасности, не выбор SQL/модели/библиотеки.

Порядок контракта: сначала актуальная идентичность/права и основание операции; затем сериализованная фиксация предметного домена с повторной проверкой прав/редакции/зависимостей; внутри одного домена — объекты в устойчивом порядке непереиспользуемых ID; затем связанные версии/медиа-ссылки/история. Нельзя сначала захватить Asset, затем пытаться войти в уже занятый контентный домен в обратном порядке. Отзыв права одновременно с сохранением имеет одну определённую границу: либо сохранение допущено до отзыва, либо отказ; открытая вкладка не сохраняет право после него.

Отдельный домен обработки заявки согласует её статус/назначение/заметку и версию основания; уникальность intent/receipt сериализует создание единственного результата. Нельзя делать независимые коммиты «заявка без согласия» или «успех receipt без заявки». Отключение сотрудника проверяет и отзывает полномочия до разрешения новых привилегированных операций, а передача открытых заявок записывает согласованную историю. Переназначение/статус/заметка из старого основания получают конфликт вместо затёртой правки.

Сетевые Telegram/Диск, перекодирование изображения и полная ночная сборка не удерживают глобальную блокировку публикации. Для внешнего отзыва сначала готовится безопасный запрет, затем в короткой фиксации повторно проверяются исходное основание и полномочия. Если за ожидание сети основание сменилось — не выполнять прежнее удаление; pending разбирается по ID операции, не открывается по таймеру. Неполный внешний результат виден честно по PR-04.

Эта схема уменьшает число возможных обратных порядков в первой версии; она не является доказательством отсутствия deadlock. До реализации зафиксировать конкретные примитивы/транзакционные границы для выбранного хранилища и проверить сохранение/удаление/Stable/очистку/отзыв прав конкурентно. Если измерения покажут необходимость более тонкой параллельности, новый порядок проходит ревью, а не появляется случайно в одном обработчике.

## Статус для рецензента

Подготовлены конкретные контракты и сценарии для прежде открытых технических стыков. Рецензент проверяет согласованность/достижимость и достаточность предстоящих проверок, не подтверждает фактические реализации. Неустранимое противоречие/неприемлемая операционная цена возвращается как замечание с источником; новые правила нельзя принять за владельца. Пакет готовится к ANA-02, а не к развёртыванию.
