# DEV07-SH — вариант явного хранения для проверяемого резерва

2026-11-01, D-346. Техническое предложение координатора, **не принятая реализация/формула**. DEV-07 около96%, этап8 около20%. Не меняет HTML1МиБ,256МиБ,10000снимков/75%, роли, зависимости или ресурсы. Старый сайт/VPS не используются.

## Проблема

Первый shared_content умеет Check/чтение и безопасно отказывает записи при неизвестном профиле. Его TextField может породить сотни скрытых TOAST-вставок одним SQL. Индексы могут расщепляться по нескольким уровням. Предположение «достаточно ×2 длины HTML» не доказано. Предложенные ранее постоянная высота32 и логарифм текущего числа строк рецензентом не приняты; они не включаются в код.

Официальные основания: [TOAST PostgreSQL18](https://www.postgresql.org/docs/18/storage-toast.html) описывает вынесенные фрагменты и отдельный индекс; [B-tree PostgreSQL18](https://www.postgresql.org/docs/18/btree.html) описывает каскадные расщепления и новые индексные записи при UPDATE. Это основания учитывать рост, а не доказательство конкретного множителя.

## Предлагаемое устранение скрытого большого batch

1. Добавить собственный immutable SharedPayload и SharedPayloadChunk. Канонические UTF8 bytes делятся на фрагменты не более512байт. В chunk фиксированы payload FK/position и ограниченные bytes; данные не индексируются. DB CHECK octet_length и STORAGE PLAIN исключают TOAST содержимого chunk. Все payload/chunk root relations/индексы/TOAST/forks включены в actual inventory.
2. Revision/draft ссылается на payload; в них нет большого дублирующего TextField. Целый HTML по-прежнему принимается до1МиБ, восстанавливается последовательным чтением chunks с проверкой числа/размера/SHA256 и UTF8. Неполное/несовместимое хранилище даёт отказ, а не пустой HTML. Source/hash/Asset policy не меняются.
3. Запись каждого малого SQL шага предваряется измерением собственного места и консервативным резервом именно этого шага. На один INSERT в один индекс рассматривается исходная грубая граница по числу текущих страниц индекса и возможному пути расщепления; для нескольких связанных маленьких INSERT берётся batch bound с ростом высоты. Формула требует отдельного подтверждения точного PG18.6 source, heap/FSM/VM extension slack и незавершённых расщеплений. Никакой fixed32/logarithmic height предпосылки.
4. Все content writes/chunks/refs/receipt остаются одной content transaction. После каждого шага — actual measurement; недопустимое продолжение откатывает логический результат. Даже промежуточная физическая аллокация должна вмещаться в проверенный предварительный резерв; один post-check не заменяет его. На rollback own bloat остаётся в actual inventory.
5. Chunk INSERT выполняется по одному; не bulk_create/COPY и не большой JSON payload, который снова создаст скрытый batch. Тяжёлый HTML parser остаётся прежним child вне content transaction. Время2048малых записей для1МиБ и длительность content lock измеряются; если профиль неприемлем, не объявлять его подходящим и не повышать лимиты автоматически.

## Общий AssetUsage и crash-accounting

Одна лишь запись charge внутри content transaction недостаточна: её rollback сотрёт charge, но физический рост общей media relation может остаться. Вариант требует отдельной durable quota reservation до начала content mutation:

- Под content/auth lock проверить actual inventory/count, actor/base/proof, закрытый список максимум4Asset slots, собственный operation fingerprint; атомарно зарезервировать собственным accounting record консервативный верхний расход общих metadata/индексов/их временного роста. Это не успешная content квитанция.
- Основная transaction снова проверяет контекст и достаточность уже удержанного резерва при свежем размере индексов; при недостаточности не начинает content writes. Никакого слепого продолжения после изменения общего ledger.
- На успешном commit преобразовать резерв в отдельно учитываемый attributable charge, измерив before/after общей relation и учитывая minimum structural charge записей в уже существующих страницах. Не уменьшать charge только из-за логического DELETE.
- При crash/unknown result/rollback удержанный durable резерв остаётся. Exact retry под тем же nonce/fingerprint не бронирует второй резерв; результат запрашивается после свежей авторизации. Неизвестный accounting state fail closed. Нужен отдельный проверяемый порядок reconciliation; нельзя автоматически списать неизвестное потребление по возрасту.
- Own accounting tables/forks/резервы входят в256МиБ. Глобальные operational audit/WAL относятся к отдельной эксплуатационной границе; snapshot body не попадает в аудит. Посторонние global AssetUsage rows целиком не приписываются этому бюджету.

Этот протокол пока **не доказан и не реализован**. Рецензент должен проверить атомарность/порядок lock, отсутствие двойного резерва, crash между фазами, held reserve при отказе и связь с count limit. Без этого текущий unknown-profile gate не снимается.

## Ворота и сценарии до изменения модели

- SBC-001: review полного bounded SQL-step reserve по exact schema/PG/block size и всех вставляемых/обновляемых отношений. Unknown index AM/expression/trigger/schema/profile — отказ.
- SBC-002: actual PG512B chunks/полный1МиБ плохо сжимаемый HTML, hash/UTF8/source roundtrip; measured parent memory/time/lock duration и delta индексов/forks. Сохранить настоящий source cap.
- SBC-003: quota около75%/256МиБ/10000, два параллельных owner действия, отказ на позднем chunk без публикации/успешной квитанции; actual own bloat учитывается.
- SBC-004: crash до/после prebook, перед commit/после commit с потерянным ответом, изменение общего ledger между фазами; reserve не исчезает и не расходуется дважды.
- SBC-005: историческое/черновое/restore чтение не получает усечённых payload, protected refs/current сохраняются. Текущая версия меняется только целиком выбранным Apply.

До независимого review и измерений новая migration/профиль не создаются. Текущий ограниченный срез проверяется отдельно; этот документ не выдаётся за завершение поручения реализовать успешный Apply.
