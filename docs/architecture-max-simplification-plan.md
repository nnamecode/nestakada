# План максимального упрощения архитектуры

Дата: 2026-11-16. Статус: **SUPERSEDED D-1220; не исполнять как in-place refactoring plan**. Решения о минимальном составе, current+previous, Telegram-only и удаляемых функциях сохраняются как требования, но реализация теперь планируется чистой пересборкой по `docs/clean-rebuild-plan.md`. Продуктовый код, БД и runtime не изменены.

Основание: D-1217 остановил прежний template/CSS plan до упрощения общей архитектуры. Владелец уточнил назначение проекта: небольшой сайт автосервиса с несколькими типами страниц, фотогалереей, YouTube-вставками и простой формой. Заявка хранится в админке, а её копия отправляется в Telegram; email не нужен. Владелец разрешил выводить из MVP целые подсистемы, если это ускоряет завершение и сохраняет приемлемую безопасность.

## 1. Итоговая цель

Один обычный модульный Django-монолит:

- Django обслуживает публичные страницы и существующую пользовательскую админку;
- PostgreSQL хранит страницы, текущую и одну предыдущую копию содержимого, права, настройки сайта, заявки и аудит;
- один media-каталог хранит изображения вне Git;
- Nginx отдаёт TLS/static/media и применяет обычные лимиты;
- Telegram получает best-effort копию уже сохранённой заявки.

Не создаются отдельные сервисы, API, SPA, Redis, Celery, очереди, универсальный page builder, собственная workflow-платформа, runtime-миграционный движок или аварийная CMS.

Целевой runtime состоит из пяти понятных областей:

1. `accounts`: Django login, две роли, разрешения сотрудника, простой throttle.
2. `pages`: дерево, точные URL, несколько фиксированных типов страниц, current+previous и безопасный редактор.
3. `media`: загрузка, проверка, привязка и галерея.
4. `requests`: сохранение заявки, закрытый список в админке, Telegram-копия, удаление владельцем.
5. `audit`: только важные действия и ошибки без содержимого страниц, телефонов и секретов.

Физические Django app labels и применённые migrations можно временно сохранить ради безопасной миграции данных. Это не означает сохранение старых runtime-подсистем.

## 2. Что обязательно остаётся

Эти свойства нельзя сокращать ради скорости:

- точные старые URL, структура и утверждённые тексты;
- побайтно неизменные оригиналы `/gallery-of-works/`;
- утверждённый дизайн как источник внешнего вида;
- login/password, роли владельца и сотрудника, серверная проверка прав;
- CSRF, XSS-sanitizing, безопасные загрузки, SQL через ORM/параметры, закрытые private responses;
- текущая и ровно одна предыдущая сохранённая копия страницы, атомарное сохранение и отмена последнего сохранения;
- подтверждённое удаление всей страницы вместе с историей только владельцем;
- backup PostgreSQL+media и проверяемое восстановление;
- заявка сначала сохраняется в БД, затем независимо отправляется в Telegram; отказ Telegram не теряет заявку;
- rate limit, honeypot/антибот и отсутствие персональных данных в логах.

## 3. Что упрощаем или удаляем

### 3.1. Публичные страницы и шаблоны

Оставить закрытый набор примерно из шести семейств:

- главная;
- каталог/раздел услуг;
- обычная услуга или статья;
- фотогалерея и альбом;
- специальные страницы: акции, отзывы, контакты;
- простой служебный вариант для legacy-страниц без отдельного макета.

Одна страница имеет `kind`, один текущий content payload и один renderer этого семейства. Не строить универсальные presentation/profile/capture слои. Общие части — обычные Django partials. CSS: базовый shell плюс отдельный небольшой файл/секция на семейство. Данные и внешний вид больше не определяются формой произвольного старого HTML.

### 3.2. Редактор

Заменить текущий универсальный редактор и большой `editor.bundle.js` на небольшой редактор фиксированных полей:

- заголовок, intro и основной rich text;
- при необходимости цены/таблица;
- выбор изображений;
- для специальных типов — только их конкретные поля;
- YouTube хранится как проверенный video ID или разрешённая ссылка, не как произвольный iframe/HTML.

Серверный sanitizer и renderer являются единственным authority. Произвольные Django template, Python, JavaScript, `<style>`, неизвестные теги и атрибуты запрещены. Preview и public используют один renderer.

По решению D-1219 отдельные owner draft, Stable, ручные именованные версии, список истории и лимит 10 удаляются из целевой архитектуры. Обычное сохранение сразу обновляет публичную страницу, а одна previous-копия даёт простой откат последнего сохранения.

### 3.3. Header/Footer и общие данные

Удалить `shared_content` как универсальную версионную CMS-подсистему. Header/Footer не являются свободным HTML:

- разметка и навигация живут в утверждённых Django templates;
- телефон, адрес, часы, соцсети и необходимые подписи хранятся в одной простой `SiteSettings` записи;
- навигация строится из опубликованного дерева страниц;
- логотип всегда ведёт на `/`.

Не нужны shared drafts, restore stages, base pins, receipts, identity reservation, filesystem fallback, journal, quota, cleanup jobs и diagnostics.

### 3.4. Current+previous и команды страниц

Оставить одну транзакцию на одну понятную команду. Использовать `transaction.atomic()`, точечный `select_for_update()` и ограничения PostgreSQL.

У страницы хранится только:

- `current` — содержимое, которое сейчас опубликовано;
- `previous` — current до последнего успешного сохранения; для первой записи может отсутствовать.

При сохранении в одной транзакции прежний current заменяет previous, затем записывается новый current. Кнопка «Отменить последнее сохранение» атомарно меняет current и previous местами, поэтому ошибочный откат тоже можно отменить. Сотрудник по-прежнему меняет только разрешённые поля, а структура, URL и защищённые поля остаются владельцу.

Удалить Stable, manual revisions, revision metadata/protection, owner draft, history list, ordinary pruning, универсальные operation receipts, identity reservation books, restore stages и base pins. Media usages защищают только current и previous.

Существующая история сначала становится read-only legacy data. После backup и проверки для каждой страницы сохраняются exact current и непосредственно предшествовавшая ему сохранённая копия. Остальные исторические строки, включая прежние Stable/manual, удаляются только отдельной подтверждённой разрушительной миграцией; применённые Django migrations не переписываются.

### 3.5. Медиа

Оставить Asset/File/Usage, проверку формата и размеров, безопасные имена, contextual authorization закрытых файлов и защиту используемых файлов от удаления.

Удалить отдельные media identity/file-key reservation и сложный lifecycle. UUID+UNIQUE, безопасный storage key и повторная проверка usages перед удалением достаточны. Оригиналы галереи никогда не перекодируются.

### 3.6. Заявки

Оставить одну модель `ServiceRequest` и только реально нужные поля. В админке — закрытые list/detail для разрешённых сотрудников, удаление только владельцем.

Удалить:

- email и `RequestSettings.recipient_email`;
- статус, ответственного, заметки, CRM и экспорт;
- очередь уведомлений, retry worker и отдельный notification ledger.

После commit выполняется одна bounded попытка Telegram. Ошибка безопасно фиксируется без телефона/комментария в логах; заявка остаётся в БД. Повторную ручную отправку можно добавить позже только при реальной потребности.

Маленький UUID-only deletion ledger сохраняется: он не является платформой, но не позволяет удалённой заявке с персональными данными незаметно воскреснуть после восстановления старого backup.

### 3.7. Эксплуатационные подсистемы

Оставить стандартные Django sessions, `generation` для отзыва доступа, простой readiness `SELECT 1`, ограниченную ротацию логов и два проверенных поколения backup.

Удалить из MVP ручной HTML reserve и Nginx HTML fallback. Для такого сайта обычный restart/restore проще, а поддержка второго статического представления всех страниц создаёт почти второй сайт. Возврат к этой функции возможен только после запуска, если реальные требования доступности её оправдают.

Удалить runtime/import пути DEV09/DEV10/DEV12 и local-demo assembler после контрольного переноса данных. Применённые Django migrations не переписываются; исторические source snapshots можно сохранить как документационное доказательство, но они не импортируются runtime-кодом.

Удалить устаревшие тестовые harnesses вместе с удаляемым кодом. Оставить компактные тесты пользовательских гарантий, а не внутренней истории реализации.

## 4. Порядок работ и оценка

Оценка дана в чистых рабочих часах, а не календарных обещаниях. Она включает код, миграции, проверки и review, но не production deploy и не ожидание ответов владельца.

| Этап | Результат | Оценка |
|---|---|---:|
| SIMP-0. Контрольный срез | Фиксируются строки/файлы/URL/media SHA/таблицы и минимальные e2e-гарантии. Никаких изменений данных. | 2–3 ч |
| SIMP-1. Утверждение минимального контракта | Финальный список типов страниц и полей; current+previous, shared content и HTML reserve; новая короткая acceptance matrix. | 1–2 ч |
| SIMP-2. Простое ядро страниц | Один current+previous save/undo путь, простой SiteSettings, прекращение новых revisions/receipts/reservations/stages/pins. Данные ещё не удаляются. | 3–5 ч |
| SIMP-3. Простой редактор и media | Фиксированные поля, малый JS, один sanitizer/renderer, безопасные image/YouTube contracts. | 5–7 ч |
| SIMP-4. Публичные шаблоны | Перенос утверждённого дизайна на 5–6 семейств, общий shell и scoped CSS; проверка всех 115 представлений. | 7–9 ч |
| SIMP-5. Заявки | DB/admin + Telegram-only, удаление email/settings/двухканальной обвязки; security tests формы. | 2–3 ч |
| SIMP-6. Отрезание старого runtime | Отключение shared_content, page history/Stable, html_reserve, runtime import/demo и legacy editor/lifecycle путей; приложение работает без них. | 3–4 ч |
| SIMP-7. Общая приёмка | Все URL, тексты, current+previous undo, роли, media SHA, форма, Telegram-failure, backup/restore, responsive representative pages. | 3–4 ч |

**До состояния «сайт и админка готовы к запуску»: примерно 26–37 часов.** Если контрольный срез подтвердит, что старые history/legacy-таблицы больше никем не читаются, ожидаемый рабочий коридор — **27–34 часа**.

Физическое удаление старых таблиц и окончательная уборка исторических тестов выполняются после успешной общей приёмки отдельным этапом `SIMP-8` (**5–8 часов**). Это не должно блокировать запуск: старые таблицы могут некоторое время оставаться выключенными и read-only, не усложняя runtime.

## 5. Как ускоряем без повторной переделки

- Сначала переключаем runtime на простой путь, потом удаляем старые таблицы. Так скорость не покупается риском потери данных.
- Переносим дизайн сразу семействами, а не чиним 112 страниц по одной.
- Проверяем все URL автоматически, а визуально — представителей каждого семейства на согласованных ширинах.
- Не сохраняем совместимость внутренних Python API и старых тестовых harnesses; сохраняем только пользовательские данные и поведение.
- Не добавляем «временно универсальный» слой. Если функция нужна одному типу страницы, она остаётся полем этого типа.
- Любой новый модуль должен либо заменять удаляемый, либо быть обязательным для пользовательского сценария. Иначе он не входит в MVP.

## 6. Безопасность приемлемого уровня

Сохраняются обязательные границы: аутентификация и права на сервере, CSRF, sanitizer и escaping, upload validation, закрытые media/private страницы, rate limit формы и входа, секреты только в окружении, parameterized SQL/ORM, backup+restore check, отсутствие ПД в логах.

Не сохраняется «доказательная инфраструктура» вокруг каждой операции: универсальные receipts, reservation books, многоступенчатые prepare/run/result протоколы, собственные journals и квоты. Для одного сайта они увеличивают поверхность ошибок сильнее, чем безопасность.

## 7. Ворота выполнения

1. Этот документ и список удаляемых функций проходят отдельное архитектурное review.
2. Владелец утверждает `SIMP-1`; только после этого меняется product code.
3. До каждого инкремента записываются короткие acceptance-сценарии; после — focused tests и review.
4. Старые таблицы/файлы не удаляются до контрольной копии, проверки нового runtime и отдельного разрешения на разрушительную миграцию.
5. Live/deploy остаются отдельным явным решением.

Следующая предлагаемая работа: `SIMP-0` — автоматизированный read-only контрольный срез с точной картой `KEEP / REPLACE / RETIRE / LEGACY-DATA`, затем корректировка оценок и независимое review плана.
