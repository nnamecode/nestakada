# Частичное удаление логов при отказе файлов: AT-062/704/705/706

2026-10-30. Основания D-093/D-095/D-098/D-115, принятый MAN-03 в analytics-manual-operations.md, UI-S041 и D-301/D-307/D-308. Только приёмочные утверждения/контракт наблюдений. Старый сайт/VPS, приложение/его команды и настройки не меняются. Файлы1ГиБ, реальные удаления и fault-процессы здесь не создавались.

`acceptance/log-delete-failures.spec.js`: **2 экземпляра** — file-access-denied и no-space-for-safe-partial-segment. Каждый выполняет полный частичный путь: подтверждение фиксированного набора доL → новый настоящий save-event в общем сегменте → логическое удаление с незавершёнными файлами → ещё одно новое событие → снятие fault и повтор **того же operationId/подтверждения** → завершение → повтор завершённой операции без новой файловой попытки/расширения набора.

Новые события послеL, запись другой категории и безопасный аудит за пределами набора сохраняются. Сохраняется фактическое содержимое защищённых файловых записей, а не только список ID/флаг exists. Текущий read cursor/обычный notification cycle/открытый critical не подтверждаются и не закрываются очисткой. После успеха два новых события остаются непрочитанными. Это частичные ветви AT-062/704/705/706, не исполненные AC.

## Собственный изолированный контур

До reset требуется independent actual-http admission ARC-10/isolation/evidence с **log-deletion-control-v1**. Транспорт перед каждой fault-командой заново проверяет собственные run/instance/admission/capability и отдельный controlOrigin/session. Команды:

- `set-log-delete-file-fault({operationId,fault})` — реальный отказ файлового доступа исполнителю либо нехватка места для безопасной переработки общего префикса; применяется только к физической стадии данной подготовленной операции на собственном тестовом томе.
- `clear-log-delete-file-fault({operationId,fault})` — снимает только этот fault; не очищает файлы/журнал/статус за продукт.

release/barrier-команда не используется. Fault включается перед настоящим POST владельца, но не ломает SQL/защищённый журнал операции: подготовленная fixture позволяет логическую фиксацию и отказывает именно файловой стадии. Чтение собственной out-of-band диагностикой допускается при запрете worker-доступа; это не утверждение доступности файлов самому worker. Нельзя заполнять дискT:/системный диск, работать с чужими каталогами/реальным сервером или исправлять сбой прямой записью expected состояния.

`category-delete-shared-range-file-failure` содержит собственные полезные события user_actions доL и другой категории site_errors, реальный общий append-only сегмент, ненулевые файловые bytes, защищённый audit вне подтверждённого удаляемого набора (другая защищённая категория либо внешний журнал), открытый ordinary cycle/critical и настоящую P-LOG-PROBE. `save-text({page,base,text})` действительно сохраняет страницу и создаёт полезное событие через реальный журнал; latest-page-save-log-event связывает именно это сохранение с фактическим eventId. Используется общий контракт сохранения текста, без альтернативного fields.text/default-преобразования в адаптере. Имитатор событий/вставка готового expected вместо save не допускаются.

`prepare-category-log-delete`/`confirm-category-log-delete-direct` — настоящие согласованные UI/HTTP-действия владельца с действительными сессией/CSRF и актуальным подтверждением состава. Отдельный повторный пароль для ordinary category-delete тесты не выдумывают. `outcome=accepted/pending` после запроса означает только фактический приём/ожидание; полный успех определяется реальной стадией и представлением, не одним HTTP200.

## Фактические чтения

Все имена — тестовые представления, не новые публичные endpoints/ORM продукта. Будущие binding/bridge/контроллер ещё требуют независимой проверки происхождения.

- `prepared-log-deletion-set`: реальный operationId/category/boundary/eventIds из зафиксированного manifest, связанный с показанными category/boundary/eventCount. Набор непуст и действительно существует до исполнения. Повтор не меняет boundary/eventIds.
- `log-category-state`: actual-db/current-visible состояние и фактические fileEventIds. После logical done выбранные события не видны, хотя часть их байтов ещё ожидает очистки. Новые события не исчезают. Собственный безопасный аудит операции/чтения допускается.
- `log-delete-shared-range-layout({operationId,tailEventId})`: фактический segmentId, подтверждённые prefix-event IDs/конец префикса и начало нового tail в **том же** сегменте. Проверяются ненулевой конец префикса и порядок offsets. Это положительное доказательство необходимости безопасной частичной переработки, не список двух несвязанных файлов.
- `log-delete-physical-records`: полное чтение/декодирование текущих записей своих файлов, source=actual-complete-decoded-log-file-records, unmappedRecordRanges=0, records[{eventId,category,rangeId,bytesBase64,bytes,sha256}]. Данные получаются из реальных сегментов/манифестов, а не из SQL/подтверждённого списка. Каждый returned диапазон имеет реальные bytes, hash пересчитывается тестом. Привязка event→байты и полнота должны быть отдельно доказаны по выбранному реальному формату; нельзя скрыть оставшиеся записи, возвращая только неудалённые SQL-ID. 64КиБ на запись — предел минимальной синтетической fixture/инструмента, не бизнес-лимит журнала. При сохранении проверяются event/category/size/SHA, физический offset/имя файла/rangeId могут меняться после безопасной переработки. Другая категория и оба новых tail представлены непустыми байтами до/после. Повтор завершённой операции может создавать отдельный безопасный технический аудит, но не новую файловую попытку/удаление защищённых данных.
- `log-delete-operation-state`: фактические operationId/state/boundary/confirmedEventIds/fileAttemptId. `LOGICAL_DONE_FILES_PENDING` означает подтверждённый логический результат без полного файлового успеха; `COMPLETED` — фактическое завершение. Это нормализованные имена тестового контракта. Retry сохраняет operationId/состав и получает новую действительную fileAttemptId; повтор уже completed возвращает прежнюю, не начинает очистку заново.
- `log-delete-progress-view`: actual-http представление владельца с тем же operationId/state, reportedComplete и физическим размером, связанным physicalCaptureId с действительным измерением этой попытки. Pending обязан явно показывать неполное завершение; ненулевой фактический размер не выдаётся за0. Не возвращать желаемое значение из SQL-флага вместо реального интерфейса.
- `log-delete-operation-evidence`: фактический retained аудит вне confirmedEventIds, с исходным operationId и реальным результатом; не исходные тела удалённых событий. Аудит допускается **либо** в другой защищённой категории, **либо** во внешнем выбранном журнале; внешняя запись может иметь ту же смысловую category.
- `log-delete-audit-placement({operationId,eventId})`: actual-audit-record-bytes-and-resolved-storage-placement, связанный с реальным audit event. auditRecord содержит фактически прочитанные непустые bytesBase64/SHA, actual decodedEventId/decodedOperationId и нормализованные физические storeIdentity/objectIdentity/startOffset/endOffset. Тест пересчитывает hash и исключает пересечение с непустыми confirmedPhysicalRanges из фактического зафиксированного manifest данной операции. Эти ranges должны полностью покрывать подтверждённый удаляемый физический набор с доказанной связью к manifest, а не выбираться так, чтобы аудит оказался снаружи. Для kind=protected-category проверяется другая фактическая защищённая category. Для kind=external-journal другая category **не требуется**: проверяются отдельная externalJournalRootIdentity и полная actual auditObjectAncestorIdentities — в ней есть внешний root и нет managedLogRootIdentity. Идентичности/ancestry получают из фактического разрешённого собственного хранилища, например canonical volume/file identities и реального разрешённого дерева после проверки alias/symlink/bind mount, не из имён ролей/пользовательских путей или флага external=true. Bytes и physical ranges связаны с тем же доказанным объектом. Если внешний журнал использует иной выбранный backend, конкретная независимо проверенная проекция должна доказать эквивалентную принадлежность/непересечение его реального store; поле теста не создаёт продуктовые колонки или не выбирает provider/формат журнала. Здесь это отдельная собственная локальная зона стенда, не реальное подключение внешнего сервиса. Метки/корневые ID сами по себе не заменяют будущего независимого ревью полного чтения и физического размещения.

## Общая физическая квота

`log-delete-physical-evidence({operationId,fileAttemptId,captureThrough:'causal-quiescence'})` — actual-isolated-volume-io-trace данной реальной файловой попытки. Capture начинается до её файловых изменений и продолжается через terminal до окончания её причинных потомков; captureClosed/terminalObserved/pendingDescendantWork0 не заменяются заранее выставленными флагами. Наблюдатель должен доказать отсутствие готовых/выполняющихся/отложенных потомков этой операции, способных ещё писать файлы; независимые будущие плановые задания не блокируют эту границу.

Общий CAP=1_073_741_824 включает active/closed/compressed/manifest/temporary всей управляемой папки, не отдельную категорию. allocationEvents имеют возрастающие реальные sequence/totalFileBytes и не превышаютCAP; highWater равен максимуму полного trace. Нужен **уникальный** checkpoint causal-quiescence-end на captureEndSequence с новой фактической FS-инвентаризацией. Тест суммирует уникальные file objects этого checkpoint; заключительное событие final-measurement на той же границе имеет тот же total. UI reportedPhysicalBytes сравнивается именно с ним, не с произвольным последним snapshot. Partial-no-space проверяет и неуспешную, и успешную retry попытки; запланированная reservation/final stat без полного trace не доказывает peak.

Конкретный OS/FS capture/декодер/изоляция пока не выбраны. Periodic polling не подменяет захват промежуточных временных bytes; данные/марки source являются контрактом будущей независимой проверки, не готовым доказательством. В этих двух тестах не требуется реальное заполнение1ГиБ: fault задаётся на собственную файловую операцию, реальные peak-бюджеты наблюдаются отдельно. Не отключать guards размера ответов ради выгрузки исходных log bodies.
